# 26 模型改版：縮窄維度改成 agent 與 CS 的 8 個維度，並用 25 的題目測試

2026-11-08。使用者指示：原模型的六維度（人、地點、時間、行為、限制、在地資源）是為在地創新簡報設計的；現在要設計新工具，應改成大型語言模型（agent）與資訊科學的維度，數量不限六個。提案經使用者確認（「好」）。

## 新的縮窄維度

出發點：現有工具大多是為「人」或「傳統程式」設計的。換成 agent 當操作者後，原本的假設在哪裡壞掉，哪裡就有新工具的機會。每個維度要問：**現有解法在這裡假設了什麼？agent 在這裡有什麼不同？**

| 維度 | 要問的 | 常被打破的假設 | 實驗裡出現過的例子 |
|---|---|---|---|
| 1. 執行者 | 誰在做、有幾個、什麼身分、行為穩不穩定、怎麼理解指示 | 一個身分就是一個操作者；操作者懂言外之意 | 多個 agent 共用 kubeconfig 和憑證 → session 綁定目標（23） |
| 2. 介入點 | 動作在哪裡看得到、攔得到：hook、包裝程式、代理、MCP、CI、檔案系統 | 只能事後看紀錄 | 每個動作都經過帶 session ID 的 hook → 租約、審批綁定（21） |
| 3. 狀態與並行 | 哪些狀態被共用、範圍多大（檔案、叢集、帳號）、誰同時在改 | 鎖只要涵蓋一個指令；一次只有一個人在改 | Terraform lock 只鎖幾秒，agent 的任務橫跨很多指令 |
| 4. 脈絡與記憶 | agent 每一刻知道什麼、能記多久、會不會過期 | 操作者記得自己做過什麼 | 壓縮後忘了哪些步驟已執行 → session 外的操作帳本（23） |
| 5. 生命週期 | 同步或非同步、有沒有人在場、中斷、續接、交接；效果何時出現 | 效果當下就看得到；操作者一直在場 | 卡在用量上限 → 到時自動續跑（25） |
| 6. 驗證 | 什麼能確認實際發生了什麼：測試、dry-run、唯讀查詢、紀錄 | 做的人說完成就是完成 | 看實際改了什麼，而不是猜指令（25） |
| 7. 信任邊界 | 憑證、秘密、沙箱、不可信的輸入、權限 | 操作者看得到的東西，留在操作者這裡 | 值一進入 context 就外流 → 秘密換代號（23）、email 換代號（25） |
| 8. 預算 | token、用量上限、延遲，以及最稀缺的人的注意力 | 人有時間審每一個變更 | N 個 session 同時要人 → 推斷狀態並逐級通知（25） |

**每一維都要問：有什麼現成的東西可以換個用途？**（原模型「重新詮釋在地資源」的核心，改成橫跨所有維度的問題。）例：Kubernetes 的 Lease 物件拿來當 agent 之間的鎖；terraform plan 的 JSON 拿來當審批依據；hook 層從「管權限」改成「協調所有 session」。

| 原維度 | 新的位置 |
|---|---|
| 人 | 執行者 |
| 地點 | 介入點、信任邊界 |
| 時間 | 生命週期 |
| 行為 | 執行者、驗證 |
| 限制 | 預算、信任邊界 |
| 在地資源 | 每一維都要問的問題 |

模型其他部分（抽象化、現有解法與瓶頸、配對、硬湊測試、往上推廣、目標檢查、三個補充）不變。英文提示全文在 [26-data/arms/C2-redesigned.md](26-data/arms/C2-redesigned.md)。

## 測試設計（作答前登記）

- **題目、需求清單、評分規則**：完全沿用 [25](25-open-problem-solutions.md)。
- **組別**：A 直接做、C 原模型（沿用 25 的各 3 份答案，同一份提示）、N 新維度版（新跑 3 次）。
- **評審**：A、C、N 共 81 個解法打亂後放在同一包，Opus、Sonnet 重新盲評，避免和 25 的評分批次不同。
- **主要指標**：平均需求滿足度。
- **判定**：N 比 A 和 C 都高至少 0.10，才算新維度有幫助；否則記為看不出差別。
- **次要**：核心 R1、「本質上是現有做法」的比例（越低越新）、可行性、花費。

**限制**：25 的分數已經接近天花板（0.82–0.86），能往上的空間只有約 0.15，差距可能量不出來。
