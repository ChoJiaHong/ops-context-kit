# 21 回測：用 2026 年 7 月之後才出現的真實工具當標準答案

## 為什麼做這個

05–19 一路卡在同一個地方：**沒有可靠的評估者**。模型自己出題、自己解、自己評分，結果常常在查證後被推翻（[19](19-evaluation-of-18.md)）。原筆記自己也列了這個疑慮：「LLM 自行出題、解題、評分可能只是模型自洽」（[00](00-original-notes.md)）。

這次換一個外部標準：

- 真實世界裡，已經有人遇到某個問題，並且做出工具解決它。
- 只挑我的知識截止（2026 年 6 月）**之後**才建立的工具，所以作答的模型不可能看過答案。
- 只給作答者「工具出現前，作者遇到的問題」，看不同方法能不能自己想出那個工具的核心機制。
- 想出來的比例，就是方法的分數。這是遺傳算法討論裡一直缺的適應度函數。

## 設計（作答前登記，之後不改）

**題目**：GitHub 與 PyPI 上 2026-07-01 之後建立、和目標領域相關的工具（AI 工作流、記憶與規則漂移、驗證 agent 的說法、多 session、infra 變更安全、成本）。建立日期用 GitHub 搜尋或 PyPI 發布紀錄核對。每題一張題卡（[21-data/cases.json](21-data/cases.json)）：

| 欄位 | 給誰看 |
|---|---|
| problem：工具出現前作者遇到的狀況與痛點，不透露解法方向 | 作答者、評審 |
| context：手上有的東西與硬限制 | 作答者 |
| prior_solutions：作者認為不夠的既有做法 | 只有評審與分析用 |
| core_mechanism（M1–M3）、full / partial / not_a_match 規則 | 只有評審 |

題卡由一個沒有參與作答的 agent 從 README 萃取，我再逐張檢查「problem 有沒有洩漏機制」。依賴截止後才出現的產品或模型的題目剔除。

**分組**（提示全文在 [21-data/arms/](21-data/arms/)，都用英文，作答者都是 Opus 5.5，知識截止 2026 年 6 月）：

| 組 | 方法 | 為什麼要這組 |
|---|---|---|
| A | 直接解 | 基準 |
| B | 雙向迴圈（[11](11-double-loop-pure.md)） | 最終抽象模型 |
| C | 原模型＋三個補充（[00](00-original-notes.md)、[16](16-model-selection.md)） | 目前選定的版本 |
| D | 先發散再收斂 | [08](08-results.md) 的教訓：要分開「方法本身」和「只是有結構」 |

- 每組最多提 3 個方案，每個方案的機制不超過 80 個英文字；分析不超過 400 字。
- 不准用任何工具（不能上網、不能讀檔），只在最後用一次 Write 存答案。
- 每組在每個題組跑 2 次（各自獨立的 agent），一個 agent 一次處理一整個題組。

**評審**：Opus 與 Sonnet 各一位，只看到各組的 Proposals 段落（分析段落拿掉），組別隨機標成 S1、S2…。每組答案評：
- best：三個方案中最高的單一分數（2 完全符合、1 部分符合、0 不符），不能把不同方案拼起來；
- p1：第一個方案的分數；
- alt：是否有不同機制、但看起來至少一樣好的方案（嚴格，預設否；只當參考，不拿來最佳化）。

**主要指標**：各組平均 best（兩次作答 × 兩位評審取平均）。次要：平均 p1、命中率（平均 best ≥ 1.5 的題數比例）、逐題勝負。

**題組**：kept 的題卡依 id 排序後，用 Python `random.Random(20261107).shuffle` 打亂，前一半是 dev、其餘是 heldout。

**評審包的做法**（依使用者「新產出只用 MD」的偏好，輔助腳本不放進 repo，這裡寫出做法以便重現）：每份作答只取 `### Proposals` 段落；每題把各組作答用 `random.Random("20261107-<題組>")` 依序打亂，標成 S1、S2…，對照表存在 `judge/key-<題組>.json`。計分：每份作答的 best 先在兩位評審間平均，再在同組兩次作答間平均，得到每題每組一個分數；各組平均即主要指標。

## 演化流程

1. 在 dev 跑 A、B、C、D，評分。
2. 天花板與地板檢查：如果所有組的平均 best 都 > 1.6 或都 < 0.3，題目沒有鑑別力，先換題再繼續，並記錄。
3. 失敗分析：C 沒拿到 2 分的題目，逐題找出「C 的哪一步如果怎麼做，就會走到 M」。
4. 修改成 C′：只能是一般性的程序或內容修改。另一個 agent 檢查 C′ 有沒有夾帶 dev 題目的特定內容，有就退回。
5. 在 heldout 跑 A、D、C、C′（各 2 次），評分。

**接受 C′ 的條件**（heldout）：C′ 的平均 best 至少比 A 與 D 中較高者多 0.25，而且逐題勝多於負。不符合就記為負面結果：在這類題目上，方法沒有勝過基準。

## 限制（事先承認）

- 一個問題不只一種好解法；真實工具的作者選的不一定最好。alt 欄位只能部分補償。
- 題數少（預計每組 6–8 題），只能看方向，不能下統計結論。
- 評審和作答者是同一家族的模型；評分規則寫成可檢查的條件來降低偏差。
- 作答 agent 有能力讀檔，只能靠指示禁止；完成時檢查工具使用次數。
- 機制層級的前例在截止前可能已存在（例如類似概念的舊工具），這種情況算合法的「重新發現」。

- **碰到天花板**：三組都超過事先定的 1.6。依預先登記，題目沒有鑑別力，不拿這組題目演化方法。

**這個結果本身的意思**：知識截止在 2026 年 6 月的模型，只要拿到工具作者寫的問題描述，**直接解**就能想出 7–10 月真實工具的核心機制，幾乎每題都中。所以在這類題目上，**解法不是瓶頸，問題描述才是**：作者寫出「什麼情況下、哪裡痛」的那一刻，難的部分已經做完了。這正好對上原模型自己的主張（[00](00-original-notes.md) 筆記三：問題界定決定解題品質），也說明 05–19 為什麼一直量不出方法的效果：我們一直在比「解法」，但差異如果存在，應該在「找出問題」那一步。

## 第二版：找問題（依預先登記的「沒有鑑別力就換題」）

改成只給**情境**，不給痛點，看各組能不能自己找出真實工具解決的那些問題，連同機制一起想出來。設計在下一節登記後才作答。

### 第二版預先登記（作答前）

- **作答者看到的**：只有一段情境（infra 工程師把大部分工作交給 Claude Code 等 agent、常常平行跑很多 session）、mid-2026 可用的元件清單、任務「找出現有工具還沒解好的問題，各提一個比現有更好的工具」。不給任何痛點。提示全文在 [21-data/arms/v2/](21-data/arms/v2/)。
- **輸出**：最多 10 項，每項一個問題配一個工具（問題 ≤ 40 字、工具 ≤ 80 字），依價值排序。
- **標準答案**：14 個真實工具（第一版的 15 題扣掉 termaxa），每個當一個目標。目標清單只給評審（[21-data/judge/v2-targets.md](21-data/judge/v2-targets.md)）。
- **評分**：每份清單對每個目標打 0／1／2（2：某一項講到這個問題，而且工具符合完全符合規則；1：講到問題但機制只部分符合，或機制符合但針對相關問題）。一項最多算給一個目標。另外數「不對應任何目標、但評審認為有價值」的項目數，只當參考。
- **主要指標**：召回率 = 分數總和 ÷（2 × 14）。分開報 dev 目標（6 個）與 heldout 目標（8 個）的召回率。
- **組別與次數**：A、B、D 各 3 次。C 試 1 次；能完成才補到 3 次，被擋就記錄。
- **評審**：Opus、Sonnet 各一位，看全部清單（隨機標成 L1、L2…）。

| | 預測 |
|---|---|
| H4 | 找問題比找解法難得多：每組召回率都 < 0.6（第一版的解法命中率約 0.9） |
| H5 | B 和 A 差不多（召回率差 < 0.1） |
| H6 | 如果 C 能跑：C 的召回率高於 A |

**之後的演化**：只看 dev 目標的漏網原因修改方法（M′），修改必須是領域無關的一般做法：拿去用在阿里山搜救這類非軟體問題也要能原封不動地用，不能出現 agent、transcript、hook 之類的字。另一個 agent 檢查有沒有夾帶。M′ 跑 3 次，看 **heldout 目標**的召回率。接受條件：M′ 的 heldout 召回率比 A 高至少 0.1。

## 結果二：找問題（v2，A、B、C、D 各 3 次，14 個目標）

| 組 | 召回率（全部） | dev 目標 | heldout 目標 |
|---|---|---|---|
| A 直接 | 0.13 | 0.21 | 0.07 |
| B 雙向迴圈 | 0.12 | 0.14 | 0.11 |
| C 原模型 | 0.10 | 0.11 | 0.09 |
| D 發散收斂 | 0.14 | 0.15 | 0.14 |

- 兩位評審 168 個分數裡 152 個相同。每份清單平均約 6 項「不對應任何目標但評審認為有價值」。
- C 組在找問題時可以完成（3 次都完成），被擋只發生在第一版的找解法。
- **H4 成立**：每組召回率都在 0.10–0.14，遠低於第一版的約 0.9。**H5 成立**（B 和 A 差 0.01）。**H6 不成立**：C 沒有高於 A。四組差距都在同組不同次的波動範圍內（同組三次之間差到 0.15）。
- 常被找到的：unlazy（agent 沒做完就說完成）、claude-bouncer（依實際環境判斷指令）、stalebrain（記憶過期）。從來沒被找到的：elephant-goldfish、evolveguard、honest-arch-diagrams、k8s-skills、openqodex。
- 作答者提出的多半是 infra 專屬問題（每個 session 共用 kubeconfig、Terraform state 與 Helm release 被平行 session 互踩、plan 與 apply 之間狀態改變、GitOps 控制器把手動修改蓋回去、秘密被讀進 context、infra 指令輸出塞爆 context），而 14 個目標大多是一般軟體開發的工具。**召回率低有一部分是因為情境寫的是 infra，目標卻不是**，所以 0.1 不能讀成「找到的問題沒價值」。

**兩個結果合起來**：
1. 給了問題，四種方法都能解（天花板）；沒給問題，四種方法都找不到同樣的問題（地板）。兩次都看不出方法之間的差別。
2. 決定結果的是**輸入**（有沒有作者那段具體的問題描述），不是思考方法。這和 [08](08-results.md)「結構化提示在外部問題上沒有比一般提示好」一致。
3. 這也是原模型自己的說法：創新來自「在地差異、在地資源」。這次作答者手上只有一段通用情境，沒有任何在地資料，原模型的縮窄就沒有東西可以縮。

## 第三版：給證據（演化的第一步，作答前登記）

假設：瓶頸是輸入，不是方法。改動是領域無關的：**先收集處境中的人實際回報的痛點，再找問題**（用在阿里山搜救，就是先讀搜救報告和救難人員的抱怨）。

- **證據**：GitHub `anthropics/claude-code` 在 2026-01-01 到 06-30 之間建立、反應數最多的 100 個 issue 的標題（REST 搜尋 API，依反應數排序，不經我挑選）。全文在 [21-data/evidence-issues.md](21-data/evidence-issues.md)。都在知識截止之前，也都在 14 個工具出現之前。
- **組別**：A＋證據、C＋證據，各 3 次。提示和 v2 完全相同，只在情境後面加上證據和一句「這是實際痛點的證據，不是待辦清單」。
- **評審**：把 v2 的 A、C 各 3 份和新的 6 份放在同一包，重新盲評，避免不同評審批次的差異。

| | 預測 |
|---|---|
| H7 | 證據讓召回率上升：A＋證據比 A 高至少 0.05 |
| H8 | 原模型比較會用在地資料：C 從證據得到的增幅大於 A |

限制：證據是一般使用者對 Claude Code 的回報，偏向一般開發，可能把作答者從 infra 拉向一般開發，召回率上升有一部分可能只是方向對上了目標。

## 結果三：給證據（A＋證據 3 次、C＋證據 1 次）

同一包重新盲評（v2 的 A、C 各 3 份＋新的 4 份），兩位評審 140 個分數裡 128 個相同。

| 組 | 召回率（全部） | dev 目標 | heldout 目標 | 次數 |
|---|---|---|---|---|
| A | 0.15 | 0.22 | 0.09 | 3 |
| A＋證據 | 0.15 | 0.28 | 0.06 | 3 |
| C | 0.12 | 0.11 | 0.12 | 3 |
| C＋證據 | 0.14 | 0.17 | 0.12 | 1 |

- 重新評的 A、C 和第一次評的分數接近（0.13→0.15、0.10→0.12），評分本身穩定。
- **H7 不成立**：證據沒有讓召回率上升（0.15 對 0.15）。**H8 無法判定**：C＋證據只有 1 次。
- C＋證據原本要跑 3 次：1 次被安全機制以 `reasoning_extraction`（要求模型寫出推理過程）擋下，1 次被安全分類器擋下。依提示，沒有自己代做、也沒有換寫法重試。

## 總結

**困境有沒有解決**：評估者有了，而且可靠（三輪評審一致率 90–97%，重評分數穩定，標準答案是知識截止後才出現的真實工具）。但用它量出來的答案是：**在這三種任務上，思考方法都不會改變結果**。

| 任務 | 結果 | 方法之間的差別 |
|---|---|---|
| 給問題、找解法 | 天花板（約 0.9） | 沒有 |
| 給情境、找問題 | 地板（約 0.1） | 沒有 |
| 給情境＋公開抱怨、找問題 | 地板（約 0.15） | 沒有 |

**這代表什麼**：
1. **解法不是瓶頸。** 問題一旦寫清楚，直接問就能得到和真實工具一樣的機制。
2. **找問題是瓶頸，而且提示詞改不動它。** 每份清單約 6.5 項被評審認為「有價值但不對應任何目標」，所以低召回率不是想不出問題，而是可能的問題太多，14 個真實工具只是其中一小部分；「和市場選的一樣」用 14 個目標量不出差別。
3. **原模型的核心是「在地差異」，但這三輪都沒有給它在地資料。** 公開 issue 標題是所有人都看得到的一般抱怨，不是某個人自己的處境。原模型如果有用，應該是在拿到**使用者自己的工作紀錄**（真實失敗、糾正、出事）之後；這正是 [22](22-validation-guide.md) 正在準備、要在使用者電腦上跑的驗證。

**工具面的教訓**：要求子 agent「寫出分析過程」會被安全機制當成擷取推理過程（`reasoning_extraction`）而擋下。原模型的步驟多、要寫的分析多，所以 C 組最常被擋。之後的實驗**只要結果、不要求寫出思考過程**。

**下一步（建議）**：
1. 換一個量「找問題」的標準：不是對 14 個工具算召回率，而是逐項查「截止後有沒有人真的做出這個工具」（GitHub 上 7 月後建立的 repo 有上千個），算精確率。這能回答「方法找出的問題，是不是真的有人痛到去做工具」。
2. 等 22 拿到使用者自己的紀錄後，把紀錄當在地資料，再比一次直接解和原模型。這是原模型唯一還沒被公平測過的主場。
