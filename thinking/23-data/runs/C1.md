## I1
P: Infra engineers running parallel agent sessions must approve each mutating kubectl/helm/terraform command. Prompts pile up, so sessions stall, or engineers rubber-stamp or allow broad patterns like Bash(kubectl:*), letting an out-of-scope delete or replace through. P*: mutating commands of tools with machine-readable dry-run (Terraform/OpenTofu, kubectl, Helm, Pulumi).
Se: Claude Code permission rules, PreToolUse hooks and Auto mode judge the command string or transcript, not its effect: `kubectl apply -f x.yaml` is harmless or fatal depending on x. Atlantis plus Sentinel/OPA check terraform plan JSON, but with static org-wide policies, via a PR round-trip, terraform-only, still human-applied.
Sn: Scope-bound effect approval. At handoff the human confirms a scope manifest: allowed contexts/namespaces/resource-address globs, allowed actions (e.g., no delete or replace) and a max change count. A PreToolUse hook intercepts mutating infra commands, runs the tool's own dry-run (`terraform plan -out` then `show -json`; `kubectl apply --dry-run=server -o json`; `helm upgrade --dry-run` or helm diff), parses it into (target, action) tuples, and auto-approves only if every tuple is in scope. It then executes exactly the checked artifact (saved plan file; validated manifest with resourceVersion precondition). Anything else blocks with a compact diff for the human.
Check: Replay real tasks with seeded out-of-scope changes. Measure human prompts per task (vs allowlist rules) and seeded deletes/replaces reaching apply (vs Auto mode). Sn wins if prompts drop ≥50% with zero escapes and no plan-to-apply drift.

## I2
P: An engineer runs parallel agent sessions on one machine against different clusters/accounts. One runs `kubectl config use-context prod` or `gcloud config set project`, rewriting shared files in $HOME; other sessions and the engineer's terminal silently hit the wrong target. P*: any CLI storing a mutable current target in $HOME.
Se: kubie and kubeswitch give each interactive shell its own kubeconfig; direnv sets per-directory env; git worktrees isolate files. But agent harnesses spawn a fresh non-interactive shell per command (env not kept, direnv hook not loaded) and worktrees share $HOME, so agents fall back to global state.
Sn: Session-scoped CLI state overlays, created by the harness. At session start it makes ~/.agent-sessions/<id>/ with copies of kubeconfig, gcloud and az config dirs and AWS config, and injects KUBECONFIG, CLOUDSDK_CONFIG, AZURE_CONFIG_DIR and AWS_CONFIG_FILE into every subprocess (e.g., a SessionStart hook writing the persisted env file). Token caches (AWS SSO, kube exec plugins) stay shared, so no re-login. The session's target (context/project/account) is pinned at start and shown in the status line; switches change only the session copy, and a command resolving to an unpinned target needs confirmation. Overlays are removed at session end.
Check: Two parallel sessions plus a human terminal; session A switches to prod mid-task. Count commands from B and the terminal reaching prod in API-server/cloud audit logs: Se ≥1 per switch, Sn 0. Field metric: wrong-target incidents per 100 sessions.

## I3
P: Multi-step ops handoffs (upgrade 12 clusters, rotate certs on 80 hosts) get interrupted by compaction, usage limits, crashes or hand-over to another session. The resumed agent trusts its todo list or summary, re-running non-idempotent steps or skipping steps falsely marked done. P*: tasks whose step effects are queryable read-only.
Se: Plan/todo tools (Claude Code TodoWrite, Codex plan) and compaction summaries store the model's self-report; Stop hooks verify only at the end; claude-auto-retry resumes from the same belief. Ansible playbooks are idempotent and checkable, but must be written upfront, while agents improvise imperative steps.
Sn: Harness-owned, probe-verified checklist. Each plan step carries a postcondition probe: a read-only command plus predicate (e.g., `kubectl get nodes -o json | jq '[.items[].status.nodeInfo.kubeletVersion]|all(.=="v1.31.4")'`), approved by the human once at handoff. The model cannot mark steps done; the harness runs the probe after each step and records pass/fail with output. On any resume, compaction or handoff it re-runs probes in order, rebuilds progress from live state, and injects only "steps 1–6 verified; step 7 failing: <probe output>". A previously passing probe that now fails is flagged as drift.
Check: Kill sessions at random points in replayed multi-cluster tasks, then resume. Count re-executed completed steps, skipped incomplete steps and accepted false "done" claims: Se (todo list + summary) vs Sn; Sn should be near zero at similar token cost.

## I4
P: Ops agents run kubectl get secret -o yaml, terraform output/state show, helm get values. Secret values enter the transcript, go to the model provider, persist in local session logs and summaries, and can resurface in commits. P*: secrets whose position in infra-tool output is structurally known.
Se: 1Password `op run` masks only secrets it injected; Vault Agent injects into env/files; gitleaks/trufflehog scan commits; permission deny rules block reading .env paths. None masks secrets the agent fetches from clusters or state at runtime, and commit scanning is too late: transcripts and provider requests already hold them.
Sn: Secret handles at the tool boundary. A wrapper around shell execution parses outputs of known infra commands (Secret .data/.stringData, terraform values marked sensitive, helm values under password/token/key names, plus an entropy fallback) and replaces each value with a handle like «sec:ctx/ns/name/key#h», h being a keyed hash so equal values get equal handles. Values live in a per-session in-memory vault. When a later command contains a handle, the wrapper rewrites it to an env-var reference set only for that process (never argv or transcript) and masks that output. The agent can copy, compare and rotate secrets without seeing them.
Check: Seed canary secrets in a test cluster and Terraform state; run typical debug/rotation tasks. Count canary values in captured provider requests, session logs and commits: Se >0, Sn 0, with task success rate within a few points of Se.

## I5
P: Infra engineers whose subscription quota drains fast across parallel sessions see an agent stop mid-task at the limit, often between a disruptive step and its restore: node drained not uncordoned, replicas scaled down, terraform state locked, for hours until reset. P*: looped ops tasks with identifiable critical sections.
Se: claude-auto-retry (and the requested Codex auto-resume) waits for the reset and continues; ccusage, status lines and /usage show remaining quota. All react after exhaustion or need a human watching; none stops the agent from entering a critical section it cannot finish, so systems stay half-changed.
Sn: Quota-aware step admission. The plan marks critical sections (from drain/scale-down/state lock to restore and verify). Before entering one, the harness reads remaining quota and reset time from the client's rate-limit data, subtracts reserves held by critical sections open in other sessions, and estimates this section's cost as the p90 token cost of earlier iterations of the same step (ops loops repeat steps across nodes; conservative default first), plus a rollback reserve. If quota is short, it does not enter: it parks at the safe point, notifies, and schedules resume at reset or switches to a pre-authorized API key.
Check: Run N-node drain/upgrade loops under tight quotas with parallel load. Count quota stops inside critical sections and node-hours left cordoned or scaled down: auto-retry vs Sn. Sn: zero in-section stops, at most modestly longer completion time.
