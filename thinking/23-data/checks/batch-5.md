# Batch

## X21
P: Ops engineers let agents work across dozens of SSH hosts. Actions become `ssh host '...'` strings or shell loops over host lists: local sandbox, permission rules, checkpoints and logs stop at the ssh boundary, quoting defeats rule matching, and one approval can mutate a whole fleet.
Se: Teleport or Boundary give role-based SSH, short-lived certificates and session recording; Ansible offers check mode and serial waves. They authorize logins or playbooks, not individual agent commands; the harness still sees an opaque ssh string, and installing an agent on every host is impractical.
Sn: Policy-carrying remote exec. The harness blocks raw ssh and pssh in Bash and offers RemoteExec(host-selector, argv, mode). Over the existing SSH connection it pushes a small static shim that re-parses argv and enforces the same allow/deny rules on the host; read mode runs inside a read-only mount namespace with no privilege escalation. Every remote call is logged with host, argv and exit code. Write mode on several hosts runs canary-first waves with a verify probe, halting on failure. Rules can name host groups, e.g., RemoteExec(prod-db, write, systemctl restart pgbouncer).
Check: 50-host lab with seeded risky tasks: count unreviewed remote mutations and hosts broken before halt, Sn versus ssh through Teleport with prefix rules; also human approvals per fleet task.

## X22
P: An engineer runs parallel agent sessions on one infra repo, say staging and prod. kubectl and gcloud fall back to machine-global defaults (current-context, active configuration), so one session's switch silently retargets the others. P*: parallel agent sessions sharing one workstation's ambient cluster and cloud configuration.
Se: Git worktrees per session isolate files only. kubie and direnv scope context per interactive shell, but agents spawn fresh login or non-interactive shells that re-run rc files or skip shell hooks, and agents can switch context themselves; gcloud's active configuration stays global.
Sn: Harness-level target pinning. At session start the user picks one target; the harness writes session-private configs (a minified, single-context, read-only KUBECONFIG, an AWS_CONFIG_FILE with one profile, its own CLOUDSDK_CONFIG directory, TF_WORKSPACE, Helm cache paths) and re-exports them in every tool call after shell startup files run, so rc files cannot override them. Commands that retarget (kubectl config use-context, --context, --profile, gcloud config set) are blocked unless they name the pinned target. The status line, notifications and each approval prompt display the target.
Check: Drill: six parallel sessions across three clusters with scripted context switches. Commands landing on the wrong cluster, counted from API-server audit logs: Sn zero versus nonzero for worktrees plus kubie.

## X23
P: Scope P*: agent sessions that launch side-effecting operations lasting longer than a turn (terraform apply, helm --wait, node drains, migrations). Stream timeouts, dropped connections, usage-limit stops, compaction or a killed session lose the outcome; the resumed agent re-applies, misreports status, or leaves state locks and half-rolled releases.
Se: Session resume (claude --resume, codex resume) plus auto-continue-after-limit wrappers, background shells, and tmux. Resume restores the conversation, not what happened to the side effect; background shells die with the session; tmux keeps the process but the agent has no structured way to find and read its outcome.
Sn: Operation ledger outside the session. A PreToolUse hook rewrites mutating infra commands to run under a detached supervisor (systemd-run --user or setsid) that appends a ledger record: op id, session, resolved target, command, start, PID, log path, exit code, plus a tool-specific post-probe (Terraform state serial, Helm revision/status, rollout status). SessionStart hooks on startup, resume and compact inject a digest of open and finished ops ("op 17 apply prod-net: exit 0 10:42, serial 311→312"). Re-issuing an identical mutation while its op runs is blocked with "attach to op 17". Agents poll ops instead of holding shells.
Check: Fault injection: kill network/session mid-operation across 50 runs; count duplicate applies, orphaned locks, wrong completion claims and minutes to correct recovery, Sn versus resume-only baseline.

## X24
P: Ops engineers letting agents run kubectl, helm or terraform against live systems: a wrong apply, delete or upgrade changes remote state that agent undo cannot reach, so recovery is manual, slow and stressful. P*: agent-made mutations of declarative systems whose prior state is readable (Kubernetes, Helm, Terraform-managed cloud).
Se: Claude Code checkpoints/rewind (like Codex's removed /undo) restore only local file edits, not shell side effects. Remote recovery uses separate tools (helm rollback, Velero backups, versioned Terraform state) that are coarse, manual and not linked to the agent step that did the damage.
Sn: Remote-state undo journal. A pre-execution hook classifies each command; for a mutation it first runs the tool's native dry run (kubectl apply --dry-run=server, helm diff, terraform plan -out) to list exactly which objects will change, saves their pre-images (kubectl get -o yaml, current Helm revision, terraform state pull) and records the inverse action under the tool-call ID. Rewinding the session to step k replays the inverses in reverse order, each after a dry-run diff. Steps whose dry run shows unrecoverable loss (PVC, database, destroy) are flagged irreversible beforehand and need explicit approval.
Check: Drill with 20 seeded harmful agent steps on a test cluster: share undone by one rewind and median time-to-restore, Sn versus engineers recovering manually with helm rollback/Velero (expect ≥90% restored, ≥5× faster).

## X25
P: An agent running a long fan-out task (a package upgrade on 60 hosts) is interrupted by compaction, a usage-limit pause, a dropped stream or a handoff, resumes from its own todo list, and skips or repeats targets. P*: long agent tasks over enumerable targets with queryable live state.
Se: Agent todo lists, plan files and Agent Teams' shared task list hold status the model wrote itself, never re-checked against reality. Ansible or Argo CD are idempotent but need the procedure written upfront, while agent work adapts per target.
Sn: Harness-owned target ledger. At task start the agent registers each target with a read-only postcondition command whose exit code proves it done (e.g., helm status app -o json | jq -e '.version>=7'; ssh host rpm -q agent-2.4). The harness, not the model, stores the ledger. On every resume, compaction, retry or handoff it re-runs all postconditions in parallel, recomputes done/pending/failed, and injects only pending targets with their last error. A target is marked done only when its postcondition passes, so false completion claims cannot enter the ledger.
Check: 40-target rollouts with injected compactions, kills and limit pauses: skipped, duplicated and falsely-done targets plus tokens spent re-orienting after resume, Sn versus todo-list baseline.
