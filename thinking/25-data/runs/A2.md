## P1
Solution: Alias Gateway — a local TLS-intercepting egress proxy that swaps the account email for a user-owned relay alias instead of blocking. A wrapper launches the agent in a network namespace (Linux netns/nftables; macOS sandbox-exec or a dev container) whose only route out is the proxy, with HTTPS_PROXY set and NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE trusting its CA, so scripts the agent writes cannot bypass it. In requests to the model API it rewrites the injected email in the system prompt to the alias (e.g. a SimpleLogin or Hide My Email address), so the model, sub-agents and commits only ever see the alias. In all other external traffic it scans URLs, headers and bodies for the real address in normalized forms (case, URL, base64, hex, quoted-printable, split local part/domain) and rewrites or blocks per destination rule. Loopback and private addresses pass untouched; every substitution is logged.
Differs from existing: Works at the network layer, not as a harness mod or string hook, so it applies on Team/Enterprise and managed machines, covers agent-written scripts and encodings, removes the email from model context without waiting for the vendor, and substitutes rather than denies, so sec.gov-style requests and localhost calls still succeed.
Needs: Agent honoring proxy and custom-CA env vars; an email alias service; rights to create network namespaces or sandboxes. Breaks if the vendor pins certificates (would then need a vendor opt-out).

## P2
Solution: Policy Conformance Kit — one policy file compiled for every agent, plus tests proving what is actually enforced. Engineers write rules once (YAML: tool, command pattern, path globs, decision). The compiler emits native configs (Claude settings.json, Codex rules and project-trust entries, Gemini policy TOML) and installs one shared PreToolUse/PermissionRequest hook plus a --permission-prompt-tool MCP server as the authoritative decider. Its matcher uses a real bash parser, normalizes global flags (git -C, env prefixes), treats cd into the workspace as neutral, ignores quoting noise and decides per subcommand; because it is a hook, it also governs skills and subagents. A conformance suite generated from each rule's positive and negative examples runs every agent headlessly in a sandbox and records executed/prompted/denied per probe; CI reruns it on each agent upgrade and blocks the version bump on drift. A PTY guard answers residual prompts per policy or fails fast.
Differs from existing: Existing hooks each reimplement matching for one agent, unreviewed and unverified. This gives one cross-agent rule source, a parser-based matcher that handles global flags and quoting, and continuous conformance tests that catch regressions (yolo, bypass, workspace policies, ExitPlanMode) before unattended runs depend on them.
Needs: Agent hook and permission-prompt interfaces; sandboxed CI with agent credentials. Vendor-only: honoring hook allow for ExitPlanMode, Remote Control prompts, Gemini policy loading (detected here, not fixed).

## P3
Solution: Forge Shadow Bridge — a self-hosted service that lets GitHub-only cloud agents work on GitLab, Bitbucket (including Data Center) and Azure DevOps code, triggered from Jira, Linear, ADO Boards or GitLab issues. It keeps a push mirror of each repo in a dedicated private GitHub org with no human members. Assigning a ticket to the bridge's bot user creates a mirrored GitHub issue with the ticket text, comments, attachments and links, then triggers the chosen agent through its native GitHub path (`@claude`, `@codex`, Copilot assignment, a Linear or web cloud session on the mirror). When the agent opens a PR on the mirror, the bridge pushes the branch to the origin forge, opens the MR/PR there, links it to the ticket, relays reviewer comments back as agent mentions, and deletes mirror branches after merge. Because the bridge runs inside the network and pushes outward, self-hosted forges behind firewalls work.
Differs from existing: Instead of waiting for each vendor to add each forge, it adapts any forge to the GitHub path every vendor already supports, so Claude Code web, Codex cloud and Linear sessions work today, including Bitbucket Data Center and self-hosted GitLab, without Premium tiers or beta integrations.
Needs: A private GitHub org and the agents' GitHub apps; bot accounts and webhooks on origin forge/tracker; policy approval for transient code copies on GitHub. Native support would remove the mirror (vendor).

## P4
Solution: Session Sentinel — a per-machine daemon that infers agent state from the session logs agents already write (Claude Code transcript JSONL, Codex rollout files, Gemini chat logs) plus process and PTY activity, instead of relying on hooks. Deterministic rules classify each session as working, awaiting approval, awaiting user, finished, errored (API error records) or stalled (process alive, no new records for a configurable N minutes). A finish is confirmed only if no continuation starts within a grace window, removing /goal false alarms. Alerts escalate from terminal bell/OSC to desktop toast to phone (ntfy/Pushover) if unacknowledged after M minutes, deduplicated per session; over Remote SSH the daemon runs on the remote host and pushes directly. The same parsed timeline feeds a statusline segment ("last instruction 14:02, last activity 3 min ago") and a `sentinel log` view listing every turn, tool call and background check with wall-clock timestamps.
Differs from existing: Hook-based notifiers miss turns ending in API errors, go silent when hooks break after updates, fire false or delayed alerts, and fail over SSH. Reading logs and process state catches all of these, works with API keys and any IDE, and adds timestamps without patching UIs.
Needs: Read access to local session logs (undocumented formats; adapters must track versions); ntfy or similar push service. Native in-chat timestamps and IDE toasts need the vendor.

## P5
Solution: Effect Journal — judge shell file activity by its effects, not its command text. A PreToolUse hook on Bash snapshots the workspace into a hidden shadow git repository (separate GIT_DIR; git's stat cache keeps it fast; large ignored dirs excluded); a PostToolUse hook snapshots again and diffs. For every file the command created, changed or deleted, it (1) checks the change against the same Edit/Write path rules and reverts violations from the snapshot, returning the reason to the model; (2) shows the diff like an Edit tool result and appends it to a journal; (3) injects the nested CLAUDE.md and path-scoped rules for touched paths as additionalContext; (4) offers `journal rewind <step>` to restore any earlier state. Read restrictions are enforced by an OS sandbox (bubblewrap/Landlock/Seatbelt) generated from Read deny rules, with file opens logged via fanotify or the sandbox log.
Differs from existing: Blocklist hooks match command strings, lose to python one-liners and heredocs, and fight the harness's Bash-first steering. Diffing outcomes cannot be routed around, lets auto mode keep using Bash, and restores path rules, diffs, rewind and nested CLAUDE.md for shell edits.
Needs: git; Bash Pre/PostToolUse hooks (or a shell wrapper for other agents); OS sandbox for reads. Integration into native /rewind and the diff UI needs the vendor.

## P6
Solution: Session Credential Broker — a small service the team hosts (container or serverless) in front of their vault, reached from cloud sessions over HTTPS. Bootstrap: one broker token stored as a network secret for broker.example.com, so the vendor proxy attaches it and the VM never sees it; where network secrets are unavailable (Team gaps, CMEK, self-hosted), the session requests a device code and the engineer approves it on their phone for a 1-hour token. The broker then (1) reverse-proxies any HTTP API, signing SigV4 for any endpoint (R2, MinIO); (2) mints short-lived scoped credentials (AWS STS session policies, GCP impersonation, Vault dynamic DB users), acting as the missing OIDC; (3) serves private npm/PyPI/Go mirrors on its own host so installs get auth; (4) tunnels TCP (Postgres, Redis) over WebSocket to a local port with broker-side auth; (5) fetches secrets live, so rotation needs no restart. All use is logged per session.
Differs from existing: Network secrets cover only HTTP headers on listed hosts. One brokered secret extends that to databases, any SigV4 endpoint, private registries, short-lived cloud credentials and live rotation, works on Team, CMEK and self-hosted setups, and keeps secrets out of vendor storage. postern and mcp-warden are local-only.
Needs: Broker reachable under the environment's network policy; vault backend; authenticated installs moved from setup scripts to session-start hooks. Keyless bootstrap via vendor-issued OIDC tokens needs the vendor.

## P7
Solution: Change-Set Coordinator — a forge app plus CLI that turns per-repo PRs from any agent session into one reviewable, testable, ordered unit. Agents stamp each PR with a trailer (`Change-Set: cs-142; after: org/types`) via an AGENTS.md/CLAUDE.md instruction or an MCP tool `changeset_open`. The app then (1) cross-links all member PRs with one status table and a combined diff page; (2) runs integration CI that checks out every member branch together, wiring dependencies to those branches (go.work, pnpm overrides, Cargo patch, Maven reactor); (3) adds a required status blocking any member's merge until all are approved and green; (4) merges in dependency order, publishing the upstream package and bumping downstream pins between steps, and opens reverts if a later step fails; (5) enforces per-repo policy (draft-only, required reviewers, push allowed or not). `cs checkout cs-142` reconstructs the whole set locally for multi-repo teleport.
Differs from existing: Existing tools make sessions multi-repo but leave PRs independent. This coordinates the outputs: linked PRs, combined CI, all-or-nothing gating, ordered merges with pin bumps and rollback, per-repo policy and local teleport, and works even with single-repo agents such as Codex cloud via a shared change-set ID.
Needs: GitHub/GitLab app permissions across repos; CI able to clone multiple repos; a package registry for intermediate releases. Native multi-repo teleport inside the agent needs the vendor.

## P8
Solution: Limit-Proof Runner — a supervisor that owns long tasks instead of the terminal. Tasks run headless (`claude -p --output-format stream-json`, `codex exec --json`) under a systemd/launchd user service, with state on disk: session ID, workdir, goal, last event. It detects limits from structured error events and exit codes, not message text; the reset time comes from the event, and if absent it probes with a cheap resume every 30 minutes, covering weekly limits and runs started already over the limit. Before sleeping it commits work in progress to a WIP ref. An OS timer with wake-from-sleep (systemd WakeSystem, pmset schedule) then runs `--resume <id>` with a continuation prompt and a pre-approved permission policy, so it never stalls on prompts. Optional policy: if the reset is over N hours away, continue on another model or an API key with a dollar cap. Alerts go to ntfy.
Differs from existing: Built-in auto-continue skips -p, background, weekly and Remote Control cases and dies with the terminal; wrappers parse human text and break. This uses structured signals plus probing, survives sleep and closed terminals, avoids permission stalls, covers Codex, and can fail over instead of waiting.
Needs: Headless mode with session resume in each agent; OS scheduler with wake support or an always-on host; optional API key for failover. Interactive desktop/Remote Control sessions need vendor support.

## P9
Solution: Turn-Boundary Queue — a per-workspace queue file (`.agent/queue.yaml`: task, mode, done-check, depends-on) that any surface can append to: an `aq add` CLI, a VS Code command, or a phone via a Telegram/ntfy bot. Delivery happens only at true turn ends: a Stop/AfterAgent hook (Claude Code, Codex, Gemini CLI) reads the queue when the agent finishes. If the turn ended in a question, an error or a failing done-check (e.g. `npm test`), it holds the queue and notifies; otherwise it pops one item and returns it as a block-with-reason continuation, so each item becomes exactly one task, in order. Items marked `fresh` instead start a new headless session (`claude -p`, `codex exec`) on the same branch. Each finished item gets its own commit. Nothing goes through the chat box, so mid-turn folding, merged turns, VS Code interrupts and desktop message loss cannot occur.
Differs from existing: Built-in queues fold messages into the running turn, merge them, interrupt in VS Code or lose them in Desktop; hook queues such as claudeq deliver blindly. This delivers one item per finished turn, gates on success, holds on questions, offers fresh sessions and remote adding, and works across agents.
Needs: Stop-type hooks that can continue the session (Claude Code, Codex, Gemini CLI); headless CLIs for fresh mode. A native hold-until-turn-end setting in each UI needs the vendor.
