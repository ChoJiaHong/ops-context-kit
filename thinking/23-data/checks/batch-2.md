# Batch

## X06
P: Terraform plans, `kubectl get -A`, `describe`, `helm template` and pod logs run to thousands of lines. Agents either ingest it all, filling context and draining quota, or truncate with head/grep and miss the one forced replacement, IAM change or CrashLoopBackOff that mattered, then report success.
Se: Harness truncation that spills long output to a file, agent-written grep/jq filters, and plan summarizers such as tf-summarize. Filters are guessed per call and silently drop what they didn't anticipate; summarizers cover one tool and give no completeness guarantee the agent can rely on.
Sn: Typed ops digests: a tool-output hook recognizes known commands and replaces raw output with a fixed-schema digest, keeping raw output on disk behind a queryable handle. Terraform: counts per action, every delete/replace with the forcing attribute, all IAM, network and data-store changes. kubectl: only unhealthy objects, Warning events and counts. Logs: deduplicated templates with counts and first/last timestamps. Invariant: risky items are never elided; if they exceed the budget, the digest says so and mutating commands are refused until the agent pages through them. Digest parsers are tested against recorded outputs per tool version.
Check: On recorded ops tasks, tokens per task fall by half or more versus raw/truncated output, and on seeded plans and clusters with buried destroys or failing pods, miss rate drops to zero while baseline misses some.

## X07
P: Scope P*: agent sessions that can mutate shared infrastructure (clusters, cloud accounts, Terraform workspaces, SSH hosts). Permission rules match command strings, yet the target comes from kube current-context, AWS_PROFILE, workspace or SSH alias. So engineers allowlist "kubectl *" or approve blindly, and one parallel session's "use-context" retargets the others.
Se: Claude Code permission rules (e.g., Bash(kubectl get:*)) plus auto mode's classifier; kubie/kubectx for isolated per-shell contexts. Rules and classifier judge text, not resolved target; kubie's subshell does not survive the agent's fresh shell per call; commands inside ssh or kubectl exec stay opaque.
Sn: Session target binding. At session start the engineer declares targets (e.g., "staging-eu/payments, aws:1111"); the harness gives the session a private KUBECONFIG copy and AWS/gcloud config dir, so context switches stay local. A PreToolUse hook resolves every command's effective target: --context/-n flags or the session's current-context, AWS account via cached sts get-caller-identity, Terraform workspace plus backend key, SSH alias to inventory group, recursing into ssh/exec inner commands. A tier map (dev/stage/prod) and verb class (read/write) drive the decision: reads allowed anywhere, writes auto-allowed on declared non-prod targets, asked on declared prod, denied on undeclared targets.
Check: Seeded run of 200 agent commands with context drift and prod/dev look-alikes: writes reaching undeclared or prod targets without human approval (Sn 0 vs baseline >0); approval prompts per hour versus string allowlists; cross-session context leaks (0).

## X08
P: Long multi-step ops tasks (rolling a chart across twelve clusters, rotating certificates) get cut off by usage limits, stream timeouts, dropped connections, unparseable tool calls or compaction. The resumed agent reconstructs progress from lossy chat memory and re-runs, skips or half-repeats steps against live state that has since moved.
Se: Auto-continue wrappers (claude-auto-retry, requested native auto-resume) and /resume restart the conversation blindly; checkpoint/rewind restores files and chat, not cluster or cloud state. Terraform locking and GitOps protect individual resources, but nothing records which steps of the agent's plan actually took effect.
Sn: A side-effect journal kept by the harness, outside the context window. The agent first registers the task as numbered steps, each with target, mutating command, and a postcondition probe (for example helm release revision N+1, deployment rolled out). Before each mutation the harness appends an intent record with a pre-state fingerprint; afterward, the outcome. On any resume, a reconciler runs probes for open and recent steps, labels each done, not done or drifted, injects that table as authoritative state, blocks automatic continuation when live state drifted during the pause, and offers recorded inverse actions (helm rollback, previous manifest).
Check: Fault injection: kill 100 multi-cluster runs at random points and resume each. Count duplicated, skipped or wrong-order steps and final-state mismatches against the intended end state. Sn should approach zero versus auto-continue plus /resume.

## X09
P: Ops engineers approving agent infrastructure mutations (terraform apply, helm upgrade, kubectl apply) see only a command string, often on a phone via remote control. Approvals become rubber stamps, or they allow `terraform apply` wholesale, so a forced replacement or deletion of a production resource passes unseen.
Se: Claude Code auto mode and allow/deny rules judge command text and transcript, not effects. OPA/Sentinel checks on plans run in Atlantis, Spacelift or Terraform Cloud pipelines, which local agent sessions bypass. helm diff and kubectl diff exist, but agents run them optionally and humans read raw output.
Sn: Effect-gated approval. A pre-execution hook recognizes mutating infra commands and first runs their dry-run twin (terraform plan -out, helm diff upgrade, kubectl diff --server-side, ansible --check --diff). It normalizes the result into a change set (resource, create/update/replace/delete, changed fields, counts) and evaluates Rego policy: e.g., auto-allow non-prod updates; require a human for deletes, replacements, IAM or prod. The human sees the compact change set, not the command. Approval binds to the artifact (saved plan file, or manifest hash plus resourceVersion preconditions); if the live state drifted, execution aborts and re-previews.
Check: Replay 200 recorded agent mutations with seeded destructive changes: Sn surfaces more seeded deletes/replacements, needs fewer human prompts, and executes nothing differing from what was approved, versus auto mode plus allow rules.

## X10
P: Ops engineers running several agent sessions in parallel share one ~/.kube/config, AWS profile set and shell environment. One session runs `kubectl config use-context prod` or `aws sso login`, and another session's next command silently hits the wrong cluster or account. Nobody sees which target each session acts on.
Se: Per-shell context tools (kubie, kubectx, direnv-set KUBECONFIG/AWS_PROFILE) plus agent sandboxes or devcontainers. They rely on convention: the agent's tool shells re-run login profiles, the agent can switch contexts or read other kubeconfigs, and sandboxes limit files and network, not which credentials are usable.
Sn: Session target pinning by capability. At session start the engineer declares a pin: cluster, namespace, cloud account/role, Terraform workspace. A launcher builds a private credential home for that session only: a kubeconfig containing just the pinned context, short-lived cloud credentials minted for that role, and env vars set in the exec wrapper after any profile scripts run. The real ~/.kube and ~/.aws are hidden inside the sandbox, so other targets are unreachable, not merely discouraged. The pin shows in the status line and every approval prompt; changing it requires the human and starts a new session.
Check: Run N parallel sessions with tasks that tempt context switches. Count API calls landing outside each session's pinned target in Kubernetes audit logs and CloudTrail: Sn should be zero, Se nonzero. Also compare setup time per session.
