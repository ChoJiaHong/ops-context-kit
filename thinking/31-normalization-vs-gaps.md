# 31 「正規化問題」和「資訊不完整時補缺口」是同一個問題嗎

2026-11-15。使用者確認：新的問題是「正規化」本身（遇到問題時，判斷它屬於哪個已知問題，再決定用現有解法或需要新解法），並問它和下面這個問題是否一樣：

> 在資訊不完整的情況下，怎麼讓 AI 找出並補齊缺口（找得到的自己查，查不到的問人），把補不了的部分標成假設，只在證據推翻某個假設時才改變結論，並把每次發現的缺口存回專案，下次就不會再缺？

## 比較

| | X：正規化 | Y：補缺口 |
|---|---|---|
| 輸入 | 一個具體問題 | 一個資訊不完整的任務 |
| 產出 | 屬於哪個已知問題；用現有解法、改造，還是要新解法 | 補齊的資訊、一份假設清單、存回專案的缺口紀錄 |
| 核心動作 | 對照已知問題的目錄，逐條檢查成立條件 | 找出缺什麼；能查就查、查不到就問；補不了的標成假設；有反證才改結論；存回去 |
| 需要的外部東西 | 已知問題的目錄 | 查詢的來源、可以問的人、存放紀錄的地方 |

## 判斷：不一樣，但 Y 是 X 的前提

- **不一樣**：X 是一個判斷（分類與決策），Y 是一套處理不完整資訊的流程。
- **Y 是 X 的前提**：正規化時，「這個已知問題的成立條件在我這裡成不成立」常常資訊不全。這時就要用 Y：能查的查、查不到的問、補不了的標成假設；等證據推翻某個假設，「用現有解法就好」的結論才改變。
- **X 是 Y 的一種應用**：Y 適用於任何結論，X 只是結論剛好是「屬於哪個已知問題、要不要新解法」的情況。
- **共同點**：兩者都把說法當假設、靠證據改結論。這也是原模型「問題當假設」的精神。

## 順便把 Y 也正規化

| Y 的部分 | 已知問題 | 已知做法 |
|---|---|---|
| 缺什麼、該查還是該問 | 資訊價值（value of information）；主動提問 | 先算補這項資訊值不值得、哪個來源最便宜；查不到或查的成本太高才問人 |
| 補不了的標成假設、有反證才改結論 | 以假設為基礎的推理與規劃 | 假設式真值維護系統（ATMS，de Kleer 1986）；RAND 的假設式規劃；發現導向規劃（McGrath & MacMillan） |
| 把缺口存回專案 | 組織學習、知識管理 | 決策紀錄（ADR）、事後檢討的教訓清單；在 Claude Code 裡是 CLAUDE.md、記憶檔、kit 的 lessons inbox |

Y 的每一部分都有已知做法；對 AI agent 來說，缺的是把三者接成一個固定流程。

## 原模型能解 Y 嗎

- 能涵蓋一部分：「問題當假設」「情境差異裡的缺少的限制」「v2 的證據等級」。
- 沒有涵蓋：該查還是該問的判斷，以及把缺口存回專案。

## 「正規化」這個說法對嗎？常用嗎？（2026-11-15）

使用者決定先處理正規化，並問這個動作的描述是否正確、有沒有其他說法、常不常用。

**動作本身的描述是對的**，可以寫得更精確：

> 把一個具體問題重新描述成某個已知問題的實例，逐條確認那個已知問題的成立條件在這裡都符合，就能沿用它的已知解法；條件不完全符合時，指出差在哪一條，再決定改造現有解法或另找新解法。

**但「正規化」這個詞容易被誤解**：在資訊領域，正規化通常指資料庫正規化（第一、第二正規形）或資料正規化（把數值縮放到固定範圍），不是這個意思。比較接近的數學意義是「化成標準形式」（canonical form），這也是這個詞能用的原因。

**各領域的既有說法**（這個動作很常用，只是名字不同）：

| 領域 | 說法 | 意思 |
|---|---|---|
| 資訊理論、演算法 | 歸約（reduction） | 把新問題轉成已經會解的問題，用已知解法解 |
| 作業研究、工程 | 問題建模、形式化（problem formulation） | 把實際問題寫成已知的模型，例如排程、指派、最短路徑 |
| 數學解題 | Polya《怎樣解題》的「你知道一個相關的問題嗎？」 | 找一個已經解過、和現在相關的問題，看能不能用它的方法或結果 |
| TRIZ | 從具體問題轉成標準問題 | 具體問題 → 標準問題 → 標準解 → 具體解 |
| 人工智慧 | 案例式推理（case-based reasoning）的檢索與重用 | 找最相似的舊案例、重用它的解法、必要時修改、把新案例存回去（retrieve、reuse、revise、retain） |
| 軟體需求 | 問題框架（Problem Frames，Michael Jackson） | 把需求歸成幾種已知的問題框架，各有對應的解法結構 |
| 醫學 | 鑑別診斷 | 把症狀對應到已知疾病，逐項排除不符合的 |
| 法律 | 涵攝 | 把事實逐一對照法條的構成要件，判斷是否適用 |

**建議用詞**：寫給資訊領域的人看，用「問題歸約」或「把問題歸到已知問題」；寫給一般讀者，用「問題歸類」或「找出這是哪一種已知問題」。

案例式推理的四步（找相似案例、重用、修改、存回去）同時涵蓋了正規化和 Y 的「把缺口存回專案」，是最接近使用者整體想法的既有框架。
