# Batch

## X26
P: Multi-step ops handoffs (upgrade 12 clusters, rotate certs on 80 hosts) get interrupted by compaction, usage limits, crashes or hand-over to another session. The resumed agent trusts its todo list or summary, re-running non-idempotent steps or skipping steps falsely marked done. P*: tasks whose step effects are queryable read-only.
Se: Plan/todo tools (Claude Code TodoWrite, Codex plan) and compaction summaries store the model's self-report; Stop hooks verify only at the end; claude-auto-retry resumes from the same belief. Ansible playbooks are idempotent and checkable, but must be written upfront, while agents improvise imperative steps.
Sn: Harness-owned, probe-verified checklist. Each plan step carries a postcondition probe: a read-only command plus predicate (e.g., `kubectl get nodes -o json | jq '[.items[].status.nodeInfo.kubeletVersion]|all(.=="v1.31.4")'`), approved by the human once at handoff. The model cannot mark steps done; the harness runs the probe after each step and records pass/fail with output. On any resume, compaction or handoff it re-runs probes in order, rebuilds progress from live state, and injects only "steps 1–6 verified; step 7 failing: <probe output>". A previously passing probe that now fails is flagged as drift.
Check: Kill sessions at random points in replayed multi-cluster tasks, then resume. Count re-executed completed steps, skipped incomplete steps and accepted false "done" claims: Se (todo list + summary) vs Sn; Sn should be near zero at similar token cost.

## X27
P: While debugging, agents run kubectl get secret -o yaml, terraform state show, helm get values, env or docker inspect. Credentials then land in model context, provider logs, local transcripts and compaction summaries, forcing rotations and compliance incidents and making security teams restrict agent use in ops.
Se: Sandbox read-denies and hooks block .env or ~/.aws; secret managers (op run, Vault Agent) inject at runtime; gitleaks scans commits; web sessions warn against secrets in env vars. These guard files and commits, not command output, so secrets fetched via kubectl or terraform still reach the model.
Sn: Secret handles at the tool-result boundary. Before any tool output enters context or logs, an interceptor finds secret values: Kubernetes Secret data, Terraform sensitive attributes (from show -json sensitive maps), known credential formats, high-entropy tokens, and exact matches against hashes of values held in Vault or the cloud secret manager. Each is replaced by a handle like {{secret:prod/db#password}}, stored in a per-session vault. The agent can pass handles into later commands; the executor substitutes real values inside the sandbox at run time and re-masks any echo. Revealing a raw value needs explicit human approval.
Check: Red-team suite of 300 ops debugging tasks seeded with canary credentials: canary bytes reaching transcripts or API requests, Sn near zero versus Se many, while task success stays within two points.

## X28
P: Engineers running several agent sessions in parallel share one ~/.kube/config current-context, AWS default profile, gcloud active config and Helm cache. When one session switches context, every other session's next command silently retargets; agent shells also load different init (direnv, mise, login profiles) than the engineer's terminal.
Se: Git worktrees (built into Claude Code and Codex) isolate files, not cluster or cloud targets. kubie, direnv and aws-vault isolate human shells, but agent subprocesses don't reliably inherit them; devcontainers isolate everything but are heavy per session and awkward with SSO credentials.
Sn: Session context capsule: launching a session requires naming a target bundle (e.g. staging-eu). The launcher builds a per-session directory with a KUBECONFIG containing only that bundle's contexts (current-context fixed), an AWS config with only its profiles, CLOUDSDK_CONFIG, TF_DATA_DIR and HELM_*_HOME, pinned tool versions, and exports them into the agent process so every subprocess inherits them. Sandbox rules deny writes to global configs. The bundle name appears in the session title, status line and every approval prompt; switching targets means starting a new capsule, never mutating a shared one.
Check: Eight parallel sessions on different clusters with scripted context switches: capsules show zero commands hitting another session's target while the worktree-only baseline shows some, with session setup under a minute.

## X29
P: An ops engineer's agent checking or changing something on 40 hosts loops ssh one host at a time. Near-identical outputs flood the context, burn quota and push earlier findings into compaction, and the three hosts that actually differ get lost in the noise or truncated away.
Se: Ansible ad-hoc commands or pssh driven by the agent, plus the harness's output truncation. They batch execution but return verbose per-host output; truncation cuts arbitrarily and can drop exactly the outliers, and the agent compensates with ad-hoc head/grep pipelines that hide anomalies.
Sn: A fleet-exec tool that returns clustered results instead of raw streams. It runs a command over an inventory selector, normalizes each host's output (masks hostnames, IPs, timestamps, PIDs), groups identical results, and returns "37 hosts: <one sample>; 3 hosts: <diff against majority>", with handles to fetch any host's raw output from disk. Context grows with distinct outcomes, not host count. For changes, the same clustering gates the rollout: run on one canary, then 10%, then the rest, and halt automatically when any host's post-check output splits from the canary's verified cluster.
Check: On recorded fleet tasks with planted outlier hosts: tokens consumed per task, outliers correctly named by the agent, and bad changes halted before reaching 10% of hosts, compared with agent-driven Ansible/pssh.

## X30
P: Scope P*: agent-issued mutations through tools with a native dry-run (Terraform/OpenTofu, Helm, kubectl, Pulumi). The approval prompt shows "terraform apply" or "helm upgrade", not the effect; an engineer juggling parallel sessions approves without seeing that a database will be replaced, or stalls each session to read plan output.
Se: Atlantis/HCP Terraform: plan posted for review, apply runs exactly the saved plan. Strong guarantee, but a PR round-trip per iteration is too slow for interactive agent work and covers only Terraform; agent prompts and auto-mode classifiers judge command text, not effect.
Sn: Plan-bound approval. A PreToolUse hook catches mutating infra commands and first runs the tool's own dry-run against the resolved target: terraform plan -out, helm diff upgrade (or --dry-run=server), kubectl diff --server-side. It shows a ten-line effect card: target, create/update/replace/destroy counts, destructive items flagged by kind (PVC, StatefulSet, database, IAM). Approval binds to the plan's hash: Terraform applies the saved planfile; for Helm/kubectl the diff is recomputed just before execution and any hash change re-prompts. Policy can auto-approve zero-destroy plans on non-prod, so humans review only destructive or prod diffs.
Check: On seeded tasks hiding destructive side effects (forced replacement, namespace deletion): share caught before execution (Sn vs command-text prompts), median human seconds per approval, and fraction of applies auto-approved safely.
