## I1
P: Scope P*: agent sessions that can mutate shared infrastructure (clusters, cloud accounts, Terraform workspaces, SSH hosts). Permission rules match command strings, yet the target comes from kube current-context, AWS_PROFILE, workspace or SSH alias. So engineers allowlist "kubectl *" or approve blindly, and one parallel session's "use-context" retargets the others.
Se: Claude Code permission rules (e.g., Bash(kubectl get:*)) plus auto mode's classifier; kubie/kubectx for isolated per-shell contexts. Rules and classifier judge text, not resolved target; kubie's subshell does not survive the agent's fresh shell per call; commands inside ssh or kubectl exec stay opaque.
Sn: Session target binding. At session start the engineer declares targets (e.g., "staging-eu/payments, aws:1111"); the harness gives the session a private KUBECONFIG copy and AWS/gcloud config dir, so context switches stay local. A PreToolUse hook resolves every command's effective target: --context/-n flags or the session's current-context, AWS account via cached sts get-caller-identity, Terraform workspace plus backend key, SSH alias to inventory group, recursing into ssh/exec inner commands. A tier map (dev/stage/prod) and verb class (read/write) drive the decision: reads allowed anywhere, writes auto-allowed on declared non-prod targets, asked on declared prod, denied on undeclared targets.
Check: Seeded run of 200 agent commands with context drift and prod/dev look-alikes: writes reaching undeclared or prod targets without human approval (Sn 0 vs baseline >0); approval prompts per hour versus string allowlists; cross-session context leaks (0).

## I2
P: Scope P*: agent-issued mutations through tools with a native dry-run (Terraform/OpenTofu, Helm, kubectl, Pulumi). The approval prompt shows "terraform apply" or "helm upgrade", not the effect; an engineer juggling parallel sessions approves without seeing that a database will be replaced, or stalls each session to read plan output.
Se: Atlantis/HCP Terraform: plan posted for review, apply runs exactly the saved plan. Strong guarantee, but a PR round-trip per iteration is too slow for interactive agent work and covers only Terraform; agent prompts and auto-mode classifiers judge command text, not effect.
Sn: Plan-bound approval. A PreToolUse hook catches mutating infra commands and first runs the tool's own dry-run against the resolved target: terraform plan -out, helm diff upgrade (or --dry-run=server), kubectl diff --server-side. It shows a ten-line effect card: target, create/update/replace/destroy counts, destructive items flagged by kind (PVC, StatefulSet, database, IAM). Approval binds to the plan's hash: Terraform applies the saved planfile; for Helm/kubectl the diff is recomputed just before execution and any hash change re-prompts. Policy can auto-approve zero-destroy plans on non-prod, so humans review only destructive or prod diffs.
Check: On seeded tasks hiding destructive side effects (forced replacement, namespace deletion): share caught before execution (Sn vs command-text prompts), median human seconds per approval, and fraction of applies auto-approved safely.

## I3
P: Scope P*: agents operating infrastructure whose tools print credentials. Routine steps (kubectl get secret -o yaml, terraform output -json, helm get values, aws sts assume-role) put live secrets into the model context, local session logs, compaction summaries and shared transcripts; denying those commands breaks legitimate debugging and rotation tasks.
Se: Process-injection secret tools (1Password op run, Vault Agent, aws-vault exec) plus agent deny rules on .env files and CI-style log masking. They keep secrets out of files and prompts, not out of command output; masking with *** also blinds the agent, which can no longer compare or reuse values.
Sn: Secret handles at the exec layer. A PreToolUse hook routes infra commands through a wrapper that uses the sensitivity tools already declare (Kubernetes Secret data/stringData, Terraform sensitive outputs and state attributes, STS credential fields, Helm values matched by chart schema/key patterns) to replace each value with a stable handle like {{sec:k8s/prod/payments/db-password#3f9a}} (keyed-hash suffix allows equality and "did it change?" checks). Handles in later commands are substituted only inside the child process, and its output is re-masked against all known values. Transcripts, logs and summaries hold only handles; the handle map lives in memory, never on disk.
Check: Seeded rotation/debug tasks with canary secrets: canary strings in transcripts, JSONL logs and summaries (Sn 0 vs unprotected many) and task success (Sn near unprotected, clearly above *** masking).

## I4
P: Scope P*: agent sessions that launch side-effecting operations lasting longer than a turn (terraform apply, helm --wait, node drains, migrations). Stream timeouts, dropped connections, usage-limit stops, compaction or a killed session lose the outcome; the resumed agent re-applies, misreports status, or leaves state locks and half-rolled releases.
Se: Session resume (claude --resume, codex resume) plus auto-continue-after-limit wrappers, background shells, and tmux. Resume restores the conversation, not what happened to the side effect; background shells die with the session; tmux keeps the process but the agent has no structured way to find and read its outcome.
Sn: Operation ledger outside the session. A PreToolUse hook rewrites mutating infra commands to run under a detached supervisor (systemd-run --user or setsid) that appends a ledger record: op id, session, resolved target, command, start, PID, log path, exit code, plus a tool-specific post-probe (Terraform state serial, Helm revision/status, rollout status). SessionStart hooks on startup, resume and compact inject a digest of open and finished ops ("op 17 apply prod-net: exit 0 10:42, serial 311→312"). Re-issuing an identical mutation while its op runs is blocked with "attach to op 17". Agents poll ops instead of holding shells.
Check: Fault injection: kill network/session mid-operation across 50 runs; count duplicate applies, orphaned locks, wrong completion claims and minutes to correct recovery, Sn versus resume-only baseline.

## I5
P: Scope P*: delegated multi-step infra tasks whose result is live state, not code. Agents report "deployed", "fixed" or "done" from their own narrative; the engineer, juggling parallel sessions, must re-verify every change by hand or trust claims that miss a pending rollout, drifted resource or skipped environment.
Se: Stop hooks that run a fixed test/lint command, CI pipelines, and GitOps health status (Argo CD/Flux synced/healthy). Stop hooks and CI check code, not which live targets this session touched; Argo shows health only for apps it manages and nothing forces the agent's final report to cite it.
Sn: Convergence-evidence gate. Every mutation the session made (from its command log or op ledger) registers a target and a matching convergence probe: terraform plan -detailed-exitcode returns 0, helm status deployed at expected revision, kubectl rollout status complete with ready replicas, Argo app Synced/Healthy, or an SSH service check. A Stop hook refuses completion while any touched target lacks a passing probe newer than its last mutation, returning the failing probes to the agent. The handoff report is generated from probe results, one row per target with evidence, so the engineer reads verified state, not the agent's prose.
Check: On 100 delegated infra tasks: rate of "done" reports later found unconverged (Sn vs Stop-hook/CI baseline), engineer minutes spent re-verifying per task, and extra agent turns the gate costs.
