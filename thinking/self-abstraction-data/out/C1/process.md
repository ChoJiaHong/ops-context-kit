# 分析過程（C1）

**採用的方法：** 先比對三個版本，找出作者改寫時一直保留的部分（跨版本不變量）；再問這套方法「比不用它多拿到了什麼資訊」，用這個機制把不變量串成骨架；最後列出它會失效的情況，反推它最有優勢的問題。理由：三份筆記是同一個模型的演化版本，改寫後仍留下來的東西最能代表核心；骨架要能解釋為什麼有效才算抓到核心；從失效倒推適用範圍，比從正面列舉更不容易自我說服。我刻意不用筆記自己的流程（抽象化、縮窄、配對、向上泛化、硬湊檢驗）來分析它，只把它當分析對象。

## 2. 不變量與變量

**三版都有、只換了名字的（候選引擎）：**
- (a) 一個既有的通用解當參照，新解是「改造它」而不是從零開始。
- (b) 具體情境和一般情境之間的落差。
- (c) 這個落差被轉成限制或資源，並且要碰到參照解的弱點。
- (d) 資源的**功能重述**：三份筆記在解釋「價值到底在哪」時，都指向同一個轉換——鐵路不再是「鐵路」，而是「能深入山區的移動補給載具」。筆記一甚至直接說創新不在無人機、也不在充電，而在這個重新看待。

**會變動的（外殼）：** 情境怎麼取得（自由縮窄或固定）、目的（新穎或有效）、驗證標準、要不要求範圍、寫給誰用。這些都在回應「給誰用、怕什麼風險」，不是引擎本身。

**判讀：** 「縮窄」雖然是筆記一、二的招牌，但它只是取得情境的手段，筆記三拿掉它方法仍然完整，所以它不屬於骨架。功能重述在三版裡出現的位置不同（筆記一在結論、筆記二在向上泛化、筆記三在術語），但內容一樣，應該升格為骨架元素。

## 3. 演化方向

- **一 → 二：** 從「既有解失效」改成「既有解不是最佳」。適用面大幅擴大，因為大多數真實問題的既有解都還能用。筆記二的向上泛化，實際上就是把功能重述一層層做出來（鐵路→固定路線→可移動補給載具）；它和筆記一的硬湊檢驗是同一件事的建設性版本：都在找「真正起作用的是哪個屬性」。
- **二 → 三：** 怕問題漂移，所以固定目標、只改表述；使用者換成 LLM。差異的分類多了「漏掉的限制」和「改變的假設」——「假設」這個詞第一次明確出現。
- **趨勢：** 三個版本一步步收斂到同一個東西：**拿具體情境去檢查通用解默認的假設**。

## 4. 機制：這套方法多拿到了什麼資訊？

通用解是為「平均情境」最佳化的，所以它內含一組對情境的默認假設。只要具體情境違反了其中一條**綁定的**假設（也就是瓶頸的來源），通用解就會留下改進空間。方法的收益＝把情境中通用解忽略的特徵納入考量的價值；但只有碰到綁定假設的特徵才有用，其他差異都是雜訊（這也解釋了為什麼會出現「硬湊」）。

用這個機制重讀筆記裡全部的例子：

| 例子 | 通用解 | 瓶頸背後的默認假設 | 情境特徵如何違反它 |
|---|---|---|---|
| 阿里山搜救 | 無人機從固定基地起降 | 基地是固定的 | 有深入山區的軌道載具 → 基地可以移動 |
| SRE「CPU 高，加機器」 | 擴容 | 負載是正常需求，會隨機器數線性分攤 | retry storm、hot partition、錯誤部署 → 加機器沒用 |
| Coding「優化這個 function」 | 優化函式內的運算 | 成本在函式內部 | ORM 迴圈查資料庫 → N+1 query |
| Support「退款系統壞了」 | 修自家系統 | 故障出在自家系統 | 依賴外部 payment provider → timeout |

四個例子都符合「情境特徵違反綁定假設」這個模式，所以骨架同時涵蓋創新例和診斷例。**但兩類例子有一個關鍵差別**：阿里山的偏差是看一眼地方就知道的資源（便宜、可觀察）；SRE 那幾例的偏差要靠 log、metrics 才看得到，「和一般情況對照」本身產生不出答案，只能告訴你該去查哪些假設。這一點後面會成為失效模式。

**結構上的發現：** 筆記一、二把「限制」和「差異」分開搜尋再配對，因此自己承認不知道「下一次該沿哪個維度縮窄」（筆記二未解問題 3），搜尋空間也是組合爆炸。用「假設」把兩者接起來，搜尋就變成有方向的：瓶頸 → 它默認了什麼 → 只就這些假設去查情境。這是我把「綁定假設」放在骨架中心的原因，雖然筆記直到第三版才講出這個詞。

## 5. 和相近方法的區隔（用來定位，不是用來分析）

相近的有 TRIZ 的資源分析、案例式推理（檢索後改造）、打破假設（assumption busting）、XY problem／問題診斷。骨架裡單看每個零件都不新；它的特色在於組合：**以既有解的瓶頸為錨＋情境是給定的＋資源要功能重述＋用同一個指標比相對優勢**。所以它的定位應該放在「這個組合剛好必要」的問題上，而不是泛用的問題界定——筆記三自己擔心的新穎性、必要性問題，正是因為把它放在太泛的位置。

## 7. 候選問題比較

候選問題：
- **A** 學生或競賽的創新提案（筆記一原本的場景）
- **B** 為給定場域適配一套方案（在地部署、產品在地化、把通用技術導入特定場域）
- **C** LLM agent 重述需求、診斷問題（筆記三）
- **D** 研究定位：為新方法找出它有優勢的問題範圍（筆記二）

| | C1 | C2 | C3 | C4 | C5 | C6 | C7 | C8 |
|---|---|---|---|---|---|---|---|---|
| A | ✓ | △ | △ | ✓ | ✓ | ✗ 多靠口頭評審 | ✗ 可自由挑情境 | ✓ |
| B | ✓ | ✓ | ✓ 常見 | ✓ | ✓ | ✓ | ✓ | △ 視領域而定 |
| C | ✓ 有標準處置 | ✓ | ✓ | ✗ 要靠蒐證 | ✓ | △ | ✓ | △ |
| D | ✓ | △ | △ | △ | △ | △ 筆記二自承 U 未定義 | ✗ 範圍本身就是輸出 | ✓ |

**結論：** 選 B。A 其實是條件比較弱的 B——如果題目先指定情境（例如「為你的家鄉設計」），A 就會變成 B，也就能避開硬湊。C 適合當作骨架的次要用途（產生「該去查的假設」清單），但不是它最有優勢的地方。D 的效用函數和停止條件都還沒解決，不適合當作 P*。

## 8. 為 P* 調整模型

和原模型相比的改動與理由：
1. **取消自由縮窄，情境是給定的：** 同時處理問題漂移（F7）和「要沿哪個維度縮窄」的問題。
2. **用假設清單引導情境盤點：** 取代六個維度的盲目搜尋，直接回答筆記二的未解問題 3。
3. **效用＝基準解自己的指標：** 不必另外定義 U，部分回答筆記二的未解問題 1、2。
4. **範圍直接由功能屬性定義：** 不必一層層移除情境；功能重述完成時，範圍也就出來了（取代筆記二的向上泛化）。
5. **硬湊的精神保留，併入驗證：** 確認拿掉該屬性後效益就消失。
6. **新增「何處基準解仍較佳」：** 防止新解被過度推廣。

## 9. 骨架定稿的取捨

- 定為 6 個元素：基準解、綁定假設、情境偏差、功能重述、調適解、優勢與範圍。
- 「限制」併入「綁定假設」：只說限制不說它的成因，就沒辦法導引搜尋。
- 「縮窄」和「大問題」不列入：前者是手段，後者是輸入。
- 「目標守恆」原本想單獨列一項，最後併進「優勢與範圍」（因為比較優勢的前提就是目標和指標都不變），以控制元素數量。
- 形式化只保留三行：通用解的定義、成立條件、範圍集合。
