# Batch

## X11
P: Ops commands emit huge output: terraform plan on large states, kubectl describe, helm template, journalctl. Raw output burns context and quota and forces compaction, while blind truncation or the agent's head/grep can drop the one line that matters, like a buried destroy. P*: verbose ops-tool output with a machine-readable form.
Se: Claude Code's fixed output cap (BASH_MAX_OUTPUT_LENGTH) middle-truncates long output, and the agent's ad hoc head/tail/grep is content-blind. Terraform's summary line gives counts, not which resources are destroyed or replaced.
Sn: Structured digests for ops commands. A wrapper recognises known commands, fetches their JSON form (terraform show -json on the saved plan, kubectl -o json, helm status -o json, journalctl -o json) and returns a digest built by fixed rules: plan → counts plus every delete/replace address; workloads → only non-Ready conditions and Warning events, deduplicated with counts; logs → error-level lines grouped by message template. Full output is saved with a handle the agent can query by jq path or grep. Destructive and failing items are always listed, never truncated.
Check: 30 ops tasks with seeded buried destroys and crash-looping pods: input tokens per task, compactions per session, and share of seeded items named in the agent's final report, Sn versus default truncation.

## X12
P: An engineer approving infra changes from many sessions sees prompts like "Allow terraform apply?" with no diff attached. They rubber-stamp. Even when the agent printed a plan earlier, what runs can differ: the plan was regenerated, files changed afterward, or -auto-approve skipped review.
Se: Agent permission rules and PreToolUse hooks match command strings, not effects; auto-approval classifiers judge intent, not the actual diff. Atlantis/Spacelift bind apply to a reviewed plan but only through a pull-request loop, too slow for interactive agent iteration, and agents with local credentials bypass them.
Sn: Diff-bound approval tokens. Mutating infra commands (terraform apply, helm upgrade/install, kubectl apply/delete/patch) are blocked by an exec wrapper unless they carry a token. To get one, the agent calls propose_change: it runs the dry-run (terraform plan -out, helm diff, kubectl diff --server-side), normalizes it into a resource-level change set with every delete and replace listed in full, and hashes it with the session's target and input file digests. The human approves from a cross-session inbox. At execution the wrapper applies the saved plan or recomputes the diff and refuses on hash mismatch. Policy can auto-approve low-risk change classes.
Check: Run both setups for a month: share of executed changes matching an approved diff, destroys/replaces executed unseen by a human, median approval time. Sn should reach 100% and zero without slower approvals.

## X13
P: An engineer runs parallel agent sessions on one machine against different clusters/accounts. One runs `kubectl config use-context prod` or `gcloud config set project`, rewriting shared files in $HOME; other sessions and the engineer's terminal silently hit the wrong target. P*: any CLI storing a mutable current target in $HOME.
Se: kubie and kubeswitch give each interactive shell its own kubeconfig; direnv sets per-directory env; git worktrees isolate files. But agent harnesses spawn a fresh non-interactive shell per command (env not kept, direnv hook not loaded) and worktrees share $HOME, so agents fall back to global state.
Sn: Session-scoped CLI state overlays, created by the harness. At session start it makes ~/.agent-sessions/<id>/ with copies of kubeconfig, gcloud and az config dirs and AWS config, and injects KUBECONFIG, CLOUDSDK_CONFIG, AZURE_CONFIG_DIR and AWS_CONFIG_FILE into every subprocess (e.g., a SessionStart hook writing the persisted env file). Token caches (AWS SSO, kube exec plugins) stay shared, so no re-login. The session's target (context/project/account) is pinned at start and shown in the status line; switches change only the session copy, and a command resolving to an unpinned target needs confirmation. Overlays are removed at session end.
Check: Two parallel sessions plus a human terminal; session A switches to prod mid-task. Count commands from B and the terminal reaching prod in API-server/cloud audit logs: Se ≥1 per switch, Sn 0. Field metric: wrong-target incidents per 100 sessions.

## X14
P: Scope P*: agents operating infrastructure whose tools print credentials. Routine steps (kubectl get secret -o yaml, terraform output -json, helm get values, aws sts assume-role) put live secrets into the model context, local session logs, compaction summaries and shared transcripts; denying those commands breaks legitimate debugging and rotation tasks.
Se: Process-injection secret tools (1Password op run, Vault Agent, aws-vault exec) plus agent deny rules on .env files and CI-style log masking. They keep secrets out of files and prompts, not out of command output; masking with *** also blinds the agent, which can no longer compare or reuse values.
Sn: Secret handles at the exec layer. A PreToolUse hook routes infra commands through a wrapper that uses the sensitivity tools already declare (Kubernetes Secret data/stringData, Terraform sensitive outputs and state attributes, STS credential fields, Helm values matched by chart schema/key patterns) to replace each value with a stable handle like {{sec:k8s/prod/payments/db-password#3f9a}} (keyed-hash suffix allows equality and "did it change?" checks). Handles in later commands are substituted only inside the child process, and its output is re-masked against all known values. Transcripts, logs and summaries hold only handles; the handle map lives in memory, never on disk.
Check: Seeded rotation/debug tasks with canary secrets: canary strings in transcripts, JSONL logs and summaries (Sn 0 vs unprotected many) and task success (Sn near unprotected, clearly above *** masking).

## X15
P: Infra engineers whose subscription quota drains fast across parallel sessions see an agent stop mid-task at the limit, often between a disruptive step and its restore: node drained not uncordoned, replicas scaled down, terraform state locked, for hours until reset. P*: looped ops tasks with identifiable critical sections.
Se: claude-auto-retry (and the requested Codex auto-resume) waits for the reset and continues; ccusage, status lines and /usage show remaining quota. All react after exhaustion or need a human watching; none stops the agent from entering a critical section it cannot finish, so systems stay half-changed.
Sn: Quota-aware step admission. The plan marks critical sections (from drain/scale-down/state lock to restore and verify). Before entering one, the harness reads remaining quota and reset time from the client's rate-limit data, subtracts reserves held by critical sections open in other sessions, and estimates this section's cost as the p90 token cost of earlier iterations of the same step (ops loops repeat steps across nodes; conservative default first), plus a rollback reserve. If quota is short, it does not enter: it parks at the safe point, notifies, and schedules resume at reset or switches to a pre-authorized API key.
Check: Run N-node drain/upgrade loops under tight quotas with parallel load. Count quota stops inside critical sections and node-hours left cordoned or scaled down: auto-retry vs Sn. Sn: zero in-section stops, at most modestly longer completion time.
