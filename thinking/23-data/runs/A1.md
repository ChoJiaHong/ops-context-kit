## I1
P: Ops engineers running several agent sessions in parallel share one ~/.kube/config, AWS profile set and shell environment. One session runs `kubectl config use-context prod` or `aws sso login`, and another session's next command silently hits the wrong cluster or account. Nobody sees which target each session acts on.
Se: Per-shell context tools (kubie, kubectx, direnv-set KUBECONFIG/AWS_PROFILE) plus agent sandboxes or devcontainers. They rely on convention: the agent's tool shells re-run login profiles, the agent can switch contexts or read other kubeconfigs, and sandboxes limit files and network, not which credentials are usable.
Sn: Session target pinning by capability. At session start the engineer declares a pin: cluster, namespace, cloud account/role, Terraform workspace. A launcher builds a private credential home for that session only: a kubeconfig containing just the pinned context, short-lived cloud credentials minted for that role, and env vars set in the exec wrapper after any profile scripts run. The real ~/.kube and ~/.aws are hidden inside the sandbox, so other targets are unreachable, not merely discouraged. The pin shows in the status line and every approval prompt; changing it requires the human and starts a new session.
Check: Run N parallel sessions with tasks that tempt context switches. Count API calls landing outside each session's pinned target in Kubernetes audit logs and CloudTrail: Sn should be zero, Se nonzero. Also compare setup time per session.

## I2
P: An engineer approving infra changes from many sessions sees prompts like "Allow terraform apply?" with no diff attached. They rubber-stamp. Even when the agent printed a plan earlier, what runs can differ: the plan was regenerated, files changed afterward, or -auto-approve skipped review.
Se: Agent permission rules and PreToolUse hooks match command strings, not effects; auto-approval classifiers judge intent, not the actual diff. Atlantis/Spacelift bind apply to a reviewed plan but only through a pull-request loop, too slow for interactive agent iteration, and agents with local credentials bypass them.
Sn: Diff-bound approval tokens. Mutating infra commands (terraform apply, helm upgrade/install, kubectl apply/delete/patch) are blocked by an exec wrapper unless they carry a token. To get one, the agent calls propose_change: it runs the dry-run (terraform plan -out, helm diff, kubectl diff --server-side), normalizes it into a resource-level change set with every delete and replace listed in full, and hashes it with the session's target and input file digests. The human approves from a cross-session inbox. At execution the wrapper applies the saved plan or recomputes the diff and refuses on hash mismatch. Policy can auto-approve low-risk change classes.
Check: Run both setups for a month: share of executed changes matching an approved diff, destroys/replaces executed unseen by a human, median approval time. Sn should reach 100% and zero without slower approvals.

## I3
P: Long multi-step ops tasks (rolling a chart across twelve clusters, rotating certificates) get cut off by usage limits, stream timeouts, dropped connections, unparseable tool calls or compaction. The resumed agent reconstructs progress from lossy chat memory and re-runs, skips or half-repeats steps against live state that has since moved.
Se: Auto-continue wrappers (claude-auto-retry, requested native auto-resume) and /resume restart the conversation blindly; checkpoint/rewind restores files and chat, not cluster or cloud state. Terraform locking and GitOps protect individual resources, but nothing records which steps of the agent's plan actually took effect.
Sn: A side-effect journal kept by the harness, outside the context window. The agent first registers the task as numbered steps, each with target, mutating command, and a postcondition probe (for example helm release revision N+1, deployment rolled out). Before each mutation the harness appends an intent record with a pre-state fingerprint; afterward, the outcome. On any resume, a reconciler runs probes for open and recent steps, labels each done, not done or drifted, injects that table as authoritative state, blocks automatic continuation when live state drifted during the pause, and offers recorded inverse actions (helm rollback, previous manifest).
Check: Fault injection: kill 100 multi-cluster runs at random points and resume each. Count duplicated, skipped or wrong-order steps and final-state mismatches against the intended end state. Sn should approach zero versus auto-continue plus /resume.

## I4
P: An ops engineer's agent checking or changing something on 40 hosts loops ssh one host at a time. Near-identical outputs flood the context, burn quota and push earlier findings into compaction, and the three hosts that actually differ get lost in the noise or truncated away.
Se: Ansible ad-hoc commands or pssh driven by the agent, plus the harness's output truncation. They batch execution but return verbose per-host output; truncation cuts arbitrarily and can drop exactly the outliers, and the agent compensates with ad-hoc head/grep pipelines that hide anomalies.
Sn: A fleet-exec tool that returns clustered results instead of raw streams. It runs a command over an inventory selector, normalizes each host's output (masks hostnames, IPs, timestamps, PIDs), groups identical results, and returns "37 hosts: <one sample>; 3 hosts: <diff against majority>", with handles to fetch any host's raw output from disk. Context grows with distinct outcomes, not host count. For changes, the same clustering gates the rollout: run on one canary, then 10%, then the rest, and halt automatically when any host's post-check output splits from the canary's verified cluster.
Check: On recorded fleet tasks with planted outlier hosts: tokens consumed per task, outliers correctly named by the agent, and bad changes halted before reaching 10% of hosts, compared with agent-driven Ansible/pssh.

## I5
P: Parallel agent sessions in separate git worktrees each test and apply to the same shared environment (staging cluster, Helm release, Terraform state). Session B applies from a branch missing session A's unmerged change and silently reverts it; both report success, and the breakage surfaces later as unexplained drift.
Se: Worktrees isolate code, not live infrastructure. Terraform state locking only serializes applies; it never asks whether the applier has the other's changes. GitOps (Argo CD, Flux) and Atlantis avoid this only when nobody applies directly, which agents iterating in dev and staging routinely do.
Sn: Provenance-checked applies. The apply wrapper stamps every target it changes with session id and source commit (Kubernetes annotation, Helm release description, a sidecar object beside the Terraform state). Before any apply it reads the live stamp; if that commit is not an ancestor of the local HEAD, the apply is refused: "staging/payments last applied by session X from branch foo at abc123; merge it, wait for its merge, or ask for an override." The agent can then fetch and merge that commit itself. Uncommitted trees cannot apply. Overrides are logged and re-stamp the target.
Check: Run paired parallel sessions on shared staging with overlapping tasks. Count silent reverts (an applied change missing from final live state) and time lost to blocked applies, versus worktrees plus state locking.
