# 25 對「沒有完美解」的問題提出新解：原模型 vs 直接做

2026-11-08。接 [24](24-open-problems.md)。題目是 24 裡核心缺口還在的 9 類問題。使用者指示「讓 AI 自己判斷」評估方式，以下由 AI 決定。

## 為什麼這樣評

這些問題現在沒有好的解法，所以沒有標準答案可以對。三種評法（做出來試、對照使用者的需求、等未來驗證）裡，選「對照使用者的需求」當主要評法，因為它可以馬上做。並用三件事降低 AI 判斷的偏差：

1. **評分清單在作答前寫好**：由另一個 agent 只根據問題描述和 24 查到的現有工具缺點，逐題寫出需求清單（R1 是核心痛點，其餘各對應一個已知缺點）。作答者看不到清單。
2. **盲評、兩位評審**：解法打亂、拿掉組別，Opus 和 Sonnet 各評一次。
3. **登記所有解法和日期**：之後可以再查有沒有人做出來、是否被採用（等未來驗證）。

## 設計（作答前登記，之後不改）

- **題目**：24 的 A 層 9 類（F01、F11、F08、F15、F16、F17、F18、F19、F27），整理在 [25-data/problems.md](25-data/problems.md)，包含問題、反應數、現有做法和已知缺點。作答者和評審都看得到。
- **評分清單**：[25-data/judge/checklists.md](25-data/judge/checklists.md)，只給評審。
- **組別**：A 直接做、C 原模型（和 21、23 同一份英文版），各 3 次，每次是一個獨立的 agent。
- **作答規則**：只准讀題目檔、最後寫一次答案；不准上網；只交結果，不寫思考過程。每題交一個解法（不超過 150 字），加上「和現有做法的差別」與「需要什麼」。

**評分**（每個解法）：

| 項目 | 怎麼算 |
|---|---|
| 需求滿足度（主要） | 清單每項：滿足 1、部分 0.5、沒有 0，取平均（0–1） |
| 核心 R1 | 單獨記錄 |
| 是否只是現有做法 | 和題目列出的某個現有做法本質相同就記「是」 |
| 可行性 | 第三方今天做得出來：是／部分（有些要原廠改）／否 |

**主要指標**：各組 27 個解法的平均需求滿足度（兩位評審平均）。

**判定**：C 比 A 高至少 0.10，才算原模型有幫助；差距小於 0.10，記為看不出差別。

**花費**：記錄每次作答的時間和 token。

## 限制（事先承認）

- 清單和評分都是 AI 做的；清單只根據 issue 摘要和查到的缺點，可能漏掉使用者真正在意的事。
- 滿足清單不代表做得出來、做出來有用。這次不做實作測試。
- 每組 3 次、9 題，差距小的時候看不出來。

## 結果

6 次作答全部完成，54 個解法都評完。評分在 [25-data/judge/](25-data/judge/)，組別對照在 `key.json`。

| | A 直接做 | C 原模型 |
|---|---|---|
| **需求滿足度（主要）** | **0.86** | **0.82** |
| 核心 R1 | 0.91 | 0.94 |
| 本質上就是現有做法 | 17% | 22% |
| 可行性 | 0.97 | 0.96 |
| 每次作答時間 | 平均 5.9 分鐘 | 平均 7.0 分鐘 |
| 每次 token | 平均約 10.1 萬 | 平均約 10.8 萬 |

- **判定：看不出差別。** C 比 A 低 0.04，沒有達到「C 高 0.10」的門檻。兩位評審都給 A 較高分（Opus：0.83 對 0.80；Sonnet：0.89 對 0.83）。
- 兩位評審對同一個解法的分數平均只差 0.06。
- 同組 3 次之間差 0.01–0.03，比兩組之間的差距小。
- 兩組都接近天花板：寫在紙上的解法，大多能滿足清單上 8 成以上的需求。
- 原模型多花約 19% 時間、約 7% token。

### 每題最高分的解法（登記日期 2026-11-08，供之後查證）

| 題 | 問題 | 最高分解法 | 組 | 分數 |
|---|---|---|---|---|
| P1 | 帳號 email 外流 | 本機閘道與對外代理：把送給模型和送出去的請求裡的 email 換成代號 | C | 1.00 |
| P2 | 權限行為和設定不符 | 一份跨工具的權限政策，編譯成各家的設定，並附上自動測試檢查實際行為 | A | 0.79 |
| P3 | 從 GitHub 以外的平台委派 | 用組織自己的 CI runner 執行，各平台的 pipeline 範本加上中繼 | C | 0.92 |
| P4 | 不知道 agent 何時結束或需要人 | 不靠 hook，從各家的對話紀錄推斷每個 session 的狀態並逐級通知 | A | 0.83 |
| P5 | 用 shell 指令改檔繞過內建工具 | 看實際改了什麼而不是猜指令：執行前後對工作目錄做快照比對 | C | 0.88 |
| P6 | 雲端 session 的憑證 | 團隊自架的憑證中介，session 用一把中介權杖換取短效憑證 | A | 0.96 |
| P7 | 跨 repo 的變更沒有協調 | 把各 repo 的 PR 綁成一個可一起審查、一起合併的變更組 | A | 0.80 |
| P8 | 卡在用量上限 | 從紀錄偵測用量上限，記下 session 與重置時間，到時自動喚醒續跑 | C | 0.96 |
| P9 | 沒辦法排隊下一個任務 | 佇列檔加 Stop hook 依序派發，每項可附驗證指令與相依 | A | 0.92 |

P3、P8、P9 的最高分解法，有一位評審認為本質上就是現有做法。

## 21、23、25 合起來

| 實驗 | 任務 | 原模型 vs 直接做 |
|---|---|---|
| 21 | 給問題找解法；給情境找問題 | 沒差別 |
| 23 | 從社群資料找問題和新解法 | 沒差別（兩組合格新解都是 0） |
| 25 | 對沒有完美解的問題提出新解 | 沒差別（直接做略高 0.04） |

四種設定、三種評法，原模型都沒有贏過直接做，而且每次多花 19–25% 時間。在公開資料、單次作答的情況下，目前的證據是：**原模型的步驟沒有帶來可量測的幫助**。

還沒測過的只剩兩種：用使用者自己的紀錄當在地資料；以及把解法實際做出來測試，這次只評了紙上的描述。
