## P1：Agent harness leaks the engineer's personal identity

問題：Engineers who let the agent search or fetch from the web find that the harness puts their account email into outbound request headers sent to arbitrary sites, and also injects it into the model's system prompt every session, without asking. Their identity reaches third parties they never chose (one reporter ties it to daily scam mail), so delegating web research quietly costs privacy.

### S1
Solution: Identity Egress Firewall — a local MITM proxy (mitmproxy addon) through which all agent traffic must pass. On model-API requests it replaces the account email and user-listed identifiers in the request body with a placeholder (`user@redacted.invalid`), so the model, sub-agents and the scripts they write never learn the real address. On all other egress it decodes headers, URLs and bodies and searches for the identifiers in any form (case-folded, percent/JSON/quoted-printable escaped, base64 at three offsets, hex, plus-addressed), rewrites hits in headers to the placeholder, blocks bodies with an explained deny, and logs each event. OS rules force every agent process through it (nftables uid-owner rule for a dedicated agent user on Linux; the agent sandbox's custom-proxy port elsewhere), so loopback calls and file writes are never inspected. A commit-msg/pre-push hook applies the same matcher to git.
Differs from existing: It acts on bytes on the wire, not tool-call text, so scripts Claude writes, sub-agents and encoded forms are caught; only real network egress is inspected, ending local false positives; the context scrub works at the network layer, so Team/Enterprise mod restrictions do not apply.
Needs: Local CA trusted by Node/tools (NODE_EXTRA_CA_CERTS); admin approval on managed machines; vendor tolerance of API-body rewriting. Vendor: dropping the email from context is the real fix.

### S2
Solution: Identity-scrubbing egress proxy — A local TLS-intercepting proxy (mitmproxy addon) that the harness and every child process use via HTTPS_PROXY plus a local CA (NODE_EXTRA_CA_CERTS, SSL_CERT_FILE); a network namespace or firewall rule allows egress only through the proxy, so agent-written scripts that ignore proxy variables cannot bypass it. Two rules: (1) on requests to the model API, replace the account email in the system prompt with a fixed pseudonym, so the model never learns the address and cannot place it in headers, scripts or commits; (2) on all other egress, match the user's known identity strings (email, name, git email) in URL, headers and body across precomputed encodings (URL, base64, hex, JSON-escaped, case variants), then rewrite or block and log. Decisions use the real destination; loopback is never proxied. A leak test suite (curl User-Agent, Python script, subagent, base64 query) reports leaks and false blocks.
Differs from existing: Hooks and the built-in mod read tool-call text: they miss scripts, encodings and subagents, and guess "network" from words, causing false denials. The no-email mod needs context hooks that managed settings skip. This acts on bytes actually sent, including the model request; measured by leaks and false blocks.
Needs: Harness honouring HTTPS_PROXY and a custom CA (Claude Code does); OS egress lock; org policy allowing TLS interception. No vendor change; vendor removal of the email makes rule 1 unnecessary.

### S3
Solution: Identity egress firewall — a wrapper launches the agent with all egress forced through a local TLS-inspecting proxy (HTTPS_PROXY plus NODE_EXTRA_CA_CERTS/SSL_CERT_FILE/REQUESTS_CA_BUNDLE for every child process; a Linux netns/nftables rule or the agent sandbox's proxy setting on macOS), so subagents and scripts Claude writes and runs cannot bypass it. At start it reads the signed-in email from the harness config and precomputes variants: case, percent-encoding, JSON escapes, base64, hex, split local part. Requests to loopback and the vendor API pass untouched; for all other hosts, headers and bodies are scanned and matches are replaced with a user-chosen alias (e.g. a forwarding address, so contact-required sites like sec.gov still work) and logged, never denied. Optionally it strips the injected email block from the system prompt on the vendor-API leg. A commit-msg hook rejects the address in commits.
Differs from existing: It inspects bytes on the wire, not tool-call text, so self-written scripts, subagent curl and encoded forms are caught; it is destination-aware, so heredocs and 127.0.0.1 calls are never blocked; it substitutes instead of denying; it works on managed logins. Measure: misses and false blocks on a leak corpus.
Needs: A local CA trusted by child tools (certificate-pinning clients fail closed); OS egress forcing. Prompt stripping only if org settings allow proxying the API. Vendor: supported opt-out of email injection.

## P2：Permission behaviour does not match what the engineer configured

問題：Engineers who have decided what the agent may do find the permission system does not follow that decision: allow and deny rules match unreliably, compound commands prompt on the harmless `cd`, ordinary quoted flags trigger new warnings, skills and subagents ignore user-level allow rules, skip-permissions or yolo modes still prompt, every new project needs its own trust approval, and workspace policy files silently do not take effect. Unattended runs stall on prompts, and engineers cannot be sure the rules they wrote are the ones enforced, so some reimplement enforcement in their own hooks.

### S1
Solution: Permission conformance suite driven by a scripted model — Write the policy once, as intents with example commands (allow read-only git anywhere, including git -C; allow cd inside the workspace; deny network writes). A local mock of the model API (ANTHROPIC_BASE_URL for Claude Code, a custom model provider for Codex, the equivalent where Gemini CLI allows) replays scripted tool calls for every example, including compound, quoted-flag, subagent and skill cases, in a headless run on a throwaway repo. The harness's real decision is read from the tool_result and permission denials the mock receives next, and compared with the intent. Output: a divergence table per harness, version and permission mode. CI runs it on every harness release and rule change; version pinning rolls out only releases that pass; divergent cases get generated PreToolUse/PermissionRequest hook rules, and cases hooks cannot override (ExitPlanMode, Remote Control prompts) become upstream bug reports.
Differs from existing: Dippy-style hooks re-implement matching without showing what the harness actually enforces; built-in rules and auto mode offer no test. This measures intended-versus-enforced mismatches deterministically per harness, version and mode, catches regressions before rollout, and limits custom hooks to measured gaps.
Needs: Harness model-endpoint override and headless mode (Claude Code, Codex; Gemini to verify); version pinning. Vendor: fixes for prompts hooks cannot override (ExitPlanMode, Remote Control).

### S2
Solution: Permission conformance tests — engineers write expected outcomes as a table: tool call, context (main agent, subagent, skill, plan exit), mode (default, auto, bypass) → allow, ask or deny. A runner starts the real installed CLI headless inside a throwaway container, pointed at a local mock model endpoint (ANTHROPIC_BASE_URL; a Codex custom model provider) that replays each case as a scripted tool call. Outcomes come from evidence: a recording --permission-prompt-tool marks ask, PATH shims record execution without side effects, denial text in the returned tool result marks deny. It runs in CI on every CLI version bump and settings change, blocks upgrades that regress, and emits a minimal PreToolUse hook covering only the failing cases, retired automatically once the native matcher passes. A transcript-mining mode lists real commands that prompted despite a matching allow rule and adds them as cases.
Differs from existing: Hook projects replace the matcher with another unreviewed parser; this checks the real enforcement point against the engineer's own expectations, catches regressions (cd prompts, bypass, subagent inheritance) before an unattended run, and keeps workarounds minimal and self-retiring. Measure: conformance rate per version; stalls per unattended run.
Needs: CLI support for a custom model endpoint and headless mode (Claude Code, Codex; Gemini CLI if overridable). No vendor change; a vendor dry-run 'explain decision' command would remove the mock.

### S3
Solution: permcheck — one policy, compiled per agent, and verified against the real agents. Engineers write a single policy (allow/ask/deny by tool, path and command semantics). A real shell parser (tree-sitter-bash) normalizes commands before matching: splits compounds and subshells, drops `cd` into the workspace, unwraps env prefixes, `sh -c`, `xargs` and `timeout`, and canonicalizes global flags (`git -C x commit` → `git commit`). The compiler emits each agent's native config (Claude settings.json, Codex rules plus `trust_level` entries for every repo under declared roots, Gemini policy TOML) and one enforcement hook installed at user and managed level, so subagents and skills get it too. `permcheck test` runs each installed agent headlessly in a throwaway container against a probe corpus (compounds, quoted flags, python -c, known bypasses) whose binaries are shims that only record calls, and reports intended versus actual allow/prompt/deny. It runs in CI and before every agent upgrade.
Differs from existing: Existing tools add yet another matcher with no proof it is applied; this measures what each agent version actually enforces, catching regressions (broken skip-permissions/yolo, ignored workspace policies, uninherited rules) before unattended runs stall, from one source of truth across Claude, Codex and Gemini.
Needs: Headless modes and hook APIs of each agent; a container runtime. Vendor fixes are still needed for defects it exposes, such as ExitPlanMode ignoring hook allows and mobile prompts.

## P3：Delegating work from forges and trackers other than GitHub

問題：Teams whose code and tickets live in GitLab, Bitbucket, Azure DevOps or Linear cannot hand work to an agent from where it lives: cloud agent sessions (Claude Code on the web, Codex web) connect only to GitHub repositories, and issues cannot be assigned to an agent to start a session. Engineers copy context by hand and manage branches and merge requests themselves, which blocks adoption in organizations that do not use GitHub.

### S1
Solution: Forge-native dispatch through the org's own CI runners — a small relay plus pipeline templates for Bitbucket Pipelines, Azure Pipelines, Jenkins (Bitbucket Data Center, Azure DevOps Server) and GitLab CI on any tier. Trigger: assigning a Jira, Linear or Azure Boards ticket to an 'agent' user, or '@agent' in an MR/PR comment. The relay (a webhook handler that can run inside the firewall) builds a task brief from the ticket (description, acceptance criteria, linked MRs, comments) and queues the pipeline through the forge API. The job runs the agent CLI headless (claude -p, codex exec) with repo-scoped CI credentials, pushes agent/<ticket-id>, opens the MR/PR natively, links it on the ticket, and stores the session transcript as an artifact; a later '@agent' review comment resumes that session on the same branch. Policies (allowed repos, budgets, max runtime) live in the relay.
Differs from existing: Needs no forge tier, feature flag, GitHub mirror or vendor integration: it reuses runners, credentials, on-prem network reach and audit trails the org already has, and one relay covers every forge-tracker pair. Unlike cyrus, no standing host. Measure: manual steps from ticket to MR (target zero); forges and trackers supported.
Needs: Runners with outbound access to the model API; an API key or CLI token as a protected CI variable; tracker webhooks or automation rules. No vendor change.

### S2
Solution: Forge bridge over proxy-injected credentials — A small webhook service listens to Linear agent assignments, Jira, Azure Boards, GitLab and Bitbucket mentions or assignments. On trigger it starts a vendor cloud session (e.g. claude --cloud) on a stub GitHub repo that holds only bridge config, no source. The environment stores a forge token as a network secret (basic auth) for the forge host, so the session clones the real repo from GitLab, Bitbucket or Azure DevOps over HTTPS and pushes back without the token entering the VM. A forge-neutral CLI in the stub repo (branch, push, open MR/PR, comment, link ticket) wraps each forge's REST API. The agent opens the MR on the origin forge and posts the link to the ticket; a review comment addressed to the agent starts a follow-up session on that branch with the comments as prompt. Self-hosted environments use the runner's own forge credential instead.
Differs from existing: Native integrations wait on vendors per forge, are beta or Premium-gated, and skip Bitbucket Data Center and Azure DevOps Server; cyrus needs self-hosted compute. This reuses the GitHub-only cloud session, keeps source off GitHub and works with any HTTPS git forge. Measured: manual steps from ticket to MR.
Needs: Claude Code network secrets on the plan (Team gap is vendor-side); forge reachable from vendor cloud (otherwise a self-hosted environment); CLI session launch accepting a stub repo.

### S3
Solution: Forge Shadow Bridge — a service that gives GitHub-only agents a private GitHub mirror of each GitLab, Bitbucket (Cloud or Data Center) or Azure DevOps repo, keeping the origin authoritative. Origin push webhooks mirror branches into a locked-down GitHub org where only agent branch prefixes (`claude/*`, `codex/*`) are writable. When an agent opens a mirror PR (Claude Code on the web, Codex cloud, Linear coding sessions, Claude Agent for Jira), the bridge pushes the branch to origin, opens the matching MR with ticket links and turns the mirror PR into a pointer. Review comments on the origin MR are relayed to the mirror PR as `@claude`/`@codex` mentions, which the vendors' GitHub integrations act on, and new commits flow back. Assigning a Jira, Linear or Azure Boards ticket to an "agent" user makes the bridge start a cloud session on the mirror with the ticket text via the vendor CLI.
Differs from existing: Instead of waiting for each vendor to support each forge, one bridge makes every GitHub-only agent work with any forge, including Bitbucket Data Center and Azure DevOps Server, without GitLab Premium gating, feature flags or per-vendor beta integrations.
Needs: A private GitHub org and approval to mirror code there (data residency if required); forge webhooks and API tokens; vendor cloud-session CLIs. No vendor change.

## P4：Not knowing when a long-running agent finishes or needs input

問題：Engineers who hand an agent a long task switch to other work, but get no noticeable signal when it finishes or waits for input, and the conversation shows no timestamps to tell when a background check last ran or an instruction was given. They either watch the terminal or lose time to an agent sitting idle.

### S1
Solution: Transcript-watching attention daemon — A small daemon on the machine where the agent runs (including Remote SSH hosts) tails the timestamped session transcripts that Claude Code, Codex and Gemini CLI already write, and checks process liveness. It derives state from evidence instead of trusting hooks: working, awaiting approval, asked a question, finished, API error, stalled (process alive, no writes for a configurable N minutes), exited. It notifies only on state transitions, debounced (a "finished" followed within seconds by an automatic /goal continuation is suppressed), and escalates: desktop toast and sound first, then phone via ntfy if unacknowledged after M minutes. Silence is itself a signal, so an unhooked error or a hook broken by an update still yields a "stalled" alert. A status-line script (it receives transcript_path) shows state, time of the last instruction and time since last activity, giving timestamps in the terminal view.
Differs from existing: Hook-based notifiers depend on events the harness emits, so API errors, hooks broken by updates, missing approval events, ~10-second delays and false /goal "done" alerts go unseen or wrong. This infers state independently. Measured: missed alerts, false alerts and alert latency on recorded sessions.
Needs: Transcript formats (undocumented; per-version adapters); ntfy or OS notifications. Vendor: timestamps inside the conversation view itself.

### S2
Solution: Liveness watcher — a daemon on the machine where the agent actually runs (including the Remote SSH host) that tails the transcript files the CLIs already write (~/.claude/projects/*.jsonl, ~/.codex/sessions/) and samples the agent's process tree. A state machine derives: working; waiting for approval (tool call outstanding, no child process, CPU idle); finished (final assistant message, nothing outstanding, idle for a debounce window, so /goal continuations don't alert); errored (error record, or no progress for N minutes while alive); exited. Each transition is pushed to ntfy, Slack or Pushover and re-sent with escalation until acknowledged; hook events, when they do arrive, only sharpen timing. `pulse log` prints a timestamped timeline of instructions, tool runs and background checks from the transcripts, and `pulse` in a second pane shows it live.
Differs from existing: Hook-based notifiers stay silent whenever the harness fails to fire; this alerts on absence of progress, covering API-error endings, hooks broken by updates, unreported Codex approvals and Remote SSH, and gives timestamps without patching any UI. Measure: missed-idle rate and alert latency on injected failures.
Needs: Read access to local transcript files (undocumented formats; parsers must track CLI versions) and a push service. No vendor change; a documented event stream would help.

### S3
Solution: Agent State Watcher — a daemon that infers each session's state from evidence that does not depend on hooks, then alerts with escalation. Inputs: the transcripts every surface writes (Claude Code `~/.claude/projects/**/*.jsonl`, Codex `~/.codex/sessions` rollouts) and the agent's process tree. Rules: turn closed with no continuation within a debounce window → done (filters /goal continuations); error record or process exit mid-turn → failed; pending tool call with no child process and no transcript growth for N seconds → needs approval; no growth for M minutes while working → stalled. Thresholds are configurable; alerts are deduplicated. Delivery escalates with input-idle time: terminal bell or OS toast first, phone push via ntfy if unacknowledged after X minutes. For Remote SSH it runs on the remote host. The same data powers `agentlog`, a timeline with wall-clock timestamps for every message, tool call and background check.
Differs from existing: Reading state instead of waiting for hooks, it catches API-error endings and Codex approval waits, survives hooks breaking or lagging after updates, ignores /goal pseudo-completions, works alike in CLI, IDE and SSH, and adds timestamps without patching webviews.
Needs: Read access to local transcripts in undocumented formats (versioned parsers); a push service such as ntfy. Timestamps inside the vendor's own chat UI need the vendor.

## P5：File work done through raw shell commands

問題：Agents increasingly read, write and edit files with sed, cat and grep through the shell instead of the dedicated file tools, more so in auto mode. Those changes bypass the file-level permission rules, diff display and edit tracking engineers use to supervise the agent.

### S1
Solution: Effect-based shell file guard — instead of guessing intent from command text, it checks what each Bash call actually changed. A PreToolUse hook snapshots the working tree into a shadow git repository (git's stat cache keeps this fast) and a filesystem watcher (inotify/FSEvents) records writes, including to git-ignored paths. A PostToolUse hook diffs the result and applies the existing Edit/Write rules to every changed path: out-of-policy changes are restored from the snapshot and the model is told which rule applied. Allowed changes are shown as a unified diff, recorded as a checkpoint so `guard rewind` can undo Bash edits, and, when a path falls under a nested CLAUDE.md or path-scoped rule, that rule's text is injected as additionalContext. Read protection stays with the OS sandbox.
Differs from existing: Pattern hooks miss python, perl and heredoc routes and fight the harness's Bash-first steering, wasting denied turns; this lets any route run, enforces on effects, and restores path rules, diffs, rewind and nested rules for Bash edits. Measure: detected writes across a route corpus; denied-retry turns.
Needs: PreToolUse/PostToolUse hooks with model feedback, local git, inotify/FSEvents. Post-hoc: keep the sandbox for hard write boundaries. Vendor (optional): a setting separating auto-approval from Bash-first routing.

### S2
Solution: Effect-based Bash file guard — hooks that judge what a shell command changed, not how it was spelled. PreToolUse on Bash snapshots the workspace into a private git index (`GIT_INDEX_FILE=.git/agent-idx git add -A; git write-tree`, plus an mtime scan for ignored paths); PostToolUse snapshots again and diffs the trees. For each changed file it checks Edit/Write permission rules and path-scoped policies, restores denied files from the pre-snapshot and tells the model to use Edit; shows the diff to the engineer via systemMessage; returns the nested CLAUDE.md and path rules for touched directories as additionalContext; and keeps every pre-snapshot as commits under `refs/agent-checkpoints` so `agent-undo` can revert any Bash edit. Read deny rules and out-of-workspace writes are enforced for Bash by an OS sandbox profile (bubblewrap/Seatbelt) generated from the same rules. A SessionStart note asks the model to prefer Edit, but nothing relies on it.
Differs from existing: Pattern blockers miss python, heredocs and new tools and fight the harness's Bash-first prompt; this catches every write route by its effect and restores diffs, path rules and undo for Bash edits instead of only refusing them.
Needs: A git workspace; PreToolUse/PostToolUse hooks with additionalContext; an OS sandbox for reads. Native /rewind tracking and dropping Bash-first steering need the vendor.

### S3
Solution: Effect-based Bash file guard — A PreToolUse(Bash) hook snapshots the workspace into a shadow git repository (separate GIT_DIR and index, honouring .gitignore, stat-cached so it stays fast); a PostToolUse(Bash) hook snapshots again and diffs. Every file the command actually changed, whether by sed, heredoc, python, make or a script, is then handled like an Edit: (1) checked against Edit/Write deny and path rules, with violating paths restored from the snapshot and the reason fed back to the model; (2) passed to the user's Write/Edit hooks (formatters, linters) as synthesized payloads; (3) shown as a diff, with the touched directories' nested CLAUDE.md and path-scoped rules returned as additionalContext; (4) kept as a per-call restore point (bash-rewind <call>). Reads stay with the OS sandbox's read denies, and sandbox write denies hard-protect secret and config paths.
Differs from existing: Pattern hooks and deny rules read command text, which python, heredocs or scripts route around; blocking also fights the harness's Bash-first steering. This detects changes by filesystem effect, so the route does not matter, and adds restore points. Measured: share of write routes (e.g. rulestack's 11) checked, diffed and restorable.
Needs: Workspace under git (or a snapshot-able tree); PreToolUse/PostToolUse hooks; OS sandbox for reads. Vendor: folding restore points into /rewind.

## P6：No safe way to give cloud sessions credentials

問題：Engineers running async agent sessions in the vendor's cloud have no secure way to provide API keys and other credentials; the environment settings field itself warns against putting secrets there. Tasks that need authenticated access either cannot run in the cloud or force engineers to expose secrets.

### S1
Solution: One-key credential broker — the team runs a small HTTPS broker in its own cloud account under that account's workload identity, so no long-lived cloud keys exist. The cloud environment stores exactly one network secret: a bearer token for broker.example.com, which the vendor proxy attaches after traffic leaves the VM, so the session holds no secret. The broker provides: SigV4 re-signing (e.g. aws-sigv4-proxy) for AWS and any S3-compatible host such as R2; a private npm/PyPI proxy (Verdaccio, devpi), installed from in-session via a SessionStart hook instead of the setup script; database access through an HTTPS SQL endpoint or WebSocket tunnel to PgBouncer, which holds the password, so the VM connects to localhost without credentials; and header injection for any other API. Scopes, audit logs and revocation live in the broker and change mid-session without reload.
Differs from existing: Network secrets alone serve only header-auth HTTP APIs and only amazonaws SigV4; the broker turns that one header into registry, database, R2 and cloud access with keys still outside the VM, plus live rotation. postern and mcp-warden are local-only. Measure: credential types usable with zero secret bytes in the VM.
Needs: Network secrets on the account (Team rollout and CMEK orgs are vendor gaps); a broker reachable from vendor egress, ideally IP-allowlisted. Vendor (optional): OIDC tokens would replace the bearer.

### S2
Solution: Credential broker chained behind the network-secret proxy — Store one network secret: a bearer token for a broker you host, with the broker host on the allowlist. The vendor proxy attaches it after requests leave the VM, so the session reaches the broker without holding a long-lived key. The broker then (1) forwards and signs requests the vendor proxy cannot (SigV4 for R2 or MinIO, HMAC-signed APIs); (2) serves as a pull-through for private packages on public registries (point .npmrc or the pip index at broker paths); (3) issues short-lived, scoped credentials for non-HTTP uses: Vault dynamic database users, SSH certificates, and AWS/GCP/Azure session credentials in place of the missing OIDC token, with minute-level TTLs, per-environment policy and a log keyed to session ID. Private installs move from the setup script to a SessionStart hook, where requests get secrets. Rotation happens in the broker, so running sessions need no reload.
Differs from existing: Network secrets cover only HTTP headers to listed hosts: not registries, setup scripts, R2, databases or keyless cloud auth; postern and mcp-warden are local-only. This puts a self-hosted broker behind the one credential the vendor can inject. Measured: credential types usable with zero long-lived secrets in env, files or transcripts.
Needs: Network secrets (Team availability and CMEK support need the vendor); a hosted broker plus Vault/STS; short-lived credentials still enter the VM, bounded by TTL and scope.

### S3
Solution: Attested credential broker — a customer-run service (container or Cloudflare Worker) holding all real secrets; cloud sessions authenticate only to it, using one network secret scoped to the broker host or, where those are unavailable (Team, CMEK), GitHub attestation: the session pushes a nonce ref through the vendor's GitHub proxy to a designated repo, and the broker verifies pusher and repo before issuing a 15-minute token bound to that repo. The broker reverse-proxies HTTP with any auth scheme (SigV4 for R2 and other S3-compatible hosts, private registries); acts as an OIDC issuer AWS, GCP and Azure trust, so sessions exchange tokens for short-lived cloud roles; tunnels Postgres, MySQL and SSH over WebSocket, injecting credentials server-side; and enforces per-repo policy with audit logs. Secrets rotate at the broker, reaching running sessions immediately. Dependency installs move from setup scripts to a SessionStart hook.
Differs from existing: Covers what network secrets cannot: non-HTTP protocols, non-AWS SigV4, keyless cloud federation, Team and CMEK orgs, mid-session changes. Unlike postern or mcp-warden it is reachable from vendor clouds and needs no engineer machine online.
Needs: Session egress to the broker host; vendor GitHub proxy allowing pushes; WebSocket support through the agent proxy (unverified). Credentials for setup scripts themselves would require the vendor.

## P7：Cross-repository work in one session

問題：Organizations with multi-repository architectures cannot use cloud or app agent sessions for cross-service changes, because a session assumes one repository, one branch and one pull request. Changes that span services, such as shared types or API contracts, must be split by hand into separate sessions and coordinated manually.

### S1
Solution: Agent-written changeset manifest with combined CI and ordered merge — A skill makes the agent write a manifest whenever it opens PRs across repos: changeset ID, PR list, dependency edges (shared types → API → clients), merge order, and each repo's link step (go.mod replace, npm override, pip -e). The manifest is embedded in every PR body. A reusable GitHub Actions/GitLab CI template reads it, checks out sibling PRs at their head SHAs, links them and tests the combined state, posting a required status "changeset N/M green". A small GitHub App holds downstream PRs until upstream ones merge, merges in topological order once all are approved and green, re-tests downstream against the new main, and opens revert PRs if a later merge fails. A PreToolUse hook enforces per-repo push policy (PR-only, branch prefix, read-only) during the session.
Differs from existing: Multi-repo sessions and Projects produce unlinked PRs, each tested against the others' main branch; Zuul or Gerrit topics need heavy infrastructure and hand-written dependencies. The agent already knows the dependency graph, so the manifest is free. Measured: changesets tested combined before merge; broken-main incidents.
Needs: CI token that reads sibling repos; GitHub App with merge rights; branch protection. Vendor: showing the changeset as one unit in the session UI, and multi-repo teleport.

### S2
Solution: Change-set gate — a session Stop hook (or skill) that, once a session has opened PRs in several repositories, writes a manifest: change-set ID, member PRs, merge order derived from dependency files (if repo B's package.json, go.mod or pyproject references repo A's package, A merges first) and the contracts touched. It stamps 'Change-Set: <id>' and 'Depends-On: org/repo#n' into each PR body and opens one tracking issue linking all diffs. A reusable GitHub Action in each repo then (1) builds and tests against sibling PR heads via npm overrides, go replace or pip git URLs, so contract breaks fail before merge, and (2) provides a required 'changeset-order' check that stays pending until predecessors merge and resets if a sibling changes after approval. A per-repo .agent-policy.yml (draft-only, no push to protected branches, forbidden paths) is enforced by a PreToolUse hook on git push and gh pr create.
Differs from existing: Multi-repo sessions today emit independent PRs, and Zuul-style Depends-On gating needs its own CI infrastructure. This uses plain GitHub Actions plus the session's own knowledge of what it changed to add linked PRs, enforced merge order, cross-repo tests and per-repo push policy. Measure: broken-main incidents from out-of-order merges.
Needs: GitHub Actions and branch protection; per-ecosystem override recipes; hooks running in the cloud session (repo settings). Vendor: multi-repo teleport and a native change-set view.

### S3
Solution: Change-set coordinator — a GitHub/GitLab app plus CLI that turns per-repo PRs into one reviewable, mergeable unit. Any agent (multi-repo web session, Codex multi-folder, local) uses one branch name or PR label `cs/<id>` across repos and commits a `changeset.yaml` (repos, dependency order, contract notes). The app finds every PR in the set, posts a shared status comment and a combined diff page, and runs a joint CI job that checks out all branches together and builds downstream repos against upstream branches via workspace overrides (pnpm overrides, go.work, Cargo [patch], Maven snapshots). A required `changeset` check blocks partial merges; on approval it merges as an ordered train, bumping downstream pins to the released upstream versions and pausing if a step fails. Per-repo `.agent-policy` files compile into branch rulesets (writable prefixes, protected paths). `cs checkout <id>` rebuilds the set as local worktrees: multi-repo teleport through git.
Differs from existing: Existing tools produce independent PRs or coordinate sessions; none tests the set together or enforces merge order. This adds atomic review, joint CI, ordered merges, per-repo push policy and git-based teleport, regardless of which agent produced the branches.
Needs: App permissions to read, check and merge PRs; CI able to clone several repos; package-manager overrides. No vendor change; showing change sets inside agent UIs would need vendors.

## P8：Unattended work stops at usage limits

問題：When a long delegated task hits the 5-hour or weekly usage limit, the agent stops even though the reset time is known. If the reset falls overnight, the work waits until the engineer returns, finds the session and re-issues the prompt.

### S1
Solution: Durable limit-aware job runner — Tasks run as jobs under the OS scheduler (systemd user units, launchd, Task Scheduler), not in a terminal. Each job record holds session ID, directory, goal and a job-scoped permission profile. The runner launches claude -p or codex exec with JSON output; on a limit it takes the reset time from machine-readable data (the result event, or rate-limit response headers via a local pass-through proxy), falling back to cheap probe calls, never screen text. It sets a wake timer, even for weekly resets beyond 24h and for a sleeping laptop, then resumes with --resume <id> or codex exec resume and a fixed prompt: check git status and your todo list, then continue. Unlisted actions are denied and logged instead of prompting, so resumed jobs never stall; denials and completion trigger a notification. Optional per-job policy: wait, or continue on an API key up to $X.
Differs from existing: Built-in auto-continue needs a live interactive terminal, skips -p, background, >24h resets and Remote Control, and still stalls on prompts; wrappers scrape changing output and fail when already limited. Measured: share of limit stops resumed within five minutes of reset with no human action.
Needs: Headless resume by session ID (Claude Code, codex exec resume); OS scheduler with wake support. Vendor: a documented reset-time field would remove proxy and probing.

### S2
Solution: Durable resume scheduler — a wrapper runs each unattended task as a job record (session ID, cwd, goal, permission profile), launching the agent headless with stream-json output. A limit is recognized from the structured result/error event, or, if already over limit at launch, from a probe call, never from TUI text. On a limit it computes the reset (5-hour or weekly, any distance), commits a WIP checkpoint and registers an OS wake job: pmset/launchd on macOS, a systemd timer with WakeSystem=true on Linux, Task Scheduler 'wake to run' on Windows. At reset plus two minutes the machine wakes, holds caffeinate/systemd-inhibit, and runs `claude --resume <id> -p continue` or `codex exec resume <id>` under a pre-approved allow-list; other permission requests go to a prompt tool that denies with a reason and notifies instead of stalling. If resume fails, a fresh session starts from the goal, WIP diff and last transcript turns.
Differs from existing: Built-in auto-continue needs a live, awake interactive process; claude-auto-resume parses display text. This survives closed terminals, sleep and reboots, covers -p, background and weekly resets, and never stalls on prompts. Measure: share of limit stops resumed within five minutes of reset, unattended.
Needs: OS wake timers (laptop on power; lid-closed wake varies by hardware), headless resume by session ID. Vendor (optional): a reset timestamp in structured output would remove the probe.

### S3
Solution: Resume scheduler — make resumption a scheduled job instead of a waiting process. Delegated tasks run headless under a supervisor (`claude -p --output-format stream-json`, `codex exec --json`) that records session id, cwd and goal and instructs the agent to keep `progress.md` current. When a run ends on a limit, the supervisor reads the structured error and its reset time, never the human message; if no reset time is available it schedules cheap probe runs. It then registers an OS timer with wake-from-sleep (systemd WakeSystem timer; launchd plus `pmset schedule wake`) for any horizon, weekly included, which runs `claude -p --resume <id>` or `codex exec resume <id>` with "Limit reset; continue from progress.md". Resumed runs use a pre-approved permission profile plus a deny-and-explain hook, so nothing stalls on a prompt; model-specific limits switch to a configured fallback model. Optional: continue on a spend-capped API key near a deadline.
Differs from existing: Nothing waits in-process, so sleep, closed terminals and Remote Control do not matter; it covers -p, background and weekly resets, starts when already over the limit, survives message-format changes, and resumed work does not stall on permission prompts.
Needs: Headless resume (exists in Claude Code and Codex); OS scheduler with wake. A documented machine-readable reset time in headless output would make scheduling exact (vendor).

## P9：No way to line up the next tasks

問題：Engineers who already know the next several things the agent should do cannot queue them: they must wait for each task to finish before giving the next, and in the VS Code extension a new message interrupts the running task instead of waiting its turn. Delegation stays turn by turn, and the engineer has to stay present between tasks.

### S1
Solution: Gated task queue in a repo file — Next tasks live in .agent/queue.md, an ordered checklist editable and reorderable from any editor and kept in version control, so no chat input box can interrupt or drop them. Items may carry done-when: (a command such as npm test) and fresh: true. A Stop hook acts at turn end. Injected tasks ask the agent to end with a sentinel line, DONE or NEEDS-INPUT: <question>; on NEEDS-INPUT or a pending question the hook holds the queue and notifies. On DONE it runs the done-when check: on failure it feeds the output back (up to N retries, then holds); on pass it ticks the item with time and commit SHA and injects the next item as a new instruction, or, for fresh items, starts a new session for clean context. Typing in chat stays steering; the file holds only next tasks.
Differs from existing: Built-in queues fold messages into the running turn, merge, interrupt or lose them; claudeq-style FIFOs push the next task even when the last one failed or the agent asked a question. This gates each dequeue on a verified result. Measured: tasks finished per unattended hour; wrong dequeues.
Needs: Stop hooks (Claude Code; Codex hooks); a session launcher for fresh items. No vendor change; a native hold-until-turn-end mode would simplify it.

### S2
Solution: Queue file with a Stop-hook dispatcher — the queue is a plain markdown checklist in the workspace (.agent/queue.md) that the engineer edits in any editor (add, reorder, delete lines) or appends to with `q add "…"` from another terminal; nothing is typed into the chat while the agent works. When the agent is about to stop, a Stop hook checks hold conditions: the last message asks the user something, a permission was denied, the task's check command fails, or a PAUSE line is present. If none hold, it marks the current item done with the commit SHA, claims the next unchecked item and returns decision 'block' with that item as the reason, so the same session starts it as the next task with full context. One item is one task, strictly in order, never injected mid-turn. An empty queue ends normally and sends a notification.
Differs from existing: Because nothing enters the chat input mid-run, VS Code interrupts, mid-turn folding, merged turns and desktop message loss are avoided; unlike claudeq or cmux-claude-queue it needs no side pane or specific terminal, and the queue persists and is editable. Measure: queued tasks run as separate tasks, in order, none lost.
Needs: A Stop hook that can continue with a reason (Claude Code; Codex where supported), with a loop guard; hooks active in each surface used. Vendor (optional): native hold-until-turn-end queue.

### S3
Solution: Queue file with Stop-hook dispatcher. Tasks live in `.agent/queue.md`, one block each with optional `verify:` command, `after:` dependency and `fresh: true`, editable in any editor, via a CLI (`q add`) or a small VS Code panel. A Stop hook (Claude Code Stop, Codex Stop, Gemini AfterAgent) fires only when the turn has really ended; if it ended normally and tasks remain, the dispatcher runs the finished task's `verify:` command, optionally commits a checkpoint, then blocks the stop with the next task as the reason, so each queued task becomes the next instruction after the previous one is done. A failed check re-prompts once, then pauses the queue and notifies. `fresh` tasks run as separate headless sessions in a worktree for clean context. Input never passes through the chat box, so mid-turn folding, VS Code interruption and desktop message loss cannot occur.
Differs from existing: Built-in queues fold messages mid-turn, merge them or lose them; third-party queues are UI- or platform-bound and unverified. This is durable, agent- and surface-agnostic, strictly one task per completed turn, and gated on verified success.
Needs: Stop hooks with block-and-reason semantics (Claude Code, Codex, Gemini); the loop ends when the queue empties. A native hold-until-turn-end setting would need the vendor.
