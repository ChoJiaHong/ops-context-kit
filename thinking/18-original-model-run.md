# 18 用原模型重跑 17 的題目

同一個題目（[17](17-ai-work-gaps.md)），改用原模型（[00](00-original-notes.md) 三份筆記）跑，並加上今晚學到的三件事：現有解法實際查證、優勢要能量測、連續兩次空轉才停。步驟順序由 AI 決定，但四種情境差異、向下與向上兩個迴圈、優勢公式、適用範圍、硬湊檢驗、目標一致都要做到。查證日期 2026-11-07。

## 1. P0 當成假設（筆記三）

**使用者的 P0**：工程師大量使用 AI；現有的規則架構、提示詞、skill 有污染、有覆蓋不到的地方；找出並解決，讓 AI 工作方式更完善。

**目標**：Goal(P0) = 大量使用 AI 時，工作仍然正確、可靠，而且人的負擔不會跟著用量變大。

「污染與覆蓋缺口」是使用者對原因的猜測，只當假設。就像筆記三的 SRE 例子：「CPU 太高，幫我加機器」，真正的問題可能是 retry storm。

## 2. 抽象 A(P0) 與現有解法 E（筆記三）

**A(P0)**：一套持續累積、跨情境重複使用的指示與知識，被一個執行者在不同情境讀取並照做。要維持正確、相關、可信。這和軟體設定管理、文件漂移、組織 SOP 是同一類問題。

**現有解法 E**（14、15、17 已逐一查證）：

| 類別 | 現有解法 |
|---|---|
| 版本控制與審查 | CLAUDE.md 放進 git、出錯就加、定期刪 |
| 靜態檢查 | agents-lint、stalebrain（對照 repo 檢查過期）、記憶分析器 |
| 從使用紀錄挖掘 | `/insights`、misfire（排出被忽略的規則） |
| 測試與評估 | skill-creator 的 eval、agent-backtest（重播對話紀錄）、evolveguard |
| 對真實環境評估 | Monday 等公司對 staging 環境評估自家 agent；ITBench、AIOpsLab 在示範環境裡製造故障當題目 |
| 範圍與載入 | 階層式載入、path 規則、關鍵字注入 |
| 強制 | hooks |
| 記憶安全 | 出處標記、指定寫入者、寫入前檢查等原則 |

## 3. 現有解法的瓶頸 L(Se, P)（筆記二第 4 步）

在「大量使用」的條件下，現有解法共同的瓶頸：

| 瓶頸 | 說明 |
|---|---|
| **L1 人的審查量** | 幾乎每個現有解法最後都落在「人定期審查、核准」。用量大時，規則、記憶、教訓、session 的數量超過人能審的量，審查變成形式或被跳過，污染就累積 |
| **L2 真相的來源** | 靜態檢查對照 repo，評估用合成題目；infra 的真相在活的系統上 |
| **L3 回饋太慢** | 程式碼的指示錯了，測試會失敗；infra 的指示錯了，要等到出事才知道 |
| **L4 寫入者是否可信** | 記憶中毒；現有提示注入防禦涵蓋不到 |

**問題重新界定**：真正的問題不是「污染」本身，而是**用量大時，人審不完、錯誤要到出事才發現**。污染和覆蓋缺口是這兩個瓶頸的結果。

## 4. 情境差異 ΔContext，歸入四類（筆記三第 5–6 步）

拿使用者的情境（infra、多個平行 session、prod 權限、AI 會讀外部文字）和 A(P0) 比較：

| 類別 | 差異 |
|---|---|
| **新增限制** | 指令有不可逆的副作用，不能在 prod 自由重播；平行 session 多，量超過人能看的；外部文字一直流入 |
| **缺少的限制** | 現有解法假設有第二個審查者（團隊的 code review），重度使用 AI 的單人沒有；假設真相在 repo，infra 沒有 |
| **可用的資源** | (a) **stg 環境**：和 prod 對應、可以安全承受副作用；(b) **任務紀錄**：每份都有 goal、可觀察的 done-when、targets、mode（`workflow` 分支）；(c) **guard 的紀錄**：每一個 Bash 指令和它的分類、目標；(d) **TRUTH.md 的查詢指令**：每個事實都附唯讀查詢方法；(e) 對話紀錄（JSONL）；(f) 系統自己的稽核紀錄（rollout history、events） |
| **改變的假設** | 現有做法假設「人寫規則、AI 讀」；重度使用時，大部分規則和記憶是 AI 自己寫的（自動記憶、`/insights` 的建議、「把這個錯寫進 CLAUDE.md」） |

## 5. 向下迴圈：沿六個維度縮窄（筆記一、二）

| 層 | 縮窄維度 | 加入的條件 | 是否出現有優勢的新解 |
|---|---|---|---|
| P1 | 人 | 單人、重度使用、平行 session | L1 變成主要瓶頸；還沒有新解 |
| P2 | 行為 | AI 自己寫規則和記憶，也讀外部文字 | L4 出現；配上資源 (b)(c) → 新解 Sn-B、Sn-D |
| P3 | 在地資源 | 有 stg、任務紀錄、guard 紀錄、TRUTH 查詢指令 | 資源 (a)(b) 配 L3 → 新解 Sn-A；資源 (d) 配 L2 → 新解 Sn-C |
| P4 | 限制 | prod 不可逆 | 確認 Sn-A 必須在 stg 而不是 prod |
| P5 | 時間 | 事故中 vs 平時 | 沒有新解（第 1 次空轉） |
| P6 | 地點 | prod、stg、本機 | 已被 P3、P4 用到，沒有新解（第 2 次空轉，停止） |

## 6. Match(L, D) → Sn = Adapt(Se, L, D)（筆記二第 5–6 步）

### Sn-A：用 stg 測試 AI 的指令，題目來自自己的任務紀錄

- **Match**：L3（回饋太慢）× 資源 (a) stg + (b) 有 done-when 的任務紀錄。
- **Adapt 的對象**：agent-backtest 和 Monday 的 staging 評估。
- **新解**：把過去 target 在 stg（或有 stg 對應）的任務紀錄，轉成可重跑的情境；完成條件直接用 done-when。CLAUDE.md、skill、模型版本改變時，在 stg 重跑，比對 guard 紀錄裡的行為軌跡和 done-when 是否達成。
- **資源重新詮釋**（筆記三）：stg 從「應用程式上線前的測試環境」變成「AI 指令的測試場」；任務紀錄從「工作紀錄」變成「評估資料集」。這和阿里山的例子同一種動作：林業鐵路從交通工具變成移動式基地。
- **優勢**：
  - 對 agent-backtest：它重播的是紀錄下來的工具結果，行為一改變就無法往新的分支走；stg 會給出真實的系統回應。
  - 對 Monday 式評估：不用另外建資料集，題目每天由工作自動產生，而且自帶驗收條件。
  - 對 ITBench、AIOpsLab：測的是自己的環境、自己的指令，不是通用題目。

### Sn-B：附證據的教訓提案，減少人的審查量

- **Match**：L1（審查量）× 資源 (b) 任務紀錄 + (c) guard 紀錄 + 改變的假設（寫規則的是 AI）。
- **Adapt 的對象**：`/insights` 的規則建議、misfire 的排序。
- **新解**：AI 提出的每條規則或教訓，必須附上重現的證據（哪個任務、哪段 guard 紀錄、哪個修正），並先在 Sn-A 的 stg 測試裡證明「有它比沒它好」；人只審「通過測試、而且會影響 prod 行為」的那幾條。
- **優勢**：人的審查從「全部看」變成「只看通過測試的決策點」。

### Sn-C：infra 事實的即時查核

- **Match**：L2（真相的來源）× 資源 (d) 查詢指令。
- **Adapt 的對象**：stalebrain（對照 repo）。
- **新解**：定期執行 TRUTH.md 每個事實的唯讀查詢，和寫下的值不同就標記。（同 17 的 T1）

### Sn-D：讀過外部文字的 session，寫入要先隔離

- **Match**：L4（寫入者是否可信）× 資源 (b) 任務綁定（知道這個 session 讀過什麼）+ 改變的假設。
- **Adapt 的對象**：記憶安全的原則（出處、指定寫入者）。
- **新解**：讀過工單、日誌、訊息、網頁的 session，寫入記憶或規則檔時由 hook 轉到隔離區。（同 17 的 T2 的一部分）

## 7. 驗證目標一致（筆記三第 9 步）

四個新解都服務 Goal(P0)：大量使用時仍然正確可靠，而且人的負擔不跟著用量變大。Sn-A、Sn-B 直接處理「人審不完、錯誤出事才知道」。

## 8. 向上迴圈：逐步移除情境，找 P\*（筆記二第 7–9 步）

| 新解 | 移除的情境 | Advantage 還 > 0 嗎 | P\* |
|---|---|---|---|
| Sn-A | infra → 任何「agent 的動作會落到外部系統、而且有非 prod 副本」的工作（資料管線的 staging DB、SaaS 的 sandbox 租戶） | 是 | **agent 的動作會影響外部系統、有非 prod 副本、有附驗收條件的任務紀錄** |
| | 外部系統 → 純程式碼工作 | 否：測試本身就是環境，agent-backtest 加測試就夠 | |
| Sn-B | infra → 任何有動作紀錄的重度使用者 | 是 | **審查量是瓶頸的重度使用** |
| | 重度使用 → 輕度使用 | 否：人可以全部審 | |
| Sn-C | infra → 真相在 repo 以外、有唯讀查詢的領域（雲端帳號、SaaS 設定） | 是 | **有唯讀查詢可驗證的、存在活系統裡的事實** |
| Sn-D | 拿掉「會讀外部文字」 | 否 | **同時讀不可信文字、又會寫持久記憶的 agent** |

## 9. 硬湊檢驗（筆記一）

| 新解 | 拿掉在地差異後 | 結果 |
|---|---|---|
| Sn-A | 沒有 stg → 只能用假環境；沒有附 done-when 的任務紀錄 → 要另建資料集 | 優勢消失，**不是硬湊** |
| Sn-B | 沒有任務和 guard 紀錄 → 退回 `/insights` 那種沒有證據的建議 | 優勢消失，不是硬湊 |
| Sn-C | 沒有查詢指令 → 退回對照 repo | 優勢消失，不是硬湊 |
| Sn-D | 不知道 session 讀過什麼 → 退回原則 | 優勢消失，不是硬湊 |

## 10. 優勢怎麼量（效用 U 的定義）

| 新解 | U 的量法 | 比較對象 |
|---|---|---|
| Sn-A | 改變指令或模型後，在真實出錯前就抓到行為改變的比率；每次評估的建置成本 | agent-backtest、手建資料集 |
| Sn-B | 每條被接受的規則，人花的審查時間；被接受後證實有害的規則比率 | 直接採用 `/insights` 的建議 |
| Sn-C | 故意放入的過期事實被抓到的比率 | stalebrain |
| Sn-D | 持續性測試：讀過惡意工單的 session 嘗試寫入記憶，下一個新 session 是否受影響 | 直接寫入記憶 |

都還沒量，目前是假設。

## 11. 和 17 的比較

| | 17（06 骨架） | 18（原模型） |
|---|---|---|
| 問題界定 | 污染與覆蓋缺口 | 重新界定為：用量大時人審不完、錯誤要到出事才知道；污染是結果 |
| 方向從哪來 | AI 自己挑的 7 組對照 | 四種情境差異 + 六個縮窄維度 |
| 最主要的新東西 | 帶出處的教訓流程 | **用 stg 和自己的任務紀錄測試 AI 的指令**（17 完全沒有） |
| 適用範圍 | 推論寫出 | 向上迴圈逐步移除情境找出，並找到優勢消失的位置 |
| 17 的 T3、T4 | 有 | 沒有出現：它們沒有對應到「在地資源」，屬於一般原則 |

原模型多產生的，正是它獨有的部分帶來的：「可用的資源」那一類讓 stg 和任務紀錄浮現；資源重新詮釋讓它們變成測試場和資料集；向上迴圈找到了優勢消失的位置（純程式碼工作、輕度使用）。
