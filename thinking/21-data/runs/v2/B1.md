### Analysis
Directions. Forward: from a concrete failure scene in this workflow to a mechanism that prevents it. Backward: from that mechanism, imagined in daily use, to the scene where it fails, is bypassed, or creates new load. Each backward end point is the next forward start. Progress means a scene not already handled by existing practice (worktrees, Terraform locking and saved plans, Argo notifications, multi-session managers, TodoWrite, auto-memory) or an earlier item. Stop when backward moves only produce covered scenes.

Loop:
1. Scene: two windows apply to one namespace; worktrees isolate files, not clusters -> lease broker (I1).
2. Back: the broker keys on the target, but the target hides in a shared kubeconfig another agent just switched -> session pinning (I2).
3. Back: pinned to prod, the agent can still run destructive commands; string permissions cannot judge them and scripts dodge hooks -> plan-bound credentials (I6).
4. Back: the human now approves 300-resource plans and rubber-stamps them -> scope declaration (I7).
5. Back: the right change applies, but "healthy" in the report was never checked -> evidence gate (I3).
6. Back: under GitOps the verifier cannot pass before the session ends -> reconcile watcher (I4).
7. Back: the resumed agent fixes the incident with kubectl patch or ssh+sed, bypassing Git -> backport gate (I5).
8. Back: shims and ledgers now store raw output, including Secret data -> secret firewall (I8).
9. Back: every gate can block a session; with eight windows across three tools, blocked or looping ones go unseen -> attention queue (I9).
10. Back: the queue shows identical loops recurring across sessions -> failure-fix miner (I10).
11. Back: mined rules diverge across CLAUDE.md/AGENTS.md/Cursor rules (symlinks and sync tools cover this); huge outputs bloat context (truncation plus I3's stored output cover most); cross-session handoff (I3 ledger plus native todos/compaction). Nothing new: stop.

Ranking: frequency x blast radius x how weakly current tools cover it, not loop order. I1, I3, I5 and I8 share one shim layer (target resolution plus read/write classification), so build that first.
### Items
I1: Parallel agents mutate the same live state (cluster namespace, Helm release, Terraform state, host) unaware of each other. Worktrees isolate files only, and an agent's reviewed plan can be silently invalidated by another agent's apply. || Lease broker: a local SQLite daemon plus PATH shims (kubectl, helm, terraform, argocd, ssh) in agent sessions. Each shim resolves the concrete target (context+namespace, release, state key+workspace, host), classifies the verb read/write, and for writes takes a lease tagged with session ID and task. Conflicting writes are refused, naming the holder and its task. Leases heartbeat via PostToolUse and release on SessionEnd; the terraform shim permits apply only from a saved plan file, so Terraform's stale-plan check fires.
I2: Kube context, gcloud config and the default AWS profile are global per user. One agent's kubectl config use-context or gcloud config set project silently retargets every other session and the human's own terminal. || Session context pinning: a SessionStart hook creates ~/.agent-ctx/<session>/ holding a kubeconfig reduced to the declared target contexts, a private CLOUDSDK_CONFIG directory and an AWS config with one profile, then exports KUBECONFIG, CLOUDSDK_CONFIG and AWS_CONFIG_FILE through CLAUDE_ENV_FILE (a launcher wrapper does the same for Codex/Cursor). A PreToolUse hook rejects commands that escape it (--kubeconfig, --context outside the set, inline env overrides). The status line shows the pinned target; retargeting requires an explicit, logged /retarget command.
I3: Agents report "applied, rollout healthy, no drift" without having run the check, or ran it before the last change. In long tasks the human cannot tell which claims rest on observed output. || Evidence gate: a PostToolUse hook appends every command, exit code, timestamp and output hash to a session ledger, tagging writes with their target (via the shim classifier). A Stop hook requires each written target to have a later passing verifier from a rule table (terraform plan -detailed-exitcode exit 0, kubectl rollout status, argocd app wait --health, a health-endpoint curl). Unverified targets block Stop with a list; the final report gets an evidence table linking each target to ledger entries.
I4: With GitOps the real change happens after merge, when Argo CD or Flux reconciles. The agent session has ended, so sync errors or degraded health surface hours later to a human lacking the session's context. || Reconcile watcher: when an agent opens a GitOps PR, a hook registers session ID, worktree, PR number and the Argo apps or Flux Kustomizations mapped from changed paths with a daemon. After merge it polls the Argo/Flux API until those apps report the merge commit Synced and Healthy. On failure or timeout it gathers events and controller messages, runs claude --resume <id> -p with them in the original worktree, and notifies the human with the diagnosis.
I5: Under pressure agents fix things imperatively: kubectl patch/scale/edit, sed on a host over ssh, a direct cloud CLI call. The fix works, is never written back to Git/Ansible/Terraform, and is later reverted or becomes silent drift. || Backport gate: the shims log every imperative write that bypasses GitOps/IaC (kubectl patch/edit/scale/set, mutating aws/gcloud verbs, ssh commands matching write patterns with before/after copies of touched host files) into an out-of-band ledger. A Stop hook blocks completion while any entry lacks either a commit in the owning repo (found through a resource-label/host-group->repo map) that codifies it, or a human waiver with expiry. Codification is verified by an empty kubectl diff, terraform plan or ansible --check for that resource.
I6: Permission rules match command strings, so they cannot tell staging from prod or a safe apply from a destructive one, and scripts or bash -c bypass them. Engineers end up rubber-stamping prompts or skipping permissions entirely. || Plan-bound credential broker: agent sessions hold only read-only cloud and cluster identities. To mutate, the agent submits an artifact (saved terraform plan, helm diff, kubectl diff) to the broker; the human approves on a phone/web page showing its risk summary. The broker mints credentials scoped to exactly those resources for 15 minutes (AWS STS session policy, Kubernetes TokenRequest bound to a generated Role), named after the session ID so CloudTrail and k8s audit logs trace back to the transcript.
I7: Agent changes often reach beyond the request: a "small" Terraform edit replaces a database, a values tweak touches other environments, a refactor reformats 40 files. Large plans and diffs hide the out-of-scope parts from reviewers. || Scope declaration check: at task start the agent drafts scope.yaml listing intended resource-address globs, environments, file globs and allowed actions (e.g. no destroy/replace); the human approves it. A checker runs over terraform show -json, helm diff, rendered-manifest diffs and git diff --name-only, flagging every change outside the declaration plus fixed hazards (replacing stateful resources, IAM or network widening). Flagged items head the approval page and need individual acknowledgement or an explicit scope amendment recorded in the ledger.
I8: Infra commands (kubectl get secret -o yaml, terraform output, env, helm get values) put credentials into model context, plaintext local transcripts and provider logs. Afterwards nobody knows which secrets leaked and need rotation. || Secret firewall: shims redact at the source (Secret data fields, sensitive Terraform outputs, env values whose keys match patterns), replacing each with a stable fingerprint (secret:<hmac8>) so the agent can still compare values. A PreToolUse hook denies raw readers (base64 -d on secret data, cat of credential files). A scanner applies gitleaks rules to new transcript lines, redacts them in place, and files a rotation ticket per exposed secret with source command and session.
I9: With eight sessions across Claude Code, Codex and Cursor windows, the human cannot see which are blocked on approval, finished, or looping on one error; blocked sessions sit unnoticed for hours while looping ones burn tokens. || Attention queue: a daemon tails each tool's local transcripts (~/.claude/projects/*.jsonl, ~/.codex/sessions) and receives hook events (Notification, Stop, Cursor's stop hook) over a Unix socket. It derives per-session state (working, awaiting approval, done, stuck), flagging loops by hashing (command, normalized error) pairs; three repeats means stuck. A TUI sorts sessions by how long the human has been the bottleneck, shows each one's target and tokens/hour, and jumps to its tmux pane or window.
I10: Each new session rediscovers the same facts (which bastion reaches a host group, a cluster's context name, the make target CI needs) through failed commands. CLAUDE.md is updated by hand, rarely, and goes stale. || Failure-fix miner: a nightly claude -p job scans the day's transcripts for a failed command followed by a succeeding variant, clusters these across sessions by normalized error, and for clusters seen in two or more sessions drafts a one-line rule into the matching repo's CLAUDE.md/AGENTS.md or a skill, opened as a PR with occurrence counts and tokens wasted. Each rule records its source and last-confirmed date; rules unconfirmed for 60 days are re-tested or proposed for deletion.
