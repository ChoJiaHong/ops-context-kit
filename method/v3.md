# v3：合併第 3 輪的結果（尚未驗證）

第 3 輪在新案例上表現最好的是專家修改版 a4′（0.85），方法修改版 a3′ 是 0.82，依預先登記沒有放進 template（見 [round3.md](round3.md)）。v3 的做法是把 a4′ 的具體做法併進 K 編號的規則，保留這個 repo 的工具：`tasks/`、SessionStart 列表、guard、check_kit 與評估迴圈。

**狀態：未驗證。** v3 是一份新的規則集，沒有在任何案例上評過。在新案例上驗證之前，不應該說它比 a4′ 或 a3′ 好。

## 每一條的來源

| 規則 | v3 的內容 | 來源 |
|---|---|---|
| K1 任務紀錄 | 接手時寫回原本的紀錄；只在三個時點更新；其他任務的紀錄只能附加；同步 manifest、補共用變更紀錄 | a3′ 的 K1′，加上 a4′ 第 1 節 |
| K2 平行 session | 衝突檢查寫成指令：`grep -rl` 整個工作區、`who`、`ps`、auth.log、LB 狀態、rollout history | a4′ 2c。第 3 輪 e01：寫成指令的 a4′ 比寫成類別的 a3′ 高 0.07 |
| K3 明確指定目標 | 照抄筆記的指令也補 context；Bash 不能靠 export 記目標；`sudo -n`、久跑包 `timeout`、連不上就標示 | 原 K3，加上 a4′ 第 0、4、5 節 |
| K4 直接做或停下 | 授權來源；「查」與「處理」的區別；直接做的條件；停下條件依「可回復性 × 環境 × 授權」 | a4′ 第 3 節。第 3 輪 e03：a3′「不可逆就停」沒有分環境，比 a4′ 低 0.11 |
| K5 變更與驗證 | prod 變更前存檔與 diff、備份成新檔名、語法檢查、能 reload 不 restart、逐台；驗證要撐過原本出錯的時間點；prod 驗證失敗先回滾 | 原 K5，加上 a4′ 第 2.5、4、5、6 節 |
| K6 一個 session 一件事 | 不變 | 原 K6 |
| K7 事實要查 | 前提與原因兩項檢查；prod 版本或設定變更先確認 stg；故障先止血 | 原 K7，加上 a4′ 2a、2b、第 2.3 節 |
| K8 收尾 | 唯讀檢查同類目標；回覆必須包含的內容 | 原 K8，加上 a4′ 第 2.6 節。第 2 輪 d03 `prod-heads-up`、d08 `siblings-flagged` 各組都偏低 |
| K10 腳本與輸出 | 只有會改變狀態的腳本才預設 dry-run；輸出先收斂；secret 不外洩 | 原 K10，加上 a4′ 第 4、6 節 |

沒有採用的 a4′ 內容：
- `ops/sessions/` 的 session 檔格式和每則回覆的狀態行：v3 用 `tasks/` 和 SessionStart hook 達成相同目的。
- 寫死在規則裡的環境清單：v3 一律以 TRUTH.md 為準。
- 變更卡：停下時回覆要附的事實、影響、下一步已經寫在 K4。

規則本體 2,455 字（a3′ 1,781 字、a4′ 2,574 字），AGENTS.md 69 行，在 80 行的上限內。

## 工具的改動
- `guard.py`：新增 `KIT_PROD_CONFIRM=0`，可以關掉「prod 上的可回復變更要確認」，不可逆操作仍然要確認。預設不變，因為在桌面版互動使用時，確認只是多點一次核准，算是保險。核准提示的文字改成給使用者看的說明。回歸測試 39/39 通過。
- `CLAUDE.md`：說明核准提示不代表 agent 該先停下來問。

## 已知的不一致
- `evals/suite/c02-prod-upgrade-confirm` 期待 agent 在使用者明確要求 prod 升級時停下來確認。v3 會先查 stg，若前提成立就直接做。這個案例是第 1 輪由規則作者寫的（循環評估），我沒有為了配合 v3 改它的 grader，因為那會重複同樣的問題。要改的話，應該由你依真實情況決定這類任務的正確做法。

## 驗證 v3 的方式
沿用第 3 輪的設計：先登記判定標準，請獨立作者寫一批新案例，組別是 a0、a4′、v3。v3 至少要不低於 a4′ 減 0.03，並且通過放進 template 的三個條件，才算驗證通過。
