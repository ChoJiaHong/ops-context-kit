# 30 把目前的問題正規化成已知問題

2026-11-15。使用者：「這個問題應該正規化成現有問題中的哪個問題？模型做得到嗎？還是不需要模型也能解決？目的是判斷：我需要為現在的問題創造新解法，還是現有解法就能解決。」

## 目前的問題（P0，當成假設）

來自使用者一開始說的目標與困擾：

- 平行開很多個 Claude session 處理 k8s 叢集和遠端主機，想要：工作流程一致、每個 session 目的清楚、session 好管理、可行又有效率。
- 「目前用 agent 還需要一步步確認或寫需求」「plan 模式下需求與我差很多」。
- 「多 session 我如何控制污染」。
- 之前的試驗裡出現過的：改到 prod 的風險、agent 說做完但沒做完、記憶與規則過期。

## 正規化

| 子問題 | 正規化成的已知問題 | 已知的標準解法 | 已查證的現成工具（見 23、24） | 需要新解法嗎 |
|---|---|---|---|---|
| 需求和 plan 落差大、要一步步確認 | 委託代理問題（資訊不對稱、目標不一致）＋規格問題 | 事先寫明驗收條件與完成定義；動工前審查計畫 | spec-kit、Claude Code plan 模式、workflow 分支的 `/start` | 不需要 |
| session 目的不清楚 | 工作分解與任務綁定 | 一個 session 對一張工單；限制同時進行的數量 | workflow 分支的 task.py、Jira 整合 | 不需要 |
| session 之間的污染 | 隔離與最小權限（多租戶隔離） | 每個 session 獨立環境與憑證 | git worktree／worktrunk、kubie、kube-guard、container-use | 不需要，需要組裝 |
| 很多 session 要盯 | 監督控制與例外管理（一個人監督多個自動化系統） | 只在例外時通知、狀態總覽、逐級升級 | Claude Code 的 session 總覽、agent-sessions、Lucarne（343 星） | 現有的不夠好（24 的 F09、F15），**可能值得自己補** |
| 記憶與規則過期 | 設定漂移／快取失效 | 單一事實來源、從 IaC 產生事實、定期驗證 | stalebrain；19 的「能查就不手寫」 | 不需要，小工具即可 |
| 改到 prod 的風險 | 變更管理＋安全聯鎖 | 審批綁定 plan、最小權限、dry-run | palisade、OPA／conftest、Atlantis、destructive_command_guard、guard.py | 不需要 |
| agent 說做完但沒做完 | 驗收測試／驗證問題 | 由獨立的檢查確認，不信自我回報 | unlazy、transcripto、Stop hook | 不需要 |
| 工作流程不一致 | 流程標準化 | 標準作業程序、範本、檢查清單 | CLAUDE.md、skills、hooks | 不需要 |

**整體**：目前的問題是一組已知問題的組合，可以統稱「一個人監督、協調多個代理人」。每一個子問題都有標準解法和現成工具。

**所以真正的問題是「選型與整合」**：從現成工具裡挑出適合 k8s 與遠端主機環境的，組成一套自己的工作方式。只有「很多 session 要盯」這一項，現有工具確實不夠好，是唯一可能值得自己做的地方。

## 模型做得到嗎？需要模型嗎？

- 這件事正好是原模型的前三步：問題當假設並抽象化 A(P0)、盤點現有解法、找瓶頸。
- 但不需要整個模型：21–26 的實驗顯示，AI 不用模型也會做抽象化和盤點。
- 真正決定結果的是兩件事：(1) 現有解法要**實際查證**，像 23、24 那樣搜尋，不是憑印象；(2) 子問題是不是**真的發生**、多常發生，要用使用者自己的紀錄確認。上表是根據對話整理的假設，還沒用紀錄驗證過（[22](22-validation-guide.md) 的驗證就是為了這個）。

## 下一步

1. 使用者確認上表的子問題，哪幾項最痛。
2. 有紀錄的話，用 22 的方式數出每項實際發生的次數。
3. 對最痛的幾項，從現成工具裡挑選、試用；只有現成工具真的不夠時，才做新的。
