# 24 找出現在無解、或沒有完美解的問題

2026-11-07。接 [23](23-community-backtest.md)：23 裡兩組方法找出的點子，6 月前都已經有小工具。這次反過來，**先找出現在還沒被解決的問題**，再拿來測方法。這份文件是第一步：找題。

## 規則（查證前登記）

**來源**：只用 GitHub。用 REST 搜尋抓目前仍開著（open）、反應數最多的 issue：

| repo | 取幾則 |
|---|---|
| anthropics/claude-code | 150 |
| openai/codex | 60 |
| google-gemini/gemini-cli | 20 |
| cline/cline | 20 |

共 250 則，在 [24-data/candidates-raw.md](24-data/candidates-raw.md)。

**篩選**（由一個 agent 依下列規則做，不由我挑）：
- 留下：把工作交給 agent 時，工作流程上的痛點，而且**不只原廠能解**，第三方用 hook、包裝程式、MCP、做法就有機會解。例如記憶、跨 session 協調、驗證 agent 的說法、安全、context、成本控制、整合。
- 去掉：計費、方案、帳號、登入；平台、IDE、作業系統支援；介面顯示問題；服務中斷與 API 錯誤；模型文風；只有原廠能改的功能。
- 同一個痛點的 issue 合併成一類，記下所有 issue 和反應數總和。

**查證**（23 的教訓：一個 agent 判會寬嚴不一）：每一類由**兩個獨立的查證 agent** 分別查到今天為止的 GitHub repo、issue 和網路，判定：

| 判定 | 條件 |
|---|---|
| 無解 | 找不到任何工具、產品功能或公認做法處理這個痛點的核心 |
| 沒有完美解 | 有工具或做法，但有具體證據顯示不夠：仍開著的 issue 說明現有做法的缺點、使用者回報失敗、只解一部分 |
| 已解 | 有工具或功能已經處理核心，且沒有證據顯示不夠 |

- 每個判定都要附連結和日期。
- 兩個 agent 判定一樣才收；不一樣的標為「不一致」，不收。
- 我抽查約 20% 的連結。

**產出**：無解與沒有完美解的問題清單，每題寫明處境、需求證據（issue 與反應數）、現有做法與它的不足。這份清單是下一個實驗的題目。

## 結果

**篩選**：250 則（修正分頁錯誤後）留下 85 則，合併成 29 類，在 [24-data/families.md](24-data/families.md)。去掉 165 則：只有原廠能改 32、介面 28、平台與 IDE 27、帳號 14、計費 12、服務中斷 12、原廠產品間同步 7、模型文風 2（前 200 則的統計，後 50 則的併入檔案末尾）。

**查證**：兩組各 4 個 agent，結果在 `24-data/result-X*.json`、`result-Y*.json`。

| 判定 | 類數 |
|---|---|
| 無解（兩組都判） | **0** |
| 沒有完美解（兩組都判） | **28** |
| 已解（兩組都判） | 0 |
| 不一致 | 1（F29「agent 看不到它改的網頁」：一組判已解，一組判沒有完美解） |

- **沒有一類是完全無解的。** 每一類都至少有一個工具、產品功能或做法處理了一部分。
- 「沒有完美解」幾乎涵蓋全部，三分法分不出差別。
- **抽查**：10 個查證 agent 引用的 repo，建立日期、星數、內容全部和引用的一致。
