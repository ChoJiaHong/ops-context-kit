# Pairs to check (anonymous, shuffled)

## X01
P: During long multi-step ops tasks (upgrading six Helm releases, migrating Terraform state), sessions die mid-mutation from usage limits, stream timeouts, unparseable tool calls or crashes. On resume or handoff, the agent cannot tell which steps landed; it re-runs non-idempotent steps or abandons half-applied changes.
Se: --resume plus auto-continue tools (claude-auto-retry) restore the conversation and type 'continue'; checkpoints/rewind revert local file edits only; in-context todo lists blur under compaction. None knows whether the apply running when the session died completed, failed or is still running.
Sn: Mutation journal with reconcile-on-resume. The agent records its plan as journal steps: id, command, target, precondition probe, postcondition probe (e.g., helm history revision, kubectl rollout status, terraform plan -detailed-exitcode returning 0). Mutating commands run detached under a supervisor that writes start, exit code and output tail to the journal even if the agent process dies. On any resume or handoff, to another session or another vendor's agent, the harness runs postcondition probes for started-but-unconfirmed steps, marks each done/not-done/unknown, blocks re-running completed step ids, and hands the agent this reconciled state instead of the old transcript.
Check: Fault injection: kill 100 multi-step rollout sessions at random points, then resume. Count duplicate or conflicting mutations, abandoned half-applied changes and human recovery minutes: Sn versus --resume with auto-continue.

## X02
P: Ops agents run kubectl get secret -o yaml, terraform output/state show, helm get values. Secret values enter the transcript, go to the model provider, persist in local session logs and summaries, and can resurface in commits. P*: secrets whose position in infra-tool output is structurally known.
Se: 1Password `op run` masks only secrets it injected; Vault Agent injects into env/files; gitleaks/trufflehog scan commits; permission deny rules block reading .env paths. None masks secrets the agent fetches from clusters or state at runtime, and commit scanning is too late: transcripts and provider requests already hold them.
Sn: Secret handles at the tool boundary. A wrapper around shell execution parses outputs of known infra commands (Secret .data/.stringData, terraform values marked sensitive, helm values under password/token/key names, plus an entropy fallback) and replaces each value with a handle like «sec:ctx/ns/name/key#h», h being a keyed hash so equal values get equal handles. Values live in a per-session in-memory vault. When a later command contains a handle, the wrapper rewrites it to an env-var reference set only for that process (never argv or transcript) and masks that output. The agent can copy, compare and rotate secrets without seeing them.
Check: Seed canary secrets in a test cluster and Terraform state; run typical debug/rotation tasks. Count canary values in captured provider requests, session logs and commits: Se >0, Sn 0, with task success rate within a few points of Se.

## X03
P: Ops agents constantly touch secret-bearing output: `kubectl get secret -o yaml`, `terraform output`, `vault read`, `env`, Helm values. Credentials then land in model context, provider logs, local session files, compaction summaries and sometimes commits or PRs, which blocks agent use on production accounts in regulated teams.
Se: Deny rules on reading .env files, secret scanners (gitleaks) at commit time, `op run`/Vault agent env injection, CI-style log masking. They keep secrets out of files and git, not out of tool output the model reads; plain masking breaks tasks that must reuse the value.
Sn: Secret handle broker: a tool-output filter detects secrets structurally (Kubernetes Secret data, Terraform sensitive outputs, Vault response fields, known-format tokens, values registered from the vault) and replaces each with a stable handle like ‹secret:prod-db-pw#a1f3›. The model reasons and writes commands with handles. A pre-execution shim resolves handles only inside the subprocess, via environment variables or stdin rather than argv, and re-masks any echoed value in output. Handles in written files resolve only at apply time. Handles are scoped to the session and target, expire with it, and every resolution is logged.
Check: Seed canary secrets into test clusters and vaults; across N ops tasks, canaries never appear in transcripts, provider requests or session files, while task success rate matches an unprotected baseline (masking-only baseline fails reuse tasks).

## X04
P: Scope P*: delegated multi-step infra tasks whose result is live state, not code. Agents report "deployed", "fixed" or "done" from their own narrative; the engineer, juggling parallel sessions, must re-verify every change by hand or trust claims that miss a pending rollout, drifted resource or skipped environment.
Se: Stop hooks that run a fixed test/lint command, CI pipelines, and GitOps health status (Argo CD/Flux synced/healthy). Stop hooks and CI check code, not which live targets this session touched; Argo shows health only for apps it manages and nothing forces the agent's final report to cite it.
Sn: Convergence-evidence gate. Every mutation the session made (from its command log or op ledger) registers a target and a matching convergence probe: terraform plan -detailed-exitcode returns 0, helm status deployed at expected revision, kubectl rollout status complete with ready replicas, Argo app Synced/Healthy, or an SSH service check. A Stop hook refuses completion while any touched target lacks a passing probe newer than its last mutation, returning the failing probes to the agent. The handoff report is generated from probe results, one row per target with evidence, so the engineer reads verified state, not the agent's prose.
Check: On 100 delegated infra tasks: rate of "done" reports later found unconverged (Sn vs Stop-hook/CI baseline), engineer minutes spent re-verifying per task, and extra agent turns the gate costs.

## X05
P: Ops engineers running agents with kubectl, helm, terraform and ssh must approve commands by text pattern. The same `kubectl delete` or `terraform apply` is harmless against dev and catastrophic against prod, depending on kubeconfig context, env vars or workspace, so they either drown in prompts or allow too much.
Se: Claude Code permission rules plus auto mode's action classifier (unavailable on Bedrock), PreToolUse hooks, Codex sandbox/approval policies. All judge command text and transcript; none resolve which cluster, account or state the command will actually hit, and wrapper scripts, aliases or a changed current-context slip past.
Sn: Effect-resolving gate (PreToolUse hook, agent-agnostic): parse each command, including compound commands, into tool invocations; for kubectl/helm/terraform/aws/gcloud/ssh resolve the effective target exactly as the tool would (kubeconfig + flags + env, AWS profile/region, terraform backend key + workspace, inventory host group) and classify the verb as read, mutate or destroy, using server-side dry-run or plan when unsure. A policy matrix keyed on target tier × verb class decides: auto-allow, ask, or deny. Prod asks show resolved target and dry-run diff and require typing the target name. Unparseable or opaque scripts default to ask.
Check: Replay a month of recorded agent commands plus red-team cases (switched context, alias, env override): Sn needs fewer approvals than prefix rules/auto mode while letting zero prod mutations through unapproved; baseline lets some through or prompts more.

## X06
P: Terraform plans, `kubectl get -A`, `describe`, `helm template` and pod logs run to thousands of lines. Agents either ingest it all, filling context and draining quota, or truncate with head/grep and miss the one forced replacement, IAM change or CrashLoopBackOff that mattered, then report success.
Se: Harness truncation that spills long output to a file, agent-written grep/jq filters, and plan summarizers such as tf-summarize. Filters are guessed per call and silently drop what they didn't anticipate; summarizers cover one tool and give no completeness guarantee the agent can rely on.
Sn: Typed ops digests: a tool-output hook recognizes known commands and replaces raw output with a fixed-schema digest, keeping raw output on disk behind a queryable handle. Terraform: counts per action, every delete/replace with the forcing attribute, all IAM, network and data-store changes. kubectl: only unhealthy objects, Warning events and counts. Logs: deduplicated templates with counts and first/last timestamps. Invariant: risky items are never elided; if they exceed the budget, the digest says so and mutating commands are refused until the agent pages through them. Digest parsers are tested against recorded outputs per tool version.
Check: On recorded ops tasks, tokens per task fall by half or more versus raw/truncated output, and on seeded plans and clusters with buried destroys or failing pods, miss rate drops to zero while baseline misses some.

## X09

## X15
P: Infra engineers whose subscription quota drains fast across parallel sessions see an agent stop mid-task at the limit, often between a disruptive step and its restore: node drained not uncordoned, replicas scaled down, terraform state locked, for hours until reset. P*: looped ops tasks with identifiable critical sections.
Se: claude-auto-retry (and the requested Codex auto-resume) waits for the reset and continues; ccusage, status lines and /usage show remaining quota. Sn: Quota-aware step admission. The plan marks critical sections (from drain/scale-down/state lock to restore and verify). Check: Run N-node drain/upgrade loops under tight quotas with parallel load. Count quota stops inside critical sections and node-hours left cordoned or scaled down: auto-retry vs Sn. Sn: zero in-section stops, at most modestly longer completion time.

## X21

Se: Session resume (claude --resume, codex resume) plus auto-continue-after-limit wrappers, background shells, and tmux. Resume restores the conversation, not what happened to the side effect; background shells die with the session; tmux keeps the process but the agent has no structured way to find and read its outcome.
Sn: Operation ledger outside the session. A PreToolUse hook rewrites mutating infra commands to run under a detached supervisor (systemd-run --user or setsid) that appends a ledger record: op id, session, resolved target, command, start, PID, log path, exit code, plus a tool-specific post-probe (Terraform state serial, Helm revision/status, rollout status). SessionStart hooks on startup, resume and compact inject a digest of open and finished ops ("op 17 apply prod-net: exit 0 10:42, serial 311→312"). Re-issuing an identical mutation while its op runs is blocked with "attach to op 17". Agents poll ops instead of holding shells.
Check: Fault injection: kill network/session mid-operation across 50 runs; count duplicate applies, orphaned locks, wrong completion claims and minutes to correct recovery, Sn versus resume-only baseline.

## X24
P: Ops engineers letting agents run kubectl, helm or terraform against live systems: a wrong apply, delete or upgrade changes remote state that agent undo cannot reach, so recovery is manual, slow and stressful. P*: agent-made mutations of declarative systems whose prior state is readable (Kubernetes, Helm, Terraform-managed cloud).
Se: Claude Code checkpoints/rewind (like Codex's removed /undo) restore only local file edits, not shell side effects. Remote recovery uses separate tools (helm rollback, Velero backups, versioned Terraform state) that are coarse, manual and not linked to the agent step that did the damage.
Sn: Remote-state undo journal. A pre-execution hook classifies each command; for a mutation it first runs the tool's native dry run (kubectl apply --dry-run=server, helm diff, terraform plan -out) to list exactly which objects will change, saves their pre-images (kubectl get -o yaml, current Helm revision, terraform state pull) and records the inverse action under the tool-call ID. Rewinding the session to step k replays the inverses in reverse order, each after a dry-run diff. Steps whose dry run shows unrecoverable loss (PVC, database, destroy) are flagged irreversible beforehand and need explicit approval.
Check: Drill with 20 seeded harmful agent steps on a test cluster: share undone by one rewind and median time-to-restore, Sn versus engineers recovering manually with helm rollback/Velero (expect ≥90% restored, ≥5× faster).

## X25
P: An agent running a long fan-out task (a package upgrade on 60 hosts) is interrupted by compaction, a usage-limit pause, a dropped stream or a handoff, resumes from its own todo list, and skips or repeats targets. P*: long agent tasks over enumerable targets with queryable live state.
Se: Agent todo lists, plan files and Agent Teams' shared task list hold status the model wrote itself, never re-checked against reality. Ansible or Argo CD are idempotent but need the procedure written upfront, while agent work adapts per target.
Sn: Harness-owned target ledger. At task start the agent registers each target with a read-only postcondition command whose exit code proves it done (e.g., helm status app -o json | jq -e '.version>=7'; ssh host rpm -q agent-2.4). The harness, not the model, stores the ledger. On every resume, compaction, retry or handoff it re-runs all postconditions in parallel, recomputes done/pending/failed, and injects only pending targets with their last error. ## X26

Sn: Harness-owned, probe-verified checklist. Each plan step carries a postcondition probe: a read-only command plus predicate (e.g., `kubectl get nodes -o json | jq '[.items[].status.nodeInfo.kubeletVersion]|all(.=="v1.31.4")'`), approved by the human once at handoff. The model cannot mark steps done; the harness runs the probe after each step and records pass/fail with output. ## X27

## X28

## X29
