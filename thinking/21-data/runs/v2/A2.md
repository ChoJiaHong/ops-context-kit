### Analysis
Existing practice covers the repository side well. Worktrees isolate files, CI runs plan, lint and policy-as-code on PRs, Terraform locks serialize state writes, and session managers organize terminals and worktrees. The gaps are where the repo ends and live systems begin, and where many sessions compete for one human's attention.

Shared live state. Sessions have separate files on disk but share the kubeconfig current-context, cloud CLI profiles, Terraform states, Helm releases and namespaces. Nothing coordinates them at the level of the live target. A branch that applies before it merges can revert another branch's change, and the other way round.

Enforcement at the wrong layer. Permission rules and most hooks match command strings. They miss the real target (an alias, a variable, a switched context), the impact (a plan that replaces a database) and bypasses (a boto3 script). They are also agent-specific, so Codex or Cursor sessions escape Claude hooks. Real control needs target resolution, computed impact and scoped credentials, built as PATH shims, credential plugins or daemons that every agent goes through.

Human attention. With ten sessions running, the engineer has to decide which one to attend to next. Prompts are scattered across terminals and carry no context, so the engineer approves them without reading. That is the failure permissions exist to prevent.

Completion and provenance. Agents report "done" based on indirect signals, but in infrastructure success means the live state is right. Afterwards nobody can tell which session changed what, or whether an applied change ever reached main.

Infra conventions. Generic agent tooling knows nothing about which resources GitOps owns, and it cannot see inside commands sent to hosts over ssh.

Knowledge freshness. Memory files are static prose, and the infrastructure changes underneath them.

Design principle: all the tools share one session ID, one target resolver and one policy file. Each tool can be built alone, but they work better together.

Dropped: output compression for verbose CLIs (existing tools cover most of it), syncing CLAUDE.md/AGENTS.md/Cursor rules (generators and symlinks are enough), and tracking prompt-injected content from logs and issues (a real risk, but better handled as one more input to the impact gate and credential broker than as a separate tool).
### Items
I1: Parallel sessions share global CLI state: kubeconfig current-context, gcloud active configuration, default AWS profile. When one agent switches context, every other session's next command, including destructive ones, silently goes to another cluster or account. || Session target pinning: a SessionStart hook reads the worktree's `.target` file (cluster, namespace, account). It writes a per-session kubeconfig containing only that context plus a per-session cloud config, and exports KUBECONFIG, CLOUDSDK_CONFIG and AWS_PROFILE via CLAUDE_ENV_FILE. A PreToolUse hook blocks `kubectl config use-context`, `gcloud config set` and profile switches, and tells the agent to start a new session for another target. PATH shims enforce the same for Codex/Cursor. The statusline shows the pinned target.
I2: Permission rules match command prefixes, so `terraform apply` or `kubectl delete` is either always allowed or always asked. They cannot see that the real target is prod, that the plan replaces a database, or that a variable hides the target. || Impact gate (PreToolUse hook plus PATH shim): it resolves the real target (kube context/namespace, cached `sts get-caller-identity` account, Terraform backend key) and computes the impact. For Terraform it forces `plan -out`, parses `terraform show -json` to count deletes/replaces per resource type, then allows only `apply <planfile>`. For kubectl/helm it runs a server-side dry-run or `helm diff`. A YAML policy maps (environment, action, resource class, count) to allow/ask/deny. "Ask" shows the computed summary, not the raw command.
I3: Agents run with the engineer's ambient admin credentials. Hooks only match strings, so an agent bypasses them by writing a boto3 script or curling the API. A confused agent can then do anything the human can. || Session credential broker: agents run as a separate OS user that cannot read the engineer's admin credentials. AWS credential_process and a kubeconfig exec plugin call a local broker that mints short-lived credentials for the declared task scope: STS AssumeRole with an inline session policy limiting accounts and actions, and a TokenRequest token for a ServiceAccount bound to namespace Roles. Both are read-only by default. Writes need a human-approved elevation that expires after N minutes. Role session names carry the session ID.
I4: Worktrees isolate files, not live targets. Two sessions on different branches apply to the same Terraform state or Helm release, and each apply reverts the other's unmerged change. State locks make applies take turns but never detect this. || Target lease broker: a daemon (SQLite locally, DynamoDB when shared) keyed by live target: Terraform backend+key, Helm release+cluster, namespace. A PreToolUse hook extracts the keys from mutating commands and takes a lease tied to session ID and branch. The lease lasts from the first apply until that branch merges or is rolled back. Conflicting applies are blocked with "held by session S, branch B; wait or rebase onto it". After the merge, the next holder's branch must contain that commit before it can apply.
I5: The human decides which session gets attention next. A dozen sessions across Claude Code, Codex and Cursor wait on prompts or questions in separate terminals. The engineer notices them late and approves without reading, because each prompt shows only a raw command. || Decision inbox: Notification, PreToolUse-ask and Stop hooks (and matching shims for other agents) post a record to a local queue: session, repo/branch, pinned target, impact summary from the gate, last assistant message. The PreToolUse hook waits for the answer and returns allow/deny, so the engineer never has to answer in the terminal. A TUI and a phone page sort items by environment risk and wait time, group identical requests for one-click approval, and offer "approve and add rule". They also list sessions that stopped on an unanswered question.
I6: Agents fix cluster issues by changing them directly (`kubectl edit/scale/patch`, `helm upgrade`) on resources that Argo CD or Flux manage. The next sync reverts the fix. With self-heal off, the fix becomes silent drift that the repo no longer describes. || GitOps ownership guard: for mutating kubectl/helm calls, a PreToolUse hook fetches the target objects and reads their tracking metadata (`argocd.argoproj.io/tracking-id`, `app.kubernetes.io/instance`, `kustomize.toolkit.fluxcd.io/name`, `helm.toolkit.fluxcd.io/name`). It finds the owning Application or Kustomization and its repo URL, path and values file, then blocks the command with "edit <repo>/<path>/values-prod.yaml instead". A break-glass flag lets the command run but opens a drift record. A Stop hook keeps blocking until a git commit touching that path exists.
I7: On long multi-part tasks, agents claim success from indirect signals ("manifests valid", "PR opened") or lose subtasks after compaction. In infrastructure, "done" means live state: rollout healthy, plan empty, alert cleared. Nothing checks that before the session stops. || Acceptance contract: the task is a `task.yaml` of subtasks, each with runnable checks (`terraform plan -detailed-exitcode` exits 0, `kubectl rollout status --timeout=5m`, `argocd app wait --health`, a PromQL query under a threshold). A Stop hook runs the checks for unfinished items and refuses to stop while any fail, showing the failing output. It writes pass evidence (command, exit code, output hash, time) back to the file. A SessionStart(compact) hook re-adds the remaining items after compaction. PreToolUse blocks agent edits to the checks.
I8: Live changes cannot be traced. An agent applies from an unmerged worktree branch, the PR is abandoned, and the next apply from main silently reverts the change. Cloud and Kubernetes audit logs show only the engineer's identity, not which session acted. || Apply ledger: hooks/shims record each mutating command (session ID, repo, commit SHA, resolved target, exit code) in SQLite. They also stamp the session's identity into each system: AWS role session name `agent-<sid>`, `kubectl --field-manager=agent-<sid>`, `helm upgrade --description <sid>@<sha>`, and the Terraform state serial before and after. Applies from uncommitted changes are blocked. A daily job flags applies whose SHA is not reachable from main after 24h. A query joins the ledger with CloudTrail and Kubernetes managedFields to answer "which session changed prod at 14:05".
I9: Agents work on remote hosts through `ssh host '...'` strings or heredocs, so hooks see one opaque command. There is no per-host policy, no host-side record of what the agent ran, and a shell loop can change the whole fleet at once. || Fleet exec MCP server: a hook blocks raw ssh/scp. Agents call `run(selector, cmd)`, where the selector matches inventory tags (env, role). The impact-gate policy applies per host class. Commands run through a dedicated agent key. Its authorized_keys forced command logs SSH_ORIGINAL_COMMAND and the session ID (passed via SendEnv) to journald, then runs the command. A mutating command aimed at several hosts runs on one host first, then a declared health check, then growing batches, stopping at the first failure.
I10: Each new session rediscovers the same environment facts (which cluster is in which account, bastion routes, naming conventions), wasting tokens and time. Meanwhile, hand-written MEMORY.md/CLAUDE.md facts go stale and confidently mislead agents about the current infrastructure. || Verified fact store (MCP server): each fact has text, scope tags and a `verify` command with a hash of its expected output (e.g. `aws eks describe-cluster --name prod-eu --query cluster.version`). After each session, a job scans transcripts for read-only lookup commands repeated across sessions and proposes facts from their outputs for one-click acceptance. A scheduled job re-runs the verify commands and marks a fact stale when its output changes. Agents query by topic and get fresh facts, with warnings on stale ones. CLAUDE.md keeps only a pointer to the store.
