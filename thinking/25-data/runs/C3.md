## P1
Solution: Identity-alias egress proxy — A local intercepting proxy (mitmproxy addon) that every outbound request from the agent's process tree must pass. A launcher wrapper (or the settings env block) sets HTTPS_PROXY/HTTP_PROXY and adds the proxy CA via NODE_EXTRA_CA_CERTS, SSL_CERT_FILE, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE and GIT_SSL_CAINFO, so the harness, WebFetch, subagents and scripts Claude writes all inherit it (loopback exempt via NO_PROXY); a per-user firewall rule (nftables/pf) or container network makes it unavoidable, and certificate-pinning tools fail closed. Model-API traffic is tunnelled untouched. For every other host, the addon scans URL, headers and body for the user's identifiers (account email, name, phone) in plain, URL-encoded, base64, JSON-escaped and case-folded forms, and rewrites matches to a per-site relay alias, so sites like sec.gov that demand a contact address still work; block-listed hosts get 403. Every rewrite is logged.
Differs from existing: Checks the bytes that actually leave, not tool-call text: covers scripts Claude writes, subagents and encoded forms; local-only commands never reach it, so no heredoc/127.0.0.1 false positives; unaffected by managed-settings hook limits; tasks needing an address keep working. Measurable: leaks and false denials on a route test-suite.
Needs: mitmproxy or similar, CA trust via env vars, OS firewall or container, a mail-relay alias. VENDOR: removing the email from the system prompt (and model-written commits).

## P2
Solution: Permission conformance harness — A test runner that checks what the installed agent actually enforces against the rules the engineer wrote. It launches the real CLI (Claude Code with ANTHROPIC_BASE_URL, Codex with a custom model_providers base_url) against a local mock model server that answers with scripted tool calls and forwards anything unscripted, such as auto-mode classifier calls, to the real API. Cases are generated from the user's own rule files: each allow/deny rule expands into variants (compound with cd, git -C and other global flags, quoted flags, bash -c/env wrappers, inside a subagent or skill, in a fresh untrusted project, under bypass/yolo). The observed outcome (ran, prompted, denied) comes from hook logs and a pty watcher, giving a per-version mismatch table. It runs in CI on each agent release and before the local auto-updater moves; the last conforming version stays pinned, and fixable mismatches get generated PermissionRequest-hook rules.
Differs from existing: Dippy, tool-gate and auto-approve hooks replace the matcher with another unverified one; this verifies whichever matcher is enforcing (built-in, hook, auto mode), catches regressions before unattended runs stall, and doubles as a bypass test for community hooks. Measurable: mismatches per release, prompt-stalls per unattended run.
Needs: Configurable model endpoint (exists in Claude Code, Codex), hooks, version pinning, CI. VENDOR: fixing mismatches hooks cannot override (ExitPlanMode, quoted-flag warning, trust prompts).

## P3
Solution: Tracker-to-runner dispatcher — Delegation runs on the CI runners the organization already operates inside its network. Assigning a ticket to an 'agent' user in Jira, Azure Boards, Linear, GitLab or Bitbucket fires the tracker's own automation or webhook (Jira Automation 'send web request', Azure DevOps service hook, Linear webhook through a small relay) at the CI's trigger API (Azure Pipelines, Bitbucket Pipelines, Jenkins, GitLab trigger token). A reusable pipeline template fetches the ticket (description, comments, linked items) over the tracker API, runs Claude Code or Codex headless with a pinned permission profile, pushes a branch, opens the MR/PR through the forge API and comments the link and summary on the ticket. Review comments that mention the agent retrigger the pipeline, which restores the saved session from a pipeline artifact and resumes it, so iteration continues in the MR. One thin adapter per forge and tracker.
Differs from existing: Generalizes the GitLab-only CI/CD pattern to any forge and tracker, with ticket-assignment start and session resume; needs no vendor integration, paid tier, feature flag or GitHub link, reaching Bitbucket Data Center and Azure DevOps Server behind firewalls; no new host, unlike Cyrus. Measurable: forges covered, assignment-to-MR time.
Needs: CI runners with repo write and model-API egress, tracker automation or a webhook relay, agent API key. VENDOR: interactive cloud sessions on these forges.

## P4
Solution: Session-log watchdog — A small daemon that tails the timestamped session logs agents already write (Claude Code ~/.claude/projects/*.jsonl, Codex ~/.codex/sessions rollouts) with inotify/FSEvents and derives state without relying on hooks: finished (final assistant entry followed by a configurable quiet period, which filters /goal continuations), waiting for approval (a tool call with no result while the agent has no live child process), errored (API-error entries, or silence after an unfinished turn, neither of which fires a hook), stalled (no entry for N minutes). Each transition is pushed once (deduplicated) via ntfy or Pushover with task duration and the last message. It runs where the agent runs, so Remote SSH and IDE-extension sessions are covered. The same parser powers a Claude Code statusline script (it receives transcript_path) showing last-prompt time, last background check and idle time, and a `when` command listing turns with timestamps.
Differs from existing: Hook notifiers only see events the harness chooses to fire, and break when it doesn't; the log records everything, so API-error stops, approval waits and idle timeouts are caught and /goal false 'done' filtered, with no subscription, IDE patch or Remote Control. Measurable: missed/false alerts on scripted scenarios, alert latency.
Needs: Read access to local session logs (undocumented formats; per-version adapters), a push service, statusline support. VENDOR: timestamps inside the conversation view.

## P5
Solution: Effect-based Bash supervision — Instead of policing which command the agent uses, supervise what it changes. A PreToolUse hook on Bash snapshots the project tree into a shadow git repository (separate GIT_DIR, stat-cached, untracked files included); a PostToolUse hook diffs against it. Every changed path then gets what file tools get: (1) checked against Edit/Write deny rules and path-scoped rules, with violations restored from the snapshot and a block reason returned to the agent; (2) the diff shown in hook output and a side log; (3) a checkpoint recorded so `bash-rewind` can restore any earlier step; (4) if the path falls under a nested CLAUDE.md or path rule not yet in context, its text returned as PostToolUse additionalContext. Writes outside the project are confined by the OS sandbox write allowlist, and reads by its read-deny list, since reads leave no effect to inspect.
Differs from existing: Pattern-based blocking and bridge hooks guess intent from command text, miss python and scripts, and fight the Bash-first prompt, wasting turns; this keys on the effect, so every route is covered and nothing is blocked up front. Measurable: share of Bash file changes diffed, rule-checked and rewindable on a route test-suite.
Needs: PreToolUse/PostToolUse hooks, git, the OS sandbox for reads and out-of-tree writes. VENDOR: native /rewind integration and removing the Bash-first steering.

## P6
Solution: Repo-attested credential broker — A small self-hosted broker (serverless function or container) hands short-lived, scoped credentials to cloud sessions, which prove who they are with something they already have: the vendor's GitHub proxy. A helper CLI gets a nonce from the broker and writes it to GitHub through the proxy (a ref push or an issue comment in an attestation repo); the broker confirms via the GitHub API that the expected user or app wrote it, deletes it, and issues what the repo/branch policy allows: cloud tokens via STS or workload identity federation, Vault dynamic database users, short-lived SSH certificates, private-registry tokens, and broker-signed requests for S3-compatible stores like R2. Credentials live 15–60 minutes and go into the process env, .npmrc or pgpass; re-running the helper rotates or adds secrets mid-session. Where network secrets work, a bearer token for the broker host replaces the GitHub step.
Differs from existing: Network secrets only add HTTP headers for listed hosts; this delivers any credential type (databases, SSH, registries, keyless cloud, R2), reloads mid-session, and needs no network-secret support (Team, CMEK). Secrets do enter the VM, but short-lived and scoped. Measurable: blocked use-cases that run, exposed credential lifetime.
Needs: GitHub write through the vendor proxy (exists; verify it permits the attestation write and is reachable from setup scripts), cloud IAM federation or Vault. VENDOR: native OIDC tokens.

## P7
Solution: Agent-authored change sets with a dependency-aware CI gate — An MCP tool/skill (`open_changeset`) the agent calls at the end of a multi-repo session: it opens one PR per repo and writes a shared manifest (member PRs, producer→consumer order, per-repo policy) into every PR description, cross-linking them. A reusable CI check in each repo reads the manifest and (1) builds and tests consumers against the producer's PR branch by temporarily overriding the dependency to that git ref (pnpm/npm overrides, go replace, pip git+, Cargo [patch]), so contract changes are tested together before merge; (2) keeps a consumer red until its producers are merged and released, then bumps the pin and re-runs; (3) enforces the target repo's own policy (draft-only, required owners). `changeset checkout <id>` recreates the whole workspace at those branches locally for review or continued work.
Differs from existing: Multi-repo sessions emit unrelated PRs; Zuul-style Depends-On gating needs dedicated infrastructure and humans writing the links. Here the session that knows the dependency graph records it and each repo's existing CI enforces it. Measurable: manual coordination steps, consumer PRs tested against producer changes before merge.
Needs: Per-repo CI, package managers with git-ref overrides, forge API tokens. VENDOR: teleporting the multi-repo session itself and a single change-set review view.

## P8
Solution: Wake-and-resume scheduler — A watcher on the session logs (or a Stop hook) notices a usage-limit stop and records session ID, working directory and reset time, parsed from the limit entry; if parsing fails it falls back to probing with a one-token headless call every 15 minutes, so format changes or starting already over the limit are harmless. It registers an OS job for the reset, however many days away: launchd plus pmset wake, a systemd timer with WakeSystem=true, or Task Scheduler 'wake to run'. The job resumes headless, `claude -p --resume <id>` or `codex exec resume <id>`, with 'Continue the interrupted task; check git status first', under the permission profile saved when the task started (allowed tools, sandbox, deny instead of ask) and an optional fallback model for model-specific weekly limits, so nothing waits on a prompt. It re-arms without a cap and pushes the result to the phone.
Differs from existing: Built-in auto-continue needs a live interactive terminal, skips -p/background, Remote Control and resets beyond 24h, caps re-arms and stalls on prompts; wrappers die with the terminal or on format changes. OS wake jobs plus session-ID resume survive all of these. Measurable: resume success rate, reset-to-resume delay.
Needs: Headless resume by session ID (exists in Claude Code and Codex CLI), an OS scheduler with wake, machine on power. VENDOR: auto-resuming Codex App /goal threads.

## P9
Solution: Completion-gated queue file — The queue is a plain file (.agent/queue.md: one task per item, optional `check:` command, optional `fresh`), appended from any editor, a `q add` CLI or a synced folder while the agent works, so nothing goes through the chat box to be folded into the running turn, merged or lost. A Stop hook runs at each turn end and hands over the next item only if the agent's last message carries a [DONE] marker (requested in every prompt by a UserPromptSubmit hook) and the previous item's check command (e.g., tests) passes; it then returns decision=block with the next task as the reason, so it begins only after the previous one ended. A question, [BLOCKED] or a failed check pauses the queue and sends a notification. Items are stamped done with times; `fresh` items run as a new headless session to keep context small.
Differs from existing: Native queues fold messages into the running turn, merge, interrupt (VS Code, Desktop) or drop them; claudeq and cmux hand over at any turn end, even over an open question or failure. This hands over only on verified completion, from any surface running hooks. Measurable: handoffs onto unfinished or failing work.
Needs: Stop and UserPromptSubmit hooks on the surface in use (CLI, IDE extension, Desktop where settings hooks run), a notifier. VENDOR: a native hold-until-turn-end queue.
