## P1
Solution: Alias-rewriting identity gateway — a local MITM proxy started by a launcher (`idguard claude`) that sets HTTPS_PROXY, NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE and runs the agent in a network namespace (Linux) or sandbox profile (macOS) where only the proxy is reachable, so agent-written scripts and subagents cannot bypass it. Model leg: on model-API requests it replaces the account email and name in the system prompt with a forwarding alias, so the model never learns the real address. Egress leg: every other request's URL, headers and body are normalized (percent-, base64-, quoted-printable-decoded, lowercased) and scanned for the identity set; hits are rewritten to a per-domain alias (minted via SimpleLogin or addy.io API) or blocked, per policy. Loopback and private ranges pass uninspected. A commit-msg hook catches the real address in commits. Per-domain aliases reveal which site leaked. Metric: leaks and false denials on a scripted/encoded/subagent/loopback test corpus.
Differs from existing: Existing guards match strings at the tool-call layer, so agent-written scripts, subagents and encodings slip past while local calls get denied. This inspects the bytes actually leaving, skips local traffic, keeps tasks working with aliases, and strips the email from context without the prompt.context hooks Team/Enterprise block.
Needs: Harness honouring HTTPS_PROXY and an extra CA (documented for corporate proxies); OS sandbox or network namespace; an alias service; admin consent under managed settings. No vendor change.

## P2
Solution: Permission conformance gate — one effect-level policy file (read/write paths, hosts, commands as normalized argv with global flags like `git -C` and leading `cd` folded into context) compiled to each harness's native rules (Claude settings, Codex rules, Gemini policy TOML) plus one shared PreToolUse/PermissionRequest decider hook, which fires inside subagents and skills too, so deny always wins regardless of native matching. A shadow log correlates PreToolUse, PermissionRequest and PostToolUse events into {command, policy verdict, actual outcome: ran/prompted/denied}. In CI, a corpus of ~200 tricky forms (cd chains, quoted flags, heredocs, subagent and skill calls) is replayed against each new harness release in a container via headless runs told to execute each command verbatim; the report lists divergences. The team's pinned harness version advances only when divergences are zero or covered by the hook. Known vendor gaps are reported, not hidden.
Differs from existing: Dippy-style hooks and auto mode also decide, but nobody checks what the installed release actually enforces. This measures it: divergence count per release, and blocks upgrades that regress (like after v2.1.77/v2.1.199). One policy covers three harnesses and subagents, not per-tool rule dialects.
Needs: Hooks in Claude Code, Codex and Gemini CLI; headless mode; version pinning. Vendor: ExitPlanMode hook-allow, Remote Control mobile prompts and Codex per-project trust need vendor fixes.

## P3
Solution: Forge-native agent runner — a container image (Claude Code or Codex CLI, headless) plus pipeline templates for GitLab CI (any tier), Bitbucket Pipelines, Azure Pipelines and Jenkins (for Bitbucket Data Center), and a webhook relay. Assigning an issue to an agent user in Linear (Agents API), Jira (Automation webhook), Azure Boards (service hook) or GitLab, or an `@agent` comment on an MR, makes the relay start the pipeline with the ticket text and links. The job pushes a branch and opens the MR with a repo-scoped bot token held as a masked CI variable, through a Renovate-style platform adapter. The session transcript is cached as an artifact keyed by MR, so each later MR comment starts a job that runs `--resume`, continues the same session and replies in the thread. Code stays on the org's forge and runners except for model-API calls. Metric: forge/tier combinations covered, ticket-to-MR time.
Differs from existing: Unlike Cursor, GitLab Duo and Linear sessions, it needs no GitHub, no Premium tier or feature flag and no beta integration, and covers Bitbucket Data Center and Azure DevOps Server. Unlike GitLab's `@claude` CI, it starts from any tracker or forge and resumes one session per MR.
Needs: CI runners with outbound access to the model API; an API key or Bedrock/Vertex account; a webhook relay host. Vendor: only for native claude.ai/code or Codex web support.

## P4
Solution: Transcript-and-process watchdog — a daemon on the machine where the agent runs (including a Remote SSH host) that tails session transcripts (~/.claude/projects/*.jsonl, ~/.codex/sessions rollouts) and watches the agent's process tree. It infers each session's state: working (new entries or a live child process), waiting for approval (pending tool call, no child process, no writes for 3 s), turn ended (debounced, so /goal continuations do not alert), API error, crashed (pid gone) or stalled (mid-turn, silent for N minutes). Only transitions are sent, deduplicated and batched across sessions, as a desktop toast and ntfy/Pushover push, escalating if unanswered after a configurable delay. Hook events serve as extra signals, not the only one. Entry timestamps feed a statusline segment and a `timeline` command showing when each instruction was given and each background check last ran. Metric: missed and false alerts under injected crashes, API errors and approval waits.
Differs from existing: Existing notifiers wait for the harness to fire the right hook, so API errors, crashes, hooks broken by updates and Codex approvals stay silent. This infers state from transcripts and processes, alerts on silence itself, works over Remote SSH and in any IDE, and adds timestamps without UI patches.
Needs: Readable transcript files (format undocumented, so per-version parsers); process inspection; ntfy or Pushover. Optional vendor: a documented session-state stream would remove parser upkeep.

## P5
Solution: Effect-based file supervision — observe what shell commands change instead of blocking them. A PreToolUse(Bash) hook snapshots the working tree into a shadow git repository (separate GIT_DIR, worktree = project, watchman fsmonitor); a PostToolUse(Bash) hook snapshots again and diffs. Then: (1) writes to paths covered by Edit/Write deny rules are restored from the pre-snapshot and the agent is told why; (2) the diff is shown like an Edit diff and logged per tool call; (3) every tool call becomes a shadow commit, so `rewind N` restores Bash and Edit changes alike; (4) nested CLAUDE.md and path-scoped rules for touched directories are returned as PostToolUse additionalContext. On Linux, fanotify attributes changes to the Bash process tree so concurrent human edits are not misattributed. Reads stay with the OS sandbox, which can block them beforehand. Metric: share of writes captured across sed, python, tee and heredoc routes.
Differs from existing: Pattern hooks and Bash deny rules must recognise each command, so python one-liners, heredocs and tee route around them, and the harness's own Bash-first steering fights them. This needs no recognition: every write by any route is diffed, policed, rewindable and gets path rules, without deny-and-retry loops.
Needs: PreToolUse/PostToolUse hooks with additionalContext; git, watchman; fanotify on Linux (macOS FSEvents gives coarser attribution). Vendor: only to merge into the built-in /rewind UI.

## P6
Solution: Bootstrap-secret credential broker — the vendor's network secret is used for one self-hosted host only: a broker token stored for broker.example.com, which the agent proxy attaches after requests leave the VM, so nothing secret enters the session. The broker holds the real credentials (Vault or 1Password backed) and offers: an HTTP reverse proxy that signs with any scheme (SigV4 for R2, HMAC, mTLS); TCP tunnels over WebSocket for Postgres and Redis, where a session-side client opens 127.0.0.1 ports and the broker authenticates upstream; a private package-registry mirror on its own host; and, where a credential must be local, per-session short-lived tokens (STS, GitHub App, 5-minute SSH certificates). Policy (read-only roles, path allowlists) and rotation change at the broker and apply at once to running sessions, with per-session audit. Without network secrets (CMEK, Team gaps, self-hosted), sessions pair through a device-code approval on the engineer's phone.
Differs from existing: Vendor network secrets cover only HTTP headers on listed hosts, never registries or non-HTTP uses, and cannot reload; postern and mcp-warden are local-only. One network secret as bootstrap gives databases, S3-compatible stores and private packages live, never-in-VM access. Metric: credential kinds served without secrets in the VM.
Needs: Vendor network secret on one custom host, passing WebSocket upgrades; broker reachable through the session allowlist. Vendor: Team-account parity; session OIDC tokens would replace the bootstrap.

## P7
Solution: Change-set gate for multi-repo PRs — a GitHub App/Action (GitLab variant uses native MR dependencies) built on Zuul's `Depends-On:` convention. A skill plus a Stop hook make any agent (Claude multi-repo sessions or Projects, Cursor, Codex) add the same `Change-Set: <id>` and `Depends-On: <PR URLs>` footer to every PR it opens, refusing to finish while one lacks it. The App then: runs each repo's existing CI via workflow_dispatch with the sibling PRs' branches as dependency overrides, so consumers test against the unmerged provider; posts one set status on every PR ("2/3 approved; merge order lib → api → web"); keeps dependents' required check failing until dependencies merge; optionally merges the set in order once all are approved, reverting on failure. An org manifest sets per-repo push policy (PR-only or direct-push branches), applied as rulesets. `cs checkout <id>` fetches every branch of the set into a local multi-repo workspace.
Differs from existing: Today multi-repo sessions yield independent PRs with no linkage, order or joint testing; Zuul does this but requires replacing CI with its own infrastructure. This reuses existing per-repo CI and branch protection, and the agent writes the dependency metadata at zero human cost. Metric: out-of-order merge breakages.
Needs: GitHub App with checks/contents permissions; per-repo CI that accepts dependency-ref inputs; agent hooks or instructions. Vendor: multi-repo session teleport and native linked-PR display.

## P8
Solution: Reset-aware run supervisor — a launchd/systemd user service that owns delegated runs (`agentd run "<task>"` starts `claude -p` or `codex exec` in a detached tmux pane and records the session id). Reset times are read from structured sources, not screen text: rate-limit response headers seen by a local proxy, or Codex rollout `rate_limits` events. At ~90% usage a PostToolUse hook tells the agent to commit work-in-progress and update HANDOFF.md, so the cutoff lands on a clean checkpoint. When the run stops on the limit, the service schedules the resume for reset plus jitter, any distance away (weekly included), sets an RTC wake (`pmset schedule wake` / `rtcwake`), then runs `--resume <id> "Continue from HANDOFF.md"` headless under a pre-declared permission policy so no prompt can stall it. Model-specific limits trigger a configured fallback model. Every interruption and resume is logged and pushed.
Differs from existing: Built-in auto-continue excludes -p, background, weekly and Remote Control sessions, dies with the terminal or sleep and still stalls on prompts; wrappers scrape changing limit messages. This survives sleep and closed terminals, reads machine-readable reset data, checkpoints before cutoff and resumes prompt-free. Metric: unattended resumes per interruption.
Needs: Headless resume by session id; rate-limit headers or rollout events (undocumented); admin rights for wake scheduling. Optional vendor: a documented usage/reset field for subscriptions.

## P9
Solution: Gated file queue — the queue is a plain file in the repo (`.agent/queue.md`, one checkbox item per task, optional `check:` command and `context: same|fresh`), editable in any editor or via `q add`. A Stop hook adapter for each harness (Claude Code Stop, Codex Stop, Gemini AfterAgent) runs at the true end of a turn: if the current item has a check, it runs it and, on failure, blocks the stop with the output so the agent keeps working on the same task (capped retries); on success it ticks the item with timestamp and commit SHA, then delivers the next item as the block reason, one item per turn. `fresh` items instead start a new headless session seeded with a generated handoff summary. Because delivery happens in the harness core, it behaves the same in CLI, VS Code, Desktop and remote sessions, and survives crashes and limit pauses.
Differs from existing: Native queues fold, merge, drop or interrupt depending on surface; claudeq and cmux queues are single-harness or macOS-only. This advances only when the previous task's check passes, one item per turn, persists outside the UI, and spans three harnesses. Metric: lost or merged items per 100 queued.
Needs: Stop/AfterAgent hooks that can block with a reason; headless mode for fresh items. No vendor change; a native hold-until-turn-end option would still help typed messages.
