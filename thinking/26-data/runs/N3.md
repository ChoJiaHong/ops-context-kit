## P1
Solution: Alias-and-canary egress layer — Two local proxies outside the harness. (1) A model-API proxy (ANTHROPIC_BASE_URL) rewrites the account email in every outgoing model request to a per-machine alias such as `dev-7f3a@alias.invalid`, so the model, sub-agents, scripts and commits only ever know the alias. (2) A TLS-intercepting egress proxy (HTTPS_PROXY, local CA exported via NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE; a firewall rule lets only the proxy reach the internet, so agent-written scripts cannot bypass it) decodes URLs, headers and bodies (percent, base64, punycode, JSON escapes) and strips or blocks the real email, the alias and listed PII toward non-allowlisted hosts. Loopback traffic never passes through it. Every alias hit is logged with destination, making leaks a measurable count; a regression suite of exfiltration routes (curl, python, node, sub-agent, encoded headers) must score zero.
Differs from existing: Hooks and the built-in check match tool-call strings (email plus a network word); this inspects decoded bytes on the wire and the model's input, so it covers agent-written scripts, sub-agents and encodings, gives no loopback false positives, and works on Team/Enterprise logins where prompt.context mods are skipped.
Needs: Harness honouring ANTHROPIC_BASE_URL and HTTPS_PROXY (if managed settings lock them: vendor); OS firewall rights; tools trusting the local CA. Removing the email at source needs the vendor.

## P2
Solution: Permission conformance suite — The engineer writes intent as a table: tool call, context (main agent, subagent, skill, headless, bypass mode, fresh project) and expected outcome (run, ask, deny). A runner starts the real harness binary (Claude Code, Codex, Gemini CLI) in a throwaway container with the engineer's actual settings, pointed at a stub model server (ANTHROPIC_BASE_URL or OPENAI_BASE_URL) that returns the table's tool calls as scripted responses, and drives the interactive UI through a pty. A canary side effect plus the transcript show whether each call ran, prompted or was refused; every row where enforcement differs from intent is reported. For failing rows only, it generates a minimal PreToolUse shim and re-runs the suite to prove it. CI runs the suite on every harness release; auto-update stays off and a new version is promoted only when green. Metric: mismatched rows per release.
Differs from existing: Dippy, tool-gate-hook and auto-approve hooks add another unreviewed matcher; /permissions lists rules, not behaviour. This tests what the shipped binary actually enforces, end to end across subagents, skills and modes, catches release regressions before engineers hit them, and limits hooks to proven gaps.
Needs: Harnesses accepting a custom model endpoint; a container runner. Prompts no hook can override (ExitPlanMode, Remote Control mobile, Codex trust) are detected, but fixing them needs the vendor.

## P3
Solution: Shadow-mirror forge bridge — A small self-hosted service connects any git forge (GitLab, Bitbucket Cloud or Data Center, Azure DevOps, Gerrit) and tracker (Linear, Jira, Azure Boards) to the vendors' GitHub-only cloud sessions. It keeps a private GitHub mirror of each repo, synced from the origin on every push webhook; mirror main is protected and the agent may push only agent branches. Assigning a ticket or mentioning the agent's service account starts a cloud session on the mirror through the vendor CLI (for example `claude --cloud`) with a prompt built from the ticket, its comments and linked MRs. When the agent pushes, the bridge pushes the branch to the origin, opens the MR there linked to the ticket, relays origin review comments into a follow-up session on the same branch, updates ticket status, and deletes mirror branches after merge. Metric: manual steps per delegated ticket (target zero).
Differs from existing: Native options are per forge, beta or tier-gated (GitLab Premium/Ultimate, Cursor beta, no Bitbucket Data Center), or require GitHub outright. One adapter layer reuses the cloud sessions teams already pay for on any git forge and removes manual context copying, branch handling and MR creation.
Needs: A private GitHub org with the vendor's app; policy allowing code on GitHub (otherwise run the adapters with a self-hosted runner); forge and tracker tokens. Native support needs the vendor.

## P4
Solution: Transcript-watching attention daemon — A per-machine daemon tails the harness's append-only session logs (Claude Code project JSONL, Codex rollout files) instead of depending on hooks. A state machine classifies each session: working, awaiting approval (pending tool call with no child process running), awaiting reply, finished, API error, or stalled (no new entry for a configurable N minutes outside a terminal state). It alerts only on transitions, deduplicated; "finished" fires after a short grace period with no new turn, suppressing false alerts on /goal continuations. Alerts escalate by attention: nothing if the session's terminal or IDE is focused, a desktop toast otherwise, a phone push via ntfy if unanswered after M minutes. Log timestamps feed a timeline command and status line showing when each instruction, tool call and background check happened. Metric: missed or false alerts per 100 turns.
Differs from existing: Hook-based notifiers depend on events that fail to fire (API-error endings, Codex approvals, hooks broken by updates), false-fire on continuations, lag ~10 s, and break over Remote SSH. Reading the durable log on the agent's machine detects silence and error states directly and provides the missing timestamps.
Needs: Log formats are undocumented and change, so per-harness parsers need version tests; ntfy or similar push; per-OS focus detection. A documented session-event stream would need the vendor.

## P5
Solution: Effect-based file supervision — Instead of guessing from command text, capture what each shell command actually changed. A Bash PreToolUse hook snapshots the working tree into a private git ref using a temporary index (`GIT_INDEX_FILE`, `git add -A`, `git write-tree`; incremental through the stat cache). The PostToolUse hook snapshots again and diffs the two trees, so sed, heredoc, python and node writes look identical. Each changed path is checked against the Edit/Write rules: denied paths are restored from the pre-snapshot; ask paths are restored and the agent is told to redo them with Edit, which raises the normal prompt. Allowed changes are shown as a diff, the nested CLAUDE.md and path-scoped rules for touched paths are returned as additionalContext, and snapshots chain into checkpoints that `agent-rewind` restores. Read deny rules are compiled into the OS sandbox's filesystem deny list. Metric: write routes caught out of a test corpus.
Differs from existing: Blocking hooks match command names, so python or heredocs route around them, and every blocked call wastes a turn. Diffing filesystem state catches every in-tree write whatever the tool, restoring rules, diff display, nested context and rewind, and coexists with the harness's Bash-first steering instead of fighting it.
Needs: Bash Pre/PostToolUse hooks; a git working tree (ignored or out-of-tree writes need the sandbox); concurrent human edits get attributed to the agent. Native /rewind integration needs the vendor.

## P6
Solution: Network-secret-bootstrapped credential broker — Store exactly one network secret: a bearer token for a broker host you run (a small service fronting Vault and cloud IAM). The vendor proxy attaches it outside the VM, so the session reaches the broker without ever holding a long-lived secret. A CLI in the session (`cred get db-staging`, also from a SessionStart hook) asks the broker for short-lived, scoped credentials: STS sessions, cloud access tokens, Vault dynamic database users, expiring private-registry tokens. For R2 and other S3-compatible stores the broker acts as a SigV4 signing proxy. Broker policy limits roles and lifetimes, logs every issue and can demand phone approval; databases are tunnelled over HTTPS if raw TCP is blocked. Credentials are fetched on demand, so rotation needs no session reload. Where network secrets are unavailable (Team gap, CMEK), the CLI falls back to an OAuth device-code flow the engineer approves.
Differs from existing: Network secrets only add HTTP headers for listed hosts; postern and mcp-warden are local-only. Using that one supported injection as the identity for a user-owned broker approximates OIDC: databases, registries, R2, cloud IAM and mid-session rotation work, and any secret's lifetime in the VM drops from indefinite to minutes.
Needs: Network secrets on the account (else an engineer approves device flows); a hosted broker allowed in the environment's network policy. Setup-script access and native OIDC tokens need the vendor.

## P7
Solution: Agent-written change sets with a cross-repo gate — One session makes every change, so the agent can record the dependency graph at no cost. A skill, enforced by a PreToolUse hook on `gh pr create`, adds footers to each PR (`Changeset: cs-142`, `Depends-On: org/api#45`) and writes a manifest (members, merge order, per-repo push policy) to a changeset index repo. A GitHub App then (1) runs each member's CI against sibling repos checked out at the sibling PR heads, so contract tests exercise the combined change; (2) posts one required status, "changeset complete", blocking every member until all are green and approved; (3) merges in dependency order, halting and opening revert PRs if a later merge fails; (4) serves one combined review diff. CI failures are posted back, and the session, which has every repo attached, fixes them together. Metric: broken-main incidents from out-of-order merges.
Differs from existing: Multi-repo sessions and Projects emit independent PRs; mars and nemus focus on local workspaces. This adds Zuul-style Depends-On testing and ordered merging without operating Zuul, fed by metadata the agent already has, so the set is tested, reviewed and merged as one unit.
Needs: A GitHub App and a CI step in each repo; a token to check out siblings; the agent following the skill (the hook enforces footers). Multi-repo teleport needs the vendor.

## P8
Solution: Wake-scheduled resume jobs — The OS, not a live process, does the waiting. A pass-through ANTHROPIC_BASE_URL proxy (for Codex, a rollout-log watcher) detects the limit from the structured 429 and its reset header, never display text, and falls back to hourly probes if no reset time is given. It writes a durable job {harness, session ID, cwd, reset time, continuation prompt} and registers a wake-capable timer: launchd plus `pmset schedule wake`, a systemd timer with `WakeSystem=true`, or Task Scheduler's "wake the computer". At reset plus jitter it runs `claude -p --resume <id>` or `codex exec resume <id>` with an unattended permission profile, so prompts become logged denials rather than stalls. Another limit re-schedules, with no 24-hour or re-arm cap. Near the limit, a PostToolUse hook reading the proxy's utilization figure asks the agent to commit WIP with a progress note. Metric: idle minutes between reset and resume.
Differs from existing: Built-in auto-continue needs a live interactive terminal, skips -p, background and weekly resets, and re-arms twice; wrappers parse changing output and die when the terminal closes or the laptop sleeps; Codex has no native resume. OS wake timers plus resume-by-ID survive all of these.
Needs: Headless resume-by-ID; a machine that wakes or stays on; a proxy-able model endpoint (else log parsing). Resuming Desktop or Remote Control sessions in place needs the vendor.

## P9
Solution: Check-gated file queue — The queue is a file in the repo (`.agent/queue.md`), one task per item, each with an optional acceptance command, a `fresh` flag and dependencies. Engineers add tasks with `q add` or by editing the file, never through the chat box, so no UI can interrupt the running task or fold the message into it. A Stop hook dequeues: when a turn ends it runs the current task's acceptance command; on failure it blocks the stop and feeds the output back (bounded retries), then halts and notifies; on success it marks the task done with a timestamp and returns the next task as the block reason, so each task begins only after the previous one has ended and passed. `fresh` tasks start a new headless session instead. The same hook behaves identically in CLI, VS Code and Desktop. Metric: tasks completed per unattended hour.
Differs from existing: Built-in queues fold messages into the running turn, interrupt in VS Code or lose input on Desktop; claudeq and cmux-claude-queue deliver in order without checking outcomes. Here the next task waits for a passing check, failures stop the chain, and delivery avoids every UI queue path.
Needs: A Stop hook that can block and inject a reason, honoured on each surface (Claude Code; Codex where supported); engineer-written acceptance commands. A native end-of-turn queue needs the vendor.
