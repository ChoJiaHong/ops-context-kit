# Solutions (anonymous; random order within each problem)

## P1

### S01
Solution: Alias-swap gateway — the agent is launched through a wrapper that points ANTHROPIC_BASE_URL at a local model gateway and HTTPS_PROXY (with a local CA) at a local egress proxy. The gateway rewrites every occurrence of the account email in outbound model requests (system prompt, tool results) to a revocable forwarding alias the engineer chose (e.g., a masked-email address), so the model, subagents and scripts it writes only ever know the alias. The egress proxy inspects non-vendor traffic after decoding (headers, URLs, bodies, including URL-encoded, base64 and hex forms of the real email) and substitutes the alias instead of blocking; loopback and file-only commands never reach it, so they cannot be false-denied. A SessionStart note tells the model to use the alias whenever a site demands a contact email (e.g., sec.gov User-Agent). Spam reaching the alias identifies the leak and the alias can be killed.
Differs from existing: Removes the email at its source, including on managed-settings logins where context mods are skipped, and judges wire bytes, not command text, so self-written scripts, subagents and encodings are covered without blocking tasks. Measure: real-email egress hits over a leak-route corpus = 0; local false denies = 0.
Needs: Agent honoring ANTHROPIC_BASE_URL and HTTPS_PROXY with a trusted local CA, user control of launch env, a forwarding-alias service. A supported opt-out would make the gateway rewrite unnecessary (vendor).

### S02
Solution: Identity-blind egress proxy — Run the agent and every child process in a container or network namespace whose only route out is a local mitmproxy-based proxy (HTTPS_PROXY plus NODE_EXTRA_CA_CERTS/SSL_CERT_FILE; nftables drops direct egress). On requests to the model API it rewrites the body, replacing the account email in the system prompt and context with a fixed alias (dev@example.invalid), so the model never learns the address and cannot put it in headers, scripts or commits. On every other request it scans URL, headers and body for the email and its variants (case, %40, base64, JSON/quoted-printable escapes, "at") plus a user PII list, then rewrites or blocks with a logged notice. Loopback and Unix-socket traffic bypass the proxy, so local calls are never denied. One config covers Claude Code, Codex and Gemini CLI.
Differs from existing: It acts on real traffic, not tool-call text, so scripts Claude writes, subagents and encoded forms are covered; it hides the email from the model without prompt.context hooks, so it works on Team/Enterprise and managed machines; loopback bypass removes the false positives; no vendor release needed.
Needs: A container or namespace for the agent and a trusted local CA. Nothing from the vendor, unless it adds certificate pinning; vendor-side fetches are protected only by the alias.

### S03
Solution: Alias-rewriting identity gateway — a local MITM proxy started by a launcher (`idguard claude`) that sets HTTPS_PROXY, NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE and runs the agent in a network namespace (Linux) or sandbox profile (macOS) where only the proxy is reachable, so agent-written scripts and subagents cannot bypass it. Model leg: on model-API requests it replaces the account email and name in the system prompt with a forwarding alias, so the model never learns the real address. Egress leg: every other request's URL, headers and body are normalized (percent-, base64-, quoted-printable-decoded, lowercased) and scanned for the identity set; hits are rewritten to a per-domain alias (minted via SimpleLogin or addy.io API) or blocked, per policy. Loopback and private ranges pass uninspected. A commit-msg hook catches the real address in commits. Per-domain aliases reveal which site leaked. Metric: leaks and false denials on a scripted/encoded/subagent/loopback test corpus.
Differs from existing: Existing guards match strings at the tool-call layer, so agent-written scripts, subagents and encodings slip past while local calls get denied. This inspects the bytes actually leaving, skips local traffic, keeps tasks working with aliases, and strips the email from context without the prompt.context hooks Team/Enterprise block.
Needs: Harness honouring HTTPS_PROXY and an extra CA (documented for corporate proxies); OS sandbox or network namespace; an alias service; admin consent under managed settings. No vendor change.

### S04
Solution: Identity-scrubbing egress proxy — A local TLS-intercepting proxy (mitmproxy addon) that the harness and every child process use via HTTPS_PROXY plus a local CA (NODE_EXTRA_CA_CERTS, SSL_CERT_FILE); a network namespace or firewall rule allows egress only through the proxy, so agent-written scripts that ignore proxy variables cannot bypass it. Two rules: (1) on requests to the model API, replace the account email in the system prompt with a fixed pseudonym, so the model never learns the address and cannot place it in headers, scripts or commits; (2) on all other egress, match the user's known identity strings (email, name, git email) in URL, headers and body across precomputed encodings (URL, base64, hex, JSON-escaped, case variants), then rewrite or block and log. Decisions use the real destination; loopback is never proxied. A leak test suite (curl User-Agent, Python script, subagent, base64 query) reports leaks and false blocks.
Differs from existing: Hooks and the built-in mod read tool-call text: they miss scripts, encodings and subagents, and guess "network" from words, causing false denials. The no-email mod needs context hooks that managed settings skip. This acts on bytes actually sent, including the model request; measured by leaks and false blocks.
Needs: Harness honouring HTTPS_PROXY and a custom CA (Claude Code does); OS egress lock; org policy allowing TLS interception. No vendor change; vendor removal of the email makes rule 1 unnecessary.

### S05
Solution: Identity egress firewall — a wrapper launches the agent with all egress forced through a local TLS-inspecting proxy (HTTPS_PROXY plus NODE_EXTRA_CA_CERTS/SSL_CERT_FILE/REQUESTS_CA_BUNDLE for every child process; a Linux netns/nftables rule or the agent sandbox's proxy setting on macOS), so subagents and scripts Claude writes and runs cannot bypass it. At start it reads the signed-in email from the harness config and precomputes variants: case, percent-encoding, JSON escapes, base64, hex, split local part. Requests to loopback and the vendor API pass untouched; for all other hosts, headers and bodies are scanned and matches are replaced with a user-chosen alias (e.g. a forwarding address, so contact-required sites like sec.gov still work) and logged, never denied. Optionally it strips the injected email block from the system prompt on the vendor-API leg. A commit-msg hook rejects the address in commits.
Differs from existing: It inspects bytes on the wire, not tool-call text, so self-written scripts, subagent curl and encoded forms are caught; it is destination-aware, so heredocs and 127.0.0.1 calls are never blocked; it substitutes instead of denying; it works on managed logins. Measure: misses and false blocks on a leak corpus.
Needs: A local CA trusted by child tools (certificate-pinning clients fail closed); OS egress forcing. Prompt stripping only if org settings allow proxying the API. Vendor: supported opt-out of email injection.

### S06
Solution: Identity-alias egress proxy — A local intercepting proxy (mitmproxy addon) that every outbound request from the agent's process tree must pass. A launcher wrapper (or the settings env block) sets HTTPS_PROXY/HTTP_PROXY and adds the proxy CA via NODE_EXTRA_CA_CERTS, SSL_CERT_FILE, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE and GIT_SSL_CAINFO, so the harness, WebFetch, subagents and scripts Claude writes all inherit it (loopback exempt via NO_PROXY); a per-user firewall rule (nftables/pf) or container network makes it unavoidable, and certificate-pinning tools fail closed. Model-API traffic is tunnelled untouched. For every other host, the addon scans URL, headers and body for the user's identifiers (account email, name, phone) in plain, URL-encoded, base64, JSON-escaped and case-folded forms, and rewrites matches to a per-site relay alias, so sites like sec.gov that demand a contact address still work; block-listed hosts get 403. Every rewrite is logged.
Differs from existing: Checks the bytes that actually leave, not tool-call text: covers scripts Claude writes, subagents and encoded forms; local-only commands never reach it, so no heredoc/127.0.0.1 false positives; unaffected by managed-settings hook limits; tasks needing an address keep working. Measurable: leaks and false denials on a route test-suite.
Needs: mitmproxy or similar, CA trust via env vars, OS firewall or container, a mail-relay alias. VENDOR: removing the email from the system prompt (and model-written commits).

### S07
Solution: Identity Egress Firewall — a local MITM proxy (mitmproxy addon) through which all agent traffic must pass. On model-API requests it replaces the account email and user-listed identifiers in the request body with a placeholder (`user@redacted.invalid`), so the model, sub-agents and the scripts they write never learn the real address. On all other egress it decodes headers, URLs and bodies and searches for the identifiers in any form (case-folded, percent/JSON/quoted-printable escaped, base64 at three offsets, hex, plus-addressed), rewrites hits in headers to the placeholder, blocks bodies with an explained deny, and logs each event. OS rules force every agent process through it (nftables uid-owner rule for a dedicated agent user on Linux; the agent sandbox's custom-proxy port elsewhere), so loopback calls and file writes are never inspected. A commit-msg/pre-push hook applies the same matcher to git.
Differs from existing: It acts on bytes on the wire, not tool-call text, so scripts Claude writes, sub-agents and encoded forms are caught; only real network egress is inspected, ending local false positives; the context scrub works at the network layer, so Team/Enterprise mod restrictions do not apply.
Needs: Local CA trusted by Node/tools (NODE_EXTRA_CA_CERTS); admin approval on managed machines; vendor tolerance of API-body rewriting. Vendor: dropping the email from context is the real fix.

### S08
Solution: Alias Gateway — a local TLS-intercepting egress proxy that swaps the account email for a user-owned relay alias instead of blocking. A wrapper launches the agent in a network namespace (Linux netns/nftables; macOS sandbox-exec or a dev container) whose only route out is the proxy, with HTTPS_PROXY set and NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE trusting its CA, so scripts the agent writes cannot bypass it. In requests to the model API it rewrites the injected email in the system prompt to the alias (e.g. a SimpleLogin or Hide My Email address), so the model, sub-agents and commits only ever see the alias. In all other external traffic it scans URLs, headers and bodies for the real address in normalized forms (case, URL, base64, hex, quoted-printable, split local part/domain) and rewrites or blocks per destination rule. Loopback and private addresses pass untouched; every substitution is logged.
Differs from existing: Works at the network layer, not as a harness mod or string hook, so it applies on Team/Enterprise and managed machines, covers agent-written scripts and encodings, removes the email from model context without waiting for the vendor, and substitutes rather than denies, so sec.gov-style requests and localhost calls still succeed.
Needs: Agent honoring proxy and custom-CA env vars; an email alias service; rights to create network namespaces or sandboxes. Breaks if the vendor pins certificates (would then need a vendor opt-out).

### S09
Solution: Alias-and-canary egress layer — Two local proxies outside the harness. (1) A model-API proxy (ANTHROPIC_BASE_URL) rewrites the account email in every outgoing model request to a per-machine alias such as `dev-7f3a@alias.invalid`, so the model, sub-agents, scripts and commits only ever know the alias. (2) A TLS-intercepting egress proxy (HTTPS_PROXY, local CA exported via NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE; a firewall rule lets only the proxy reach the internet, so agent-written scripts cannot bypass it) decodes URLs, headers and bodies (percent, base64, punycode, JSON escapes) and strips or blocks the real email, the alias and listed PII toward non-allowlisted hosts. Loopback traffic never passes through it. Every alias hit is logged with destination, making leaks a measurable count; a regression suite of exfiltration routes (curl, python, node, sub-agent, encoded headers) must score zero.
Differs from existing: Hooks and the built-in check match tool-call strings (email plus a network word); this inspects decoded bytes on the wire and the model's input, so it covers agent-written scripts, sub-agents and encodings, gives no loopback false positives, and works on Team/Enterprise logins where prompt.context mods are skipped.
Needs: Harness honouring ANTHROPIC_BASE_URL and HTTPS_PROXY (if managed settings lock them: vendor); OS firewall rights; tools trusting the local CA. Removing the email at source needs the vendor.

## P2

### S01
Solution: Policy Conformance Kit — one policy file compiled for every agent, plus tests proving what is actually enforced. Engineers write rules once (YAML: tool, command pattern, path globs, decision). The compiler emits native configs (Claude settings.json, Codex rules and project-trust entries, Gemini policy TOML) and installs one shared PreToolUse/PermissionRequest hook plus a --permission-prompt-tool MCP server as the authoritative decider. Its matcher uses a real bash parser, normalizes global flags (git -C, env prefixes), treats cd into the workspace as neutral, ignores quoting noise and decides per subcommand; because it is a hook, it also governs skills and subagents. A conformance suite generated from each rule's positive and negative examples runs every agent headlessly in a sandbox and records executed/prompted/denied per probe; CI reruns it on each agent upgrade and blocks the version bump on drift. A PTY guard answers residual prompts per policy or fails fast.
Differs from existing: Existing hooks each reimplement matching for one agent, unreviewed and unverified. This gives one cross-agent rule source, a parser-based matcher that handles global flags and quoting, and continuous conformance tests that catch regressions (yolo, bypass, workspace policies, ExitPlanMode) before unattended runs depend on them.
Needs: Agent hook and permission-prompt interfaces; sandboxed CI with agent credentials. Vendor-only: honoring hook allow for ExitPlanMode, Remote Control prompts, Gemini policy loading (detected here, not fixed).

### S02
Solution: Permission conformance harness — A test runner that checks what the installed agent actually enforces against the rules the engineer wrote. It launches the real CLI (Claude Code with ANTHROPIC_BASE_URL, Codex with a custom model_providers base_url) against a local mock model server that answers with scripted tool calls and forwards anything unscripted, such as auto-mode classifier calls, to the real API. Cases are generated from the user's own rule files: each allow/deny rule expands into variants (compound with cd, git -C and other global flags, quoted flags, bash -c/env wrappers, inside a subagent or skill, in a fresh untrusted project, under bypass/yolo). The observed outcome (ran, prompted, denied) comes from hook logs and a pty watcher, giving a per-version mismatch table. It runs in CI on each agent release and before the local auto-updater moves; the last conforming version stays pinned, and fixable mismatches get generated PermissionRequest-hook rules.
Differs from existing: Dippy, tool-gate and auto-approve hooks replace the matcher with another unverified one; this verifies whichever matcher is enforcing (built-in, hook, auto mode), catches regressions before unattended runs stall, and doubles as a bypass test for community hooks. Measurable: mismatches per release, prompt-stalls per unattended run.
Needs: Configurable model endpoint (exists in Claude Code, Codex), hooks, version pinning, CI. VENDOR: fixing mismatches hooks cannot override (ExitPlanMode, quoted-flag warning, trust prompts).

### S03
Solution: Permission conformance harness — a CI/pre-upgrade runner that black-box tests the real CLI's enforcement in a throwaway container. A fake model server (via ANTHROPIC_BASE_URL or a Codex custom provider) replays scripted tool calls: compound and cd-chained commands, quoted flags, git -C, ExitPlanMode, and the same calls issued from inside a subagent or skill. --permission-prompt-tool points at a recording MCP server, so each case's actual outcome (allowed, asked, denied) is captured at zero token cost. Expected outcomes come from a short intent file plus cases harvested from the engineer's own transcripts, where every prompt they approved or rejected is a labelled case. Output is a divergence table per CLI version. A wrapper pins the CLI and promotes a new version only when the suite passes; for each divergent case it generates a narrowly scoped PreToolUse shim and keeps it only if the whole suite, including deny cases, still passes.
Differs from existing: Hook projects are one more unverified matcher; this measures the enforcement actually delivered, catches regressions (bypass, yolo or inheritance breaks) before unattended runs, and only adds shims proven against both allow and deny cases. Measure: divergent cases per version; prompt stalls per unattended run.
Needs: CLI accepting a custom model endpoint and a permission-prompt tool; version pinning. Unfixable divergences (ExitPlanMode hook allow, Remote Control prompts, Gemini policy loading) need vendor fixes; it reports them.

### S04
Solution: Permission conformance suite — The engineer writes intent as a table: tool call, context (main agent, subagent, skill, headless, bypass mode, fresh project) and expected outcome (run, ask, deny). A runner starts the real harness binary (Claude Code, Codex, Gemini CLI) in a throwaway container with the engineer's actual settings, pointed at a stub model server (ANTHROPIC_BASE_URL or OPENAI_BASE_URL) that returns the table's tool calls as scripted responses, and drives the interactive UI through a pty. A canary side effect plus the transcript show whether each call ran, prompted or was refused; every row where enforcement differs from intent is reported. For failing rows only, it generates a minimal PreToolUse shim and re-runs the suite to prove it. CI runs the suite on every harness release; auto-update stays off and a new version is promoted only when green. Metric: mismatched rows per release.
Differs from existing: Dippy, tool-gate-hook and auto-approve hooks add another unreviewed matcher; /permissions lists rules, not behaviour. This tests what the shipped binary actually enforces, end to end across subagents, skills and modes, catches release regressions before engineers hit them, and limits hooks to proven gaps.
Needs: Harnesses accepting a custom model endpoint; a container runner. Prompts no hook can override (ExitPlanMode, Remote Control mobile, Codex trust) are detected, but fixing them needs the vendor.

### S05
Solution: Policy-as-tests (permcheck) — One agent-neutral allow/ask/deny policy file, compiled three ways. (1) Native rules for Claude Code settings, Codex config and Gemini user-level policies; a launcher adds Codex trust entries for directories under approved roots. (2) One PreToolUse/PermissionRequest decision hook registered at user level in each agent, so subagents and skills hit the same rules; it parses commands into a shell AST (mvdan/sh), normalises `cd` into the workspace, env prefixes, `git -C`, quoted flags and wrapper commands, and denies what it cannot resolve (eval, `bash -c "$x"`). (3) A conformance suite: a mock model endpoint, set through each agent's base-URL option, emits a few hundred scripted tool calls (including subagent ones) in a throwaway sandbox after every agent update. It records what each agent actually did — allowed, prompted, denied — and fails with a rule-by-rule drift report, optionally pinning the last passing version.
Differs from existing: Existing hooks replace matching but nobody checks that enforced behaviour equals the written policy. Deterministic probes catch drift (yolo regressions, ignored policy files, subagent inheritance) before unattended runs, across Claude Code, Codex and Gemini, and fail-closed parsing plus the probe corpus supply the missing security review.
Needs: Hook and base-URL support in each agent. Vendor fixes remain needed where the harness overrides hooks (ExitPlanMode allow, Remote Control prompts); the suite detects these and pins versions.

### S06
Solution: Permission conformance gate — one effect-level policy file (read/write paths, hosts, commands as normalized argv with global flags like `git -C` and leading `cd` folded into context) compiled to each harness's native rules (Claude settings, Codex rules, Gemini policy TOML) plus one shared PreToolUse/PermissionRequest decider hook, which fires inside subagents and skills too, so deny always wins regardless of native matching. A shadow log correlates PreToolUse, PermissionRequest and PostToolUse events into {command, policy verdict, actual outcome: ran/prompted/denied}. In CI, a corpus of ~200 tricky forms (cd chains, quoted flags, heredocs, subagent and skill calls) is replayed against each new harness release in a container via headless runs told to execute each command verbatim; the report lists divergences. The team's pinned harness version advances only when divergences are zero or covered by the hook. Known vendor gaps are reported, not hidden.
Differs from existing: Dippy-style hooks and auto mode also decide, but nobody checks what the installed release actually enforces. This measures it: divergence count per release, and blocks upgrades that regress (like after v2.1.77/v2.1.199). One policy covers three harnesses and subagents, not per-tool rule dialects.
Needs: Hooks in Claude Code, Codex and Gemini CLI; headless mode; version pinning. Vendor: ExitPlanMode hook-allow, Remote Control mobile prompts and Codex per-project trust need vendor fixes.

### S07
Solution: Permission conformance suite driven by a scripted model — Write the policy once, as intents with example commands (allow read-only git anywhere, including git -C; allow cd inside the workspace; deny network writes). A local mock of the model API (ANTHROPIC_BASE_URL for Claude Code, a custom model provider for Codex, the equivalent where Gemini CLI allows) replays scripted tool calls for every example, including compound, quoted-flag, subagent and skill cases, in a headless run on a throwaway repo. The harness's real decision is read from the tool_result and permission denials the mock receives next, and compared with the intent. Output: a divergence table per harness, version and permission mode. CI runs it on every harness release and rule change; version pinning rolls out only releases that pass; divergent cases get generated PreToolUse/PermissionRequest hook rules, and cases hooks cannot override (ExitPlanMode, Remote Control prompts) become upstream bug reports.
Differs from existing: Dippy-style hooks re-implement matching without showing what the harness actually enforces; built-in rules and auto mode offer no test. This measures intended-versus-enforced mismatches deterministically per harness, version and mode, catches regressions before rollout, and limits custom hooks to measured gaps.
Needs: Harness model-endpoint override and headless mode (Claude Code, Codex; Gemini to verify); version pinning. Vendor: fixes for prompts hooks cannot override (ExitPlanMode, Remote Control).

### S08
Solution: permcheck — one policy, compiled per agent, and verified against the real agents. Engineers write a single policy (allow/ask/deny by tool, path and command semantics). A real shell parser (tree-sitter-bash) normalizes commands before matching: splits compounds and subshells, drops `cd` into the workspace, unwraps env prefixes, `sh -c`, `xargs` and `timeout`, and canonicalizes global flags (`git -C x commit` → `git commit`). The compiler emits each agent's native config (Claude settings.json, Codex rules plus `trust_level` entries for every repo under declared roots, Gemini policy TOML) and one enforcement hook installed at user and managed level, so subagents and skills get it too. `permcheck test` runs each installed agent headlessly in a throwaway container against a probe corpus (compounds, quoted flags, python -c, known bypasses) whose binaries are shims that only record calls, and reports intended versus actual allow/prompt/deny. It runs in CI and before every agent upgrade.
Differs from existing: Existing tools add yet another matcher with no proof it is applied; this measures what each agent version actually enforces, catching regressions (broken skip-permissions/yolo, ignored workspace policies, uninherited rules) before unattended runs stall, from one source of truth across Claude, Codex and Gemini.
Needs: Headless modes and hook APIs of each agent; a container runtime. Vendor fixes are still needed for defects it exposes, such as ExitPlanMode ignoring hook allows and mobile prompts.

### S09
Solution: Permission conformance tests — engineers write expected outcomes as a table: tool call, context (main agent, subagent, skill, plan exit), mode (default, auto, bypass) → allow, ask or deny. A runner starts the real installed CLI headless inside a throwaway container, pointed at a local mock model endpoint (ANTHROPIC_BASE_URL; a Codex custom model provider) that replays each case as a scripted tool call. Outcomes come from evidence: a recording --permission-prompt-tool marks ask, PATH shims record execution without side effects, denial text in the returned tool result marks deny. It runs in CI on every CLI version bump and settings change, blocks upgrades that regress, and emits a minimal PreToolUse hook covering only the failing cases, retired automatically once the native matcher passes. A transcript-mining mode lists real commands that prompted despite a matching allow rule and adds them as cases.
Differs from existing: Hook projects replace the matcher with another unreviewed parser; this checks the real enforcement point against the engineer's own expectations, catches regressions (cd prompts, bypass, subagent inheritance) before an unattended run, and keeps workarounds minimal and self-retiring. Measure: conformance rate per version; stalls per unattended run.
Needs: CLI support for a custom model endpoint and headless mode (Claude Code, Codex; Gemini CLI if overridable). No vendor change; a vendor dry-run 'explain decision' command would remove the mock.

## P3

### S01
Solution: Forge-native agent runner — a container image (Claude Code or Codex CLI, headless) plus pipeline templates for GitLab CI (any tier), Bitbucket Pipelines, Azure Pipelines and Jenkins (for Bitbucket Data Center), and a webhook relay. Assigning an issue to an agent user in Linear (Agents API), Jira (Automation webhook), Azure Boards (service hook) or GitLab, or an `@agent` comment on an MR, makes the relay start the pipeline with the ticket text and links. The job pushes a branch and opens the MR with a repo-scoped bot token held as a masked CI variable, through a Renovate-style platform adapter. The session transcript is cached as an artifact keyed by MR, so each later MR comment starts a job that runs `--resume`, continues the same session and replies in the thread. Code stays on the org's forge and runners except for model-API calls. Metric: forge/tier combinations covered, ticket-to-MR time.
Differs from existing: Unlike Cursor, GitLab Duo and Linear sessions, it needs no GitHub, no Premium tier or feature flag and no beta integration, and covers Bitbucket Data Center and Azure DevOps Server. Unlike GitLab's `@claude` CI, it starts from any tracker or forge and resumes one session per MR.
Needs: CI runners with outbound access to the model API; an API key or Bedrock/Vertex account; a webhook relay host. Vendor: only for native claude.ai/code or Codex web support.

### S02
Solution: Shadow-mirror forge bridge — A small self-hosted service connects any git forge (GitLab, Bitbucket Cloud or Data Center, Azure DevOps, Gerrit) and tracker (Linear, Jira, Azure Boards) to the vendors' GitHub-only cloud sessions. It keeps a private GitHub mirror of each repo, synced from the origin on every push webhook; mirror main is protected and the agent may push only agent branches. Assigning a ticket or mentioning the agent's service account starts a cloud session on the mirror through the vendor CLI (for example `claude --cloud`) with a prompt built from the ticket, its comments and linked MRs. When the agent pushes, the bridge pushes the branch to the origin, opens the MR there linked to the ticket, relays origin review comments into a follow-up session on the same branch, updates ticket status, and deletes mirror branches after merge. Metric: manual steps per delegated ticket (target zero).
Differs from existing: Native options are per forge, beta or tier-gated (GitLab Premium/Ultimate, Cursor beta, no Bitbucket Data Center), or require GitHub outright. One adapter layer reuses the cloud sessions teams already pay for on any git forge and removes manual context copying, branch handling and MR creation.
Needs: A private GitHub org with the vendor's app; policy allowing code on GitHub (otherwise run the adapters with a self-hosted runner); forge and tracker tokens. Native support needs the vendor.

### S03
Solution: Forge bridge over proxy-injected credentials — A small webhook service listens to Linear agent assignments, Jira, Azure Boards, GitLab and Bitbucket mentions or assignments. On trigger it starts a vendor cloud session (e.g. claude --cloud) on a stub GitHub repo that holds only bridge config, no source. The environment stores a forge token as a network secret (basic auth) for the forge host, so the session clones the real repo from GitLab, Bitbucket or Azure DevOps over HTTPS and pushes back without the token entering the VM. A forge-neutral CLI in the stub repo (branch, push, open MR/PR, comment, link ticket) wraps each forge's REST API. The agent opens the MR on the origin forge and posts the link to the ticket; a review comment addressed to the agent starts a follow-up session on that branch with the comments as prompt. Self-hosted environments use the runner's own forge credential instead.
Differs from existing: Native integrations wait on vendors per forge, are beta or Premium-gated, and skip Bitbucket Data Center and Azure DevOps Server; cyrus needs self-hosted compute. This reuses the GitHub-only cloud session, keeps source off GitHub and works with any HTTPS git forge. Measured: manual steps from ticket to MR.
Needs: Claude Code network secrets on the plan (Team gap is vendor-side); forge reachable from vendor cloud (otherwise a self-hosted environment); CLI session launch accepting a stub repo.

### S04
Solution: Forge Shadow Bridge — a service that gives GitHub-only agents a private GitHub mirror of each GitLab, Bitbucket (Cloud or Data Center) or Azure DevOps repo, keeping the origin authoritative. Needs: A private GitHub org and approval to mirror code there (data residency if required); forge webhooks and API tokens; vendor cloud-session CLIs. No vendor change.

### S05
Solution: Forge Shadow Bridge — a self-hosted service that lets GitHub-only cloud agents work on GitLab, Bitbucket (including Data Center) and Azure DevOps code, triggered from Jira, Linear, ADO Boards or GitLab issues.
