# Batch

## X16
P: Infra engineers running parallel agent sessions must approve each mutating kubectl/helm/terraform command. Prompts pile up, so sessions stall, or engineers rubber-stamp or allow broad patterns like Bash(kubectl:*), letting an out-of-scope delete or replace through. P*: mutating commands of tools with machine-readable dry-run (Terraform/OpenTofu, kubectl, Helm, Pulumi).
Se: Claude Code permission rules, PreToolUse hooks and Auto mode judge the command string or transcript, not its effect: `kubectl apply -f x.yaml` is harmless or fatal depending on x. Atlantis plus Sentinel/OPA check terraform plan JSON, but with static org-wide policies, via a PR round-trip, terraform-only, still human-applied.
Sn: Scope-bound effect approval. At handoff the human confirms a scope manifest: allowed contexts/namespaces/resource-address globs, allowed actions (e.g., no delete or replace) and a max change count. A PreToolUse hook intercepts mutating infra commands, runs the tool's own dry-run (`terraform plan -out` then `show -json`; `kubectl apply --dry-run=server -o json`; `helm upgrade --dry-run` or helm diff), parses it into (target, action) tuples, and auto-approves only if every tuple is in scope. It then executes exactly the checked artifact (saved plan file; validated manifest with resourceVersion precondition). Anything else blocks with a compact diff for the human.
Check: Replay real tasks with seeded out-of-scope changes. Measure human prompts per task (vs allowlist rules) and seeded deletes/replaces reaching apply (vs Auto mode). Sn wins if prompts drop ≥50% with zero escapes and no plan-to-apply drift.

## X17
P: Ops engineers running several agent sessions in parallel against different clusters, accounts and Terraform workspaces share ambient state (~/.kube/config current-context, AWS SSO cache, gcloud config). One session's `kubectl config use-context prod` silently retargets all others; stray flags or defaults send commands to the wrong environment.
Se: kubie/kubectx or direnv giving each worktree its own KUBECONFIG/AWS_PROFILE, plus permission deny rules and a status line. Agents can still read global configs and SSO caches or override via flags; prefix-matching rules miss env, flags and compound commands; the status line shows the shell's context, not each command's.
Sn: Session target binding. At session start the harness binds an explicit target set (kube context+namespaces, cloud account/role, Terraform backend key/workspace, host group) and mints short-lived credentials valid only for it (STS AssumeRole with session tags, Kubernetes TokenRequest for a namespaced ServiceAccount, SSH certificate with limited principals). It writes session-private KUBECONFIG, AWS_CONFIG_FILE and CLOUDSDK_CONFIG, hides the global ones in the sandbox, and resolves each infra command's effective target from flags, env and files before running; out-of-binding commands are denied with the reason. Retargeting requires an explicit human re-bind. Every tool call displays its resolved target.
Check: Seeded trial: eight parallel sessions with distinct targets plus injected retargeting (use-context, --profile, export, edited kubeconfig). Commands reaching an unbound cluster/account: Sn zero versus Se nonzero, with equal or fewer human prompts per task.

## X18
P: Parallel agent sessions in separate git worktrees each test and apply to the same shared environment (staging cluster, Helm release, Terraform state). Session B applies from a branch missing session A's unmerged change and silently reverts it; both report success, and the breakage surfaces later as unexplained drift.
Se: Worktrees isolate code, not live infrastructure. Terraform state locking only serializes applies; it never asks whether the applier has the other's changes. GitOps (Argo CD, Flux) and Atlantis avoid this only when nobody applies directly, which agents iterating in dev and staging routinely do.
Sn: Provenance-checked applies. The apply wrapper stamps every target it changes with session id and source commit (Kubernetes annotation, Helm release description, a sidecar object beside the Terraform state). Before any apply it reads the live stamp; if that commit is not an ancestor of the local HEAD, the apply is refused: "staging/payments last applied by session X from branch foo at abc123; merge it, wait for its merge, or ask for an override." The agent can then fetch and merge that commit itself. Uncommitted trees cannot apply. Overrides are logged and re-stamp the target.
Check: Run paired parallel sessions on shared staging with overlapping tasks. Count silent reverts (an applied change missing from final live state) and time lost to blocked applies, versus worktrees plus state locking.

## X19
P: Ops agents routinely run kubectl get secret, helm get values, terraform output -json or env. The values land in model context, API requests and local transcripts that are kept, synced and shared, so security teams bar agents from production. P*: secrets surfaced in output of structured ops tools.
Se: Secret injectors (1Password op run, Vault Agent) mask only values they injected themselves; secrets read from clusters or Terraform state pass through. Deny rules only block reading files like .env. Regex/NER redactors (gitleaks patterns, Presidio-based gateway guardrails) miss low-entropy passwords, and redacted values become unusable to the agent.
Sn: Schema-aware secret handles. A tool-output filter parses known ops outputs and replaces every value the format marks secret (Kubernetes Secret data/stringData, Terraform sensitive outputs and attributes, Vault response data), plus any exact recurrence of those values (raw and base64) elsewhere in output, with a stable handle like {{secret:prod/db/password#3f2a}}. A local session vault keeps the mapping. When the agent later runs a command containing a handle, the executor substitutes the real value only inside the spawned process, so tasks still work while context, transcripts and API traffic never carry the value.
Check: Seed canary secrets, including dictionary-word passwords, in a test cluster and Terraform state; run 30 ops tasks. Canary occurrences in API requests and transcripts: Sn zero versus regex-redaction baseline, at equal task success rate.

## X20
P: Long multi-part ops tasks (rolling upgrades across clusters, multi-stack Terraform migrations) get interrupted by stream timeouts, unparseable tool calls, usage-limit pauses, compaction or crashes. The resumed agent doesn't know whether the last mutation completed, trusts a lossy summary, and re-runs or skips non-idempotent steps.
Se: /resume, auto-continue wrappers (claude-auto-retry) and checkpoint rewind restore conversation and local files only; compaction summaries are model-written prose. Nothing records external side effects durably, so after interruption the agent's belief about cluster and cloud state is unverified.
Sn: Write-ahead ops ledger: a pre-execution hook appends each mutating command to an on-disk ledger with intent, resolved target and a pre-state fingerprint (resourceVersion, Helm revision, Terraform state serial, package version); a post hook records exit code and post-fingerprint. After any interruption, compaction or resume, the ledger, not the summary, is re-injected. Any entry marked started-but-unfinished blocks further mutations until the agent runs the generated probe (helm history, state serial check, rollout status), and the ledger marks it completed, failed or partial. Live fingerprints diverging from the ledger also force re-reads.
Check: Fault-injection: kill 100 multi-step runs on kind clusters at random points, then resume. Count duplicated, skipped or conflicting mutations and false "done" claims; Sn should approach zero versus plain resume/auto-continue, with little extra wall time.
