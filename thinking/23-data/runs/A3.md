## I1
P: Ops engineers running several agent sessions in parallel against different clusters, accounts and Terraform workspaces share ambient state (~/.kube/config current-context, AWS SSO cache, gcloud config). One session's `kubectl config use-context prod` silently retargets all others; stray flags or defaults send commands to the wrong environment.
Se: kubie/kubectx or direnv giving each worktree its own KUBECONFIG/AWS_PROFILE, plus permission deny rules and a status line. Agents can still read global configs and SSO caches or override via flags; prefix-matching rules miss env, flags and compound commands; the status line shows the shell's context, not each command's.
Sn: Session target binding. At session start the harness binds an explicit target set (kube context+namespaces, cloud account/role, Terraform backend key/workspace, host group) and mints short-lived credentials valid only for it (STS AssumeRole with session tags, Kubernetes TokenRequest for a namespaced ServiceAccount, SSH certificate with limited principals). It writes session-private KUBECONFIG, AWS_CONFIG_FILE and CLOUDSDK_CONFIG, hides the global ones in the sandbox, and resolves each infra command's effective target from flags, env and files before running; out-of-binding commands are denied with the reason. Retargeting requires an explicit human re-bind. Every tool call displays its resolved target.
Check: Seeded trial: eight parallel sessions with distinct targets plus injected retargeting (use-context, --profile, export, edited kubeconfig). Commands reaching an unbound cluster/account: Sn zero versus Se nonzero, with equal or fewer human prompts per task.

## I2
P: Ops engineers approving agent infrastructure mutations (terraform apply, helm upgrade, kubectl apply) see only a command string, often on a phone via remote control. Approvals become rubber stamps, or they allow `terraform apply` wholesale, so a forced replacement or deletion of a production resource passes unseen.
Se: Claude Code auto mode and allow/deny rules judge command text and transcript, not effects. OPA/Sentinel checks on plans run in Atlantis, Spacelift or Terraform Cloud pipelines, which local agent sessions bypass. helm diff and kubectl diff exist, but agents run them optionally and humans read raw output.
Sn: Effect-gated approval. A pre-execution hook recognizes mutating infra commands and first runs their dry-run twin (terraform plan -out, helm diff upgrade, kubectl diff --server-side, ansible --check --diff). It normalizes the result into a change set (resource, create/update/replace/delete, changed fields, counts) and evaluates Rego policy: e.g., auto-allow non-prod updates; require a human for deletes, replacements, IAM or prod. The human sees the compact change set, not the command. Approval binds to the artifact (saved plan file, or manifest hash plus resourceVersion preconditions); if the live state drifted, execution aborts and re-previews.
Check: Replay 200 recorded agent mutations with seeded destructive changes: Sn surfaces more seeded deletes/replacements, needs fewer human prompts, and executes nothing differing from what was approved, versus auto mode plus allow rules.

## I3
P: During long multi-step ops tasks (upgrading six Helm releases, migrating Terraform state), sessions die mid-mutation from usage limits, stream timeouts, unparseable tool calls or crashes. On resume or handoff, the agent cannot tell which steps landed; it re-runs non-idempotent steps or abandons half-applied changes.
Se: --resume plus auto-continue tools (claude-auto-retry) restore the conversation and type 'continue'; checkpoints/rewind revert local file edits only; in-context todo lists blur under compaction. None knows whether the apply running when the session died completed, failed or is still running.
Sn: Mutation journal with reconcile-on-resume. The agent records its plan as journal steps: id, command, target, precondition probe, postcondition probe (e.g., helm history revision, kubectl rollout status, terraform plan -detailed-exitcode returning 0). Mutating commands run detached under a supervisor that writes start, exit code and output tail to the journal even if the agent process dies. On any resume or handoff, to another session or another vendor's agent, the harness runs postcondition probes for started-but-unconfirmed steps, marks each done/not-done/unknown, blocks re-running completed step ids, and hands the agent this reconciled state instead of the old transcript.
Check: Fault injection: kill 100 multi-step rollout sessions at random points, then resume. Count duplicate or conflicting mutations, abandoned half-applied changes and human recovery minutes: Sn versus --resume with auto-continue.

## I4
P: While debugging, agents run kubectl get secret -o yaml, terraform state show, helm get values, env or docker inspect. Credentials then land in model context, provider logs, local transcripts and compaction summaries, forcing rotations and compliance incidents and making security teams restrict agent use in ops.
Se: Sandbox read-denies and hooks block .env or ~/.aws; secret managers (op run, Vault Agent) inject at runtime; gitleaks scans commits; web sessions warn against secrets in env vars. These guard files and commits, not command output, so secrets fetched via kubectl or terraform still reach the model.
Sn: Secret handles at the tool-result boundary. Before any tool output enters context or logs, an interceptor finds secret values: Kubernetes Secret data, Terraform sensitive attributes (from show -json sensitive maps), known credential formats, high-entropy tokens, and exact matches against hashes of values held in Vault or the cloud secret manager. Each is replaced by a handle like {{secret:prod/db#password}}, stored in a per-session vault. The agent can pass handles into later commands; the executor substitutes real values inside the sandbox at run time and re-masks any echo. Revealing a raw value needs explicit human approval.
Check: Red-team suite of 300 ops debugging tasks seeded with canary credentials: canary bytes reaching transcripts or API requests, Sn near zero versus Se many, while task success stays within two points.

## I5
P: Ops engineers let agents work across dozens of SSH hosts. Actions become `ssh host '...'` strings or shell loops over host lists: local sandbox, permission rules, checkpoints and logs stop at the ssh boundary, quoting defeats rule matching, and one approval can mutate a whole fleet.
Se: Teleport or Boundary give role-based SSH, short-lived certificates and session recording; Ansible offers check mode and serial waves. They authorize logins or playbooks, not individual agent commands; the harness still sees an opaque ssh string, and installing an agent on every host is impractical.
Sn: Policy-carrying remote exec. The harness blocks raw ssh and pssh in Bash and offers RemoteExec(host-selector, argv, mode). Over the existing SSH connection it pushes a small static shim that re-parses argv and enforces the same allow/deny rules on the host; read mode runs inside a read-only mount namespace with no privilege escalation. Every remote call is logged with host, argv and exit code. Write mode on several hosts runs canary-first waves with a verify probe, halting on failure. Rules can name host groups, e.g., RemoteExec(prod-db, write, systemctl restart pgbouncer).
Check: 50-host lab with seeded risky tasks: count unreviewed remote mutations and hosts broken before halt, Sn versus ssh through Teleport with prefix rules; also human approvals per fleet task.
