## cc-projects
### Analysis
Diverge: (1) a planner session writes a task graph into the repo; (2) an orchestrator agent launches and steers cloud sessions; (3) GitHub issues as the task queue, with labels for state; (4) one branch and one PR per task, with acceptance tests written before work starts; (5) interfaces and stubs committed first, so parallel tasks do not collide; (6) a status board built from PR and CI state, not from chat; (7) a fresh verifier session reviews each PR against its task spec; (8) a merge train onto an integration branch that runs the full test suite after each merge; (9) a dispatcher that knows the usage budget and limits how many sessions run at once; (10) the human approves only the plan and the final merge.

Converge: the coordination cost comes from four manual loops: splitting the goal, assigning tasks, tracking progress, and checking and stitching results. Cloud sessions can already open PRs and run tests, so PRs and CI make a reliable status channel and chat recall is not needed. Splitting is done best once, up front, as a reviewable file with owned paths and acceptance commands. That cuts merge conflicts and makes "done" checkable. Checking should not be left to the session that wrote the code. Stitching is mechanical once tasks merge in dependency order with a full test run after each merge. Usage limits rule out unlimited fan-out, so the dispatcher must cap concurrency. A fully autonomous orchestrator agent (2) and issue labels (3) mostly move the same tracking work somewhere else. Keep (1)+(4)+(5) as the core, (7)+(8) for verification and integration, and (6)+(9) for visibility and budget.

### Proposals
P1: Plan-as-code dispatcher — A planner session turns the goal into plan.yaml. Each task has an id, owned paths, dependencies, an acceptance command, and interface stubs committed first. The human approves the plan once. A small dispatcher starts one cloud session per ready task from a template (spec, owned paths, acceptance command, branch name task/<id>). Each session must open a PR tagged with the task id. Progress is read from branches, PRs and CI, never from chat.
P2: Independent verifier plus merge train — For each PR, a fresh session that did not write it checks four things: only owned paths changed, the acceptance command passes, no tests were deleted or weakened, and the diff matches the spec. Passing PRs merge in dependency order into an integration branch, with the full test suite run after each merge. If a merge fails the suite, it is reverted automatically and the task is requeued with the failure log added.
P3: Budget-aware status board — A script polls GitHub for task/<id> branches, PRs and check results. It renders a table with each task's state (queued, running, PR open, verified, merged, failed), its blocker and its last activity. The dispatcher starts a task only when its dependencies have merged, and caps concurrent sessions at a limit set in plan.yaml from the subscription quota.

## honest-arch-diagrams
### Analysis
Diverge: (1) deterministic parsers per source build a fact graph, and the LLM only labels and lays it out; (2) every node and edge cites its evidence (file plus JSON pointer); (3) confidence tiers: observed in traces, declared in manifests, inferred from naming; (4) a verify command that rejects diagram elements without evidence; (5) explicit "unknown" boxes for unresolved hosts instead of guessed components; (6) a diff between declared and observed edges; (7) secret hygiene: read Secret names and keys only, and drop env values that are not plain endpoints; (8) Mermaid/D2 output with a legend and footnotes; (9) golden tests on fixture estates; (10) a skill that tells the agent to run the CLI and forbids adding edges by hand.

Converge: the failure is invention, so the fix is to take the model out of deciding what exists. A Node CLI with no dependencies can parse JSON sources natively (kubectl, terraform show -json, OpenAPI JSON, OTLP JSON). For YAML it can either require rendered JSON input (helm template piped to a JSON converter the user already has) or ship a small parser for the YAML subset Kubernetes uses. Edges come only from concrete links: Ingress to Service backends, Service selectors to workloads, env or config values that resolve to in-cluster Service DNS names, terraform resource references, compose depends_on and networks, and trace parent/child spans across services. Anything that does not resolve is shown as unknown, never filled in. Tiers let one diagram combine traces and manifests honestly. A verify gate covers agents that still draw diagrams themselves. Secrets: never print Secret data, strip userinfo from URLs, and scan the final output for high-entropy strings. Ideas (1), (2), (3), (5), (4) and (7) survive. Golden tests are build hygiene, not a proposal.

### Proposals
P1: Evidence-cited fact graph — The Node CLI has one parser per source. Each parser emits nodes and edges carrying evidence {file, JSON pointer, source kind}. Edges come only from resolvable links: Ingress to Service, selector to Deployment, env value to Service DNS name, terraform reference, compose link, cross-service trace span. The renderer emits Mermaid with numbered evidence footnotes. With no evidence, nothing is drawn. The skill tells the agent to run the CLI and only add prose.
P2: Confidence tiers and explicit gaps — Every edge gets a tier: observed (trace spans), declared (manifests or terraform), or inferred (naming heuristics). Tiers render as solid, dashed and dotted lines with a legend. Hosts that resolve to nothing become "unresolved: <host>" boxes rather than guessed Redis or gateway nodes. A section under the diagram lists edges seen in traces but not declared, and edges declared but never observed.
P3: Verify gate with secret hygiene — `verify diagram.mmd` parses any diagram an agent wrote and checks each node and edge against the fact graph. It exits non-zero and lists unsupported elements, and the skill requires a pass before the diagram is shown. Secret objects are read only for names and keys. URLs lose their userinfo, and values are dropped unless they parse as host:port. A final pass masks high-entropy strings.

## squadra
### Analysis
Diverge: (1) an append-only event ledger shared by all checkouts; (2) per-agent inbox files with acknowledgement nonces; (3) confirming receipt by scanning on-disk transcripts for the nonce; (4) test evidence tied to the exact working-tree hash; (5) reviews tied to that same hash, and shipping gated on hash equality; (6) the reviewer must be a different harness or session than the author; (7) task claims as leases that expire; (8) a `brief` command that rebuilds context for a new window; (9) a decision log with timestamps; (10) a single git branch carrying coordination state.

Converge: the constraints rule out push. Codex cannot wake Claude, and Cursor is never launched, so coordination must be pull-based plus visible to the human. Agents read their inbox when instructed (AGENTS.md or CLAUDE.md snippets), and the tool shows which assignments were never received so the human can nudge that window. Several checkouts of one project share the git common dir, which is a natural place for a shared ledger with no server. "Which code was tested or reviewed" is answered precisely by recording a tree hash: `git write-tree` on a temporary index that includes uncommitted changes. Self-review is countered by requiring a reviewer identity that differs from the author's. Context loss is countered by folding the ledger into a brief. Ideas (1), (4), (5), (6), (8) and (9) form the core, with (2)+(3) for receipt. A git branch for state (10) causes merge friction, so the ledger is better.

### Proposals
P1: Content-bound event ledger — A Python stdlib CLI appends JSONL events to a ledger in the git common dir, shared by every checkout. Event types: task created, claimed (agent, checkout, lease), assigned, acked, tested (command, exit code, tree hash including uncommitted changes), reviewed (tree hash, reviewer), decided (text, time). `status` folds the events into current state. `brief <agent>` prints that agent's tasks and the recent decisions, so a new window recovers.
P2: Inbox with transcript-verified receipt — Each assignment goes to a per-agent inbox with a nonce. Instruction snippets tell agents to run `squadra inbox` at turn start and `squadra ack <nonce>`. For unacked items, the tool scans that harness's transcript files for the nonce and reports "not seen", "seen, not acked" or "acked". Status lists stale assignments so the human can prompt that window by hand. Nothing is launched or woken automatically.
P3: Ship gate on identical trees — `squadra check-ship <task>` passes only if three things hold: the latest passing test event's tree hash equals the branch HEAD tree, a review event exists for that same hash from a different harness or session than the author, and nothing changed after the review. Otherwise it lists exactly what is missing. It never pushes or publishes; it prints the command for the human.

## termaxa
### Analysis
Diverge: (1) a shell tokenizer plus a rule engine that classifies commands as irreversible; (2) state-aware decisions that check whether anything would actually be lost; (3) deny with a message naming a safer equivalent, so the agent corrects itself; (4) create a recovery point before allowing a risky command; (5) a repo policy file with rules for each tool; (6) an audit journal and an undo command; (7) requiring a dry run or plan before infrastructure changes; (8) protected paths for write tools; (9) environment and context awareness (production kube context, protected branches); (10) a policy test suite run in CI.

Converge: the setting is unattended. A hook that only asks for approval just stalls the agent, so the useful outcomes are allow, allow after taking a recovery point, or deny with a reason the agent can act on. Static pattern matching alone gives false positives that teach users to switch it off. Checking real state ("are there uncommitted changes, does the remote have commits we lack, does the plan destroy anything") keeps ordinary chores working and stops only the commands that would actually lose data. Tokenizing must handle chained commands, `bash -c` wrappers, env and sudo prefixes, and aliases of the same flag. No model is allowed, so classification must be rules plus state probes. Policy must live in the repo and be testable. Since hooks advise rather than sandbox, recovery points are the backstop when a rule misses. Ideas (1)+(2)+(3) form the core, (4)+(6) the safety net, and (5)+(7)+(9)+(10) the policy layer.

### Proposals
P1: State-aware verdicts with safer alternatives — The binary tokenizes the command (chains, pipes, wrappers, prefixes) and matches rules. For risky git, filesystem, SQL and infrastructure operations it probes real state: porcelain status, remote-ahead counts, whether target paths are tracked, the current kube context, the terraform plan's destroy count. If nothing would be lost, it allows the command. Otherwise it denies and names the safer form (force-with-lease, stash first, soft reset, targeted delete), so the agent retries without help.
P2: Recovery point, then allow — For risky but legitimate commands, the hook first records a cheap restore point instead of blocking. It saves `git stash create` output and current branch tips under refs/termaxa/<id>. It copies files about to be deleted into a trash folder inside .git. For destructive SQL on small tables it dumps those tables first, and above a size limit it denies. A journal records each restore point, and `termaxa undo <id>` restores it.
P3: Reviewable, tested repo policy — .termaxa.toml in the repo defines rules for each tool. Each rule has an action (allow, deny, snapshot), conditions (protected branch, kube context pattern, plan destroy count greater than zero, protected path globs for write tools) and a message for the agent. `termaxa explain "<cmd>"` shows which rule fires and why. `termaxa test` runs fixture commands with expected verdicts in CI, so policy changes are reviewed like code.

## tokeneconomizer
### Analysis
Diverge: (1) a cost ledger from transcript usage with cache-aware pricing; (2) prune tool definitions and MCP servers that sessions on a repo never use; (3) compact instruction files; (4) a repo brief injected at session start so the agent explores less; (5) cache-stability analysis to find prefix-busting content; (6) advice on large tool outputs; (7) A/B testing of settings changes against a success measure; (8) reuse knowledge across sessions by distilling earlier transcripts; (9) suggest compaction or a fresh session at efficient points; (10) dedupe repeated file reads.

Converge: the agent is a black box with no API key, so the levers are settings files, instruction files, hooks that add context, and measurement. Every change must be reversible, and none may stop a turn, so hooks may only add context or advice. Cost must count cache reads and writes and the tool's own model calls, which use the agent's login in headless mode. Pruning tools and instructions shrinks the per-turn prefix, but it can hurt success, so it needs a controlled comparison. A repo brief targets the "never saw this repo" cost, but it must be byte-stable to stay cacheable and must be cheaper than the exploration it replaces. Cache busts (dynamic dates or git status in instruction files, mid-session tool list changes) are often the largest hidden cost and can be detected from usage fields alone. Ideas (1)+(2)+(3)+(7) form one measured loop, (4)+(8) form a second, and (5)+(6) a third. Deduping reads (10) needs to change tool results, which the hooks may not allow, so it is dropped.

### Proposals
P1: Measured, reversible settings experiments — Parse transcript usage (input, cache write, cache read, output), price each turn at cache rates, and split cost into fixed prefix (instructions plus tool definitions) and conversation. Propose changes: disable MCP servers or tools unused over N sessions, trim instruction files. Apply each change as a journaled diff, revertible with one command. Alternate sessions with and without the change, and keep it only if cost per successful task drops. Success means tests passed and work committed, with no user rework request.
P2: Stable repo brief at session start — Build a compact brief (layout, build and test commands, key modules, known pitfalls) from files and commands that earlier transcripts repeatedly explored. Generate it with the agent's own login in headless mode and count that cost. A SessionStart hook injects it byte-identical between sessions, so it stays cacheable. Regenerate only when the git tree changes materially. Keep the brief only if exploration calls and cost per task fall.
P3: Cache-bust detector — Flag mid-session spikes in cache creation tokens and attribute each to a cause: dynamic text in instruction files (dates, git status), tool list changes after MCP reconnects, edits to settings or instructions during a session. Recommend fixes, such as moving dynamic content out of the cached prefix. A PostToolUse hook only adds advice when outputs pass a size threshold, never blocking.

## transcripto
### Analysis
Diverge: (1) adapters that normalize each harness's transcripts into one event model; (2) failure detectors (tool error flags, non-zero exits, edit-match failures, timeouts, interrupts); (3) checking claims in the final message against evidence; (4) comparing the transcript with the actual git diff and filesystem; (5) a last-state view of each file and each test command; (6) a timeline report with line references; (7) a Stop hook that prints the report as the session ends; (8) severity ranking so the worst problems surface first; (9) an LLM summarizer; (10) a live watcher that tails transcripts.

Converge: the constraints are local, no accounts and no extra runtimes. That rules out an LLM summarizer (9) and points to one script in a runtime the machine already has. The real need is "what actually happened, in 30 seconds". Most silent failures show up in the structured events: error flags on tool results, exit codes, edit tools reporting no match, commands that timed out, tests whose last run after the last edit failed. Final-message claims can be matched with modest regex patterns to the evidence they imply, labelled supported, contradicted or no evidence. Ground truth on disk catches what the transcript cannot, such as reverted or never-written files. Harness formats differ, so a thin adapter layer is essential. Ideas (1)+(2)+(5)+(8) form the core, then (3), then (4)+(7). A live watcher adds little over an end-of-session report.

### Proposals
P1: Normalized events with failure detectors — One script with adapters for Claude Code JSONL, Codex and Cursor session files. Each event records tool, arguments, result, error flag, exit code, files touched and transcript line. Detectors flag errored tools, non-zero exits, failed edits, timeouts and interrupts, errors never followed by success, and tests whose last run after the final edit failed or never ran. The output is a short ranked report with transcript line references.
P2: Final-claim checker — Extract claims from the closing message with patterns ("tests pass", "created X", "updated Y", "fixed", "verified"). Match each to evidence: the last test run's exit code after the last edit, the named file existing with a matching edit event, the command actually executed. Each claim is labelled supported, contradicted or no evidence, citing transcript lines, so the engineer reads three flagged lines instead of the session.
P3: Transcript versus disk — Compare edits recorded in the transcript with the current `git status` and `git diff`. List edits the transcript claims that are absent on disk, disk changes the transcript does not explain, and claimed output files that do not exist. An optional Stop hook runs this together with P1 and P2 as the session ends and writes the report next to the transcript.

## unlazy
### Analysis
Diverge: (1) a list of required outcomes with machine-checkable predicates, written before work starts; (2) a Stop hook that refuses "done" while checks fail; (3) subagents return evidence and the parent re-runs the checks itself; (4) a fresh-context verifier subagent; (5) completeness by search: zero remaining matches of the pattern being migrated; (6) a per-item manifest for fan-out, where each item needs evidence; (7) detecting placeholders and truncation in diffs; (8) detecting removed or skipped tests and weakened assertions; (9) a progress ledger that survives context resets; (10) a final report generated from check results instead of the agent's words.

Converge: the core failure is that "done" is an assertion, not a measurement. Required outcomes must exist as checks before work starts, or the agent defines done after the fact. Checks run with ambient access and no sandbox, so commands an agent writes are a risk. The manifest must be approved by the user and hash-locked, and later edits need re-approval. Hooks need consent, so installation is an explicit step. The Stop gate needs a retry cap so it cannot loop forever, after which it reports the failures. Subagent claims become trustworthy only when the parent runs the checks itself. Truncation leaves recognizable fingerprints (placeholder comments, not-implemented stubs, skipped tests). A Node 16+ script with no dependencies can do all of this with child_process and fs. Ideas (1)+(2)+(5)+(10) form the core, (3)+(6) cover fan-out, and (7)+(8) catch truncation. A verifier subagent (4) on its own is again just an opinion.

### Proposals
P1: Locked outcome manifest with Stop gate — The skill has the agent write unlazy.json before working. It lists each required outcome with a check: command plus expected exit code, a search pattern that must count zero, a required file, or a test that must pass. The user approves it, and the tool hashes and locks it. A consent-installed Stop hook runs every check and blocks completion with the list of failures, up to N retries, then reports them. A hash mismatch means unapproved edits.
P2: Evidence-checked subagent handoffs — On fan-out, each subagent gets manifest item ids and must return JSON listing, per item, its status, the files changed and the check to run. The parent never accepts the status itself: `unlazy verify` re-runs each item's locked check in the parent's own context. Failed or missing items go to a fresh subagent with the failure output attached, and the final report lists every item's check result.
P3: Truncation and test-weakening detector — Scans the session's diff for signs of partial work: placeholder comments ("rest unchanged", "...", "TODO implement"), not-implemented stubs, newly skipped or deleted tests, removed assertions, loosened expectations, and leftover matches of the migrated pattern. It runs inside the Stop gate and as a standalone command. Findings join the check-generated final report, which replaces the agent's own "done" summary.
