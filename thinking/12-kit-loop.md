# 12 用雙向迴圈檢視 ops-context-kit

用 [11](11-double-loop-pure.md) 的最終模型（兩個相反的方向，其他由 AI 決定）跑一次。對象是 template/：CLAUDE.md（14 行）、AGENTS.md（K1–K8、K10，69 行）、TRUTH.md、tasks/、tools/、hooks。方向、轉向、停止都由執行的 AI（Claude）決定，每次轉向記在下面。

證據等級：檔案內容、行數、哪些 hook 存在是直接觀察；優化方向是這次推理的假設，還沒驗證。

## 迴圈紀錄

### 第 1 組方向：規則 ↔ 時刻

- **規則 → 時刻**：把每條規則放到 session 的時間線上，看它在哪個時刻起作用。

  | 時刻 | 起作用的 |
  |---|---|
  | 1. 開 session | SessionStart hook 列出進行中的任務；CLAUDE.md + AGENTS.md 全部載入 |
  | 2. 使用者交辦 | （沒有） |
  | 3. 規劃 | K7 查事實、K2 查有沒有別人在動 |
  | 4. 執行 | K3、K4、K5、K10；guard hook |
  | 5. 中途偏題 | K6 |
  | 6. context 壓縮 | PreCompact hook 提醒更新任務紀錄 |
  | 7. 收尾 | K8、K5 的完成證據 |
  | 8. 結束 session | K1 一句話（使用者同意後封存） |
  | 9. 跨 session 學習 | （沒有：規則只在 method/ 的大型實驗裡修改） |

- **時刻 → 規則**：反過來從時刻看需要什麼。時刻 2、8、9 沒有任何機制支撐；時刻 4 有四條規則加一個 hook。K5、K8、K10 只在某個時刻有用，卻每次都載入。
- **看到的**：kit 在「執行」很強，在兩端很弱：入口（交辦）、出口（結束）、學習。長度不是問題（69 行遠低於社群的 200 行預算），問題是規則依主題排列，不是依時刻。
- **轉向理由**：這組方向已經畫出完整的時間線，再走只會重複。換一組看「誰在做事」。

### 第 2 組方向：人 ↔ agent

- **人 → agent**：每個時刻現在由誰出力？交辦（時刻 2）由人每次手寫需求；學習（時刻 9）只靠人做實驗；多 session 的總覽要人自己去看 board。
- **agent → 人**：反過來，哪些判斷必須留給人？prod 變更的核准、規則的增刪、要不要結束 session。
- **看到的**：人花力氣的地方（寫需求、整理教訓）正好是低風險、agent 可以起草的；人該把關的地方（核准）現在已經由 K4 和 hook 處理。可以把人的工作從「寫」移到「核准」。
- **轉向理由**：這組指出入口和學習要交給 agent 起草，但還沒說清楚多個 session 之間怎麼銜接。換到「單一 ↔ 整體」。

### 第 3 組方向：單一 session ↔ 整個工作區

- **單一 → 整體**：規則幾乎都寫給單一 session。整體的問題（隔離、共用目標、共用記憶）只有 K2 的「grep 看看有沒有人在動」，而且是軟性的。
- **整體 → 單一**：任務檔已經有 `targets` 欄位（「宣告」），但目前只被 hook 拿來列清單、被 K2 拿來 grep。
- **看到的（新東西）**：`targets` 可以變成整個系統的中樞。同一個欄位可以驅動：
  - 載入哪些規則（`envs/<target>/`）。
  - 這個 session 拿得到哪些憑證（只含宣告目標的 kubeconfig、ssh config），隔離由權限保證。
  - guard 的範圍檢查：對沒宣告的目標寫入就要確認。這是對目標的白名單，比對指令的黑名單更不容易漏（試驗 1 發現黑名單補不完）。

  同理，`done-when` 可以驅動 Stop hook 的完成檢查。
- **轉向理由**：找到一個把前面發現串起來的中心，換一組方向檢查它站不站得住：規則有什麼根據。

### 第 4 組方向：規則 ↔ 證據

- **規則 → 證據**：每條 K 規則的根據是什麼？method/ 的三輪全是思想實驗（模型評審），evals/run.sh 的行為測試和消融從來沒有實際跑過。所有規則都停在 09 定義的最低證據等級（模型意見）。
- **證據 → 規則**：反過來，如果要用行為測試決定去留，哪些規則能被測？K3、K4、K5 有可觀察的行為（指令有沒有帶 context、有沒有停、有沒有備份），可以在沙盒裡測；K1、K6、K8 的效果要看多個 session 和長時間，難測。
- **看到的**：「規則依時刻搬家」和「任務檔當中樞」都是假設，要靠行為測試驗證；能測的規則優先測。
- **轉向理由**：試了第 5 組（現在 ↔ 以後，看維護成本），得到的還是「學習迴路缺失」，沒有新東西。照模型，移動不再產生新東西就停。

## 停止

第 5 組方向沒有產生新的發現，停在這裡。

## 優化方向

| 優先 | 方向 | 內容 | 來自 |
|---|---|---|---|
| 1 | 任務檔當中樞 | `targets` 驅動規則載入、憑證範圍、guard 的目標白名單；`done-when` 驅動 Stop hook 的完成檢查 | 第 3 組 |
| 2 | 補入口 | 指令集：`/start <工單>`、`/look`、`/fix`、`/change` 帶出必填欄位，填進任務檔；可接 Jira | 第 1、2 組 |
| 3 | 規則依時刻搬家 | K5、K8、K10 變成在對的時刻完整執行的 skill（`/change`、`/handoff`）；AGENTS.md 只留每次都成立的原則（K1–K4、K6、K7） | 第 1 組 |
| 4 | 補學習迴路 | session 只把建議寫進 `lessons/inbox.md`；定期用雙向迴圈審查（拿掉一條規則，行為有沒有變） | 第 1、2、4 組 |
| 5 | 補證據 | 沙盒行為測試取代思想實驗，先測 K3、K4、K5 | 第 4 組 |

## 優化的意義

這套 kit 原本的定位是「一份規則集」。跑完之後，它的意義變成：**一個以任務檔為中心的 session 生命週期系統**。

- 任務檔記下這個 session 的目的（goal）、範圍（targets）和終點（done-when）。
- 入口的指令負責填任務檔；hook、憑證、規則載入依任務檔運作；出口檢查任務檔的終點；教訓經過審查再回到規則。
- md 規則退到少數每次都成立的原則。

這也回答了最初的三個目標：流程一致靠入口和出口的指令；session 目的清楚靠任務檔；多 session 好管理靠 targets 驅動的隔離。

## 這次執行本身的觀察

- 方向是 AI 自己選的四組，沒有用到 11 列的任何一個例子，表示模型沒有被例子綁住。
- 轉向和停止的理由都是「再走下去不會有新東西」。這是 AI 的判斷，沒有外部檢驗。
- 第 3 組產生了前面討論都沒提過的東西（targets 當中樞、目標白名單），符合「產生新工具」的期待。但它是否真的比較好，要靠第 5 項的行為測試。
