# 23 社群回測：模型找出的「問題＋新解法」，後來社群真的需要嗎

2026-11-07。接 [21](21-backtest.md) 的設計檢討。

## 為什麼做

要回答決定 3：模型找到的解法值不值得採用。同時順便回答決定 1：模型值不值得繼續發展。

[00](00-original-notes.md) 的模型主張：用它可以找出一組問題 P 和新解法 Sn，而且 P 是真的、Sn 是新的、Sn 比現有最好的解法 Se 好，而且這件事不用模型比較難做到。這次逐一檢查這四點，每一關都不由產出答案的 AI 自己評。

和 21 的差別：21 拿 14 個工具當標準答案，看模型能不能撞到它們，找到別人沒做過的好點子反而拿 0 分。這次反過來，**模型提出的每一組都拿去 GitHub 逐一查證**。

## 設計（作答前登記，之後不改）

**時間切點 T = 2026-06-30**，也就是作答模型的知識截止日。T 之前的社群資料給模型找問題；T 之後的社群資料拿來驗證，模型完全看不到。

**找問題用的資料**（只用 GitHub，用 REST 搜尋 API 依下列規則自動抓取，不由我挑；每則保留標題、建立日期、反應數、留言數、內文前 600 字）：

|---|---|---|---|
| S1 | `repo:anthropics/claude-code is:issue` | 反應數 | 100 |
| S2 | `repo:openai/codex is:issue` | 反應數 | 40 |
| S3 | `repo:google-gemini/gemini-cli is:issue` | 反應數 | 20 |

共 180 則，全文在 [23-data/corpus.md](23-data/corpus.md)。

規則改過一次（作答前）：原本還有「含 `"claude code"` 和 kubectl、terraform 等關鍵字的 issue，依留言數排序」。實際抓下來大多是機器人自動產生的 issue（每日 CI 報告、懸賞活動，留言數上千），改成反應數排序也一樣雜，所以換成主要 agent 工具的 repo。代價是資料偏一般開發，infra 專屬的痛點變少。



**組別**（提示全文在 [23-data/arms/](23-data/arms/)）：

| 組 | 方法 |
|---|---|
| A | 直接做 |
| C | 原模型＋三個補充（同 21 的英文版） |

- 各跑 3 次，每次是一個獨立的 agent。
- 只准讀資料檔和最後寫一次答案，不准上網。上網就會看到 7 月以後的東西。
- **只交結果，不要求寫出思考過程**：21 發現要求寫出分析會被安全機制擋下。
- 每次交 5 組，依價值排序。每組寫 P、Se（到 6 月為止現有最好的解法和它的不足）、Sn（怎麼運作）、Check（什麼可觀察的證據能顯示 Sn 比 Se 好）。

**查證**：30 組全部打亂、拿掉組別，交給查證 agent。查證 agent 可以用 GitHub REST 搜尋和網路搜尋，每關都要附上連結。

| 關 | 問題 | 過關條件 |
|---|---|---|
| G1 真問題 | 7 月之後有人回報 P 嗎 | 2026-07-01 之後建立、讀過確認相關的 issue 至少 3 則，來自至少 2 個不同的 repo 或作者 |
| G2 新 | 6 月以前已經有人這樣做了嗎 | 找不到 2026-07-01 以前就存在、核心機制相同的工具或產品功能 |
| G3 有人要 | 7 月之後有人做出來或提出需求嗎 | 至少 1 個：7 月後建立、機制大致相同的 repo，或明確要求這種功能的 issue |
| G4 比較好（只當參考） | 7 月之後的具體失敗案例，Sn 和 Se 誰處理得了 | 最多 3 個案例，分別判斷，回報次數 |

- 7 月之後才出現的工具不影響 G2（它們算 G3 的證據）。
- 我抽查約 20% 的查證連結：連結存在、日期對、內容相關。抽查錯誤率超過 20% 就整批重查。

**主要指標**：每次執行的 5 組裡，有幾組同時通過 G1、G2、G3（記為「合格新解」）。

**次要指標**：各關通過率、G4 的勝負。

## 預測與判定

| | 預測 | 判定規則 |
|---|---|---|
| H1 | C 的合格新解比 A 多 | C 每次平均至少比 A 多 1 組，才算模型有用；差距小於 1 組，記為「這次看不出差別」 |
| H2 | 兩組都有不少 Sn 過不了 G2：直接想到的往往是已經有人做的 | 只記錄，不判定 |

- 合格新解就是決定 3 的候選，可以進下一步的實地試用。
- C 被安全機制擋下時，用同一個提示重跑一次；再被擋就記錄為缺資料。

## 限制（事先承認）

- 社群資料是很多人的平均處境，不是使用者自己的處境。這次測的是模型在公開資料上的能力。
- G3 用「有沒有人做或有沒有人要」代表價值；有人做不等於做得好。
- 查證是 AI 做的，只靠連結和抽查來約束。
- 每組只跑 3 次，差距小的時候看不出來。

## 結果

6 次作答全部完成（這次只要求交結果，沒有被安全機制擋下）。30 組都查證完，查證紀錄和連結在 [23-data/checks/](23-data/checks/)，組別對照在 `key.json`。

| | A 直接做 | C 原模型 |
|---|---|---|
| **每次的合格新解**（G1＋G2＋G3） | 1、0、2，平均 **1.0** | 0、1、2，平均 **1.0** |
| G1 真問題 | 13/15 | 14/15 |
| G2 新 | **3/15** | **4/15** |
| G3 後來有人做或有人要 | 14/15 | 15/15 |
| G4 後來的失敗案例（參考）：Sn 處理得了／Se 處理得了 | 29／4（共 42 例） | 29／5（共 45 例） |

- **H1 不成立**：兩組一樣，都是每次 1 組。
- **H2 成立**：真正擋人的是 G2。30 組裡 23 組在 6 月以前就已經有人做了，兩組都一樣。
- **G3 幾乎沒有篩選力**：30 組有 29 組過。就算點子在 6 月前已經存在，7 月後還是有人再做一次或再提一次需求。下次要加門檻，例如星數或採用量。
- **抽查**：12 個連結（6 個 repo、3 個 issue、2 個早於 7 月的工具，加上 1 個 issue 多查一次），全部存在、日期正確、內容相關，錯誤率 0。
- **遮蔽不完全**：C 組有些項目在 P 裡寫了「P*：」，可能透露出自同一種方法；查證 agent 不知道這代表哪一組。

### 6 組合格新解

| 新解 | 誰找到 | 7 月後的證據 |
|---|---|---|
| **每個 session 綁定一個目標，並給它私有的憑證環境**：只含指定 context 的 kubeconfig、只含一個 profile 的雲端設定、短效憑證，看不到全域設定 | A1、A3、C3（兩組獨立找到 3 次） | glovebox（2026-08-28，8 星）、cloudpin（10-08）、mochi-donut（10-28）、CodeAlta#186（10-19 要求每個空間獨立的 CLI 設定）、beekeeper#147（09-28 要求「不准用預設 kube context」） |
| **依實際效果審批**：攔下會改變基礎設施的指令，先跑它的 dry-run（terraform plan、helm diff、kubectl diff），依變更內容套政策，審批綁定那份 plan | A3 | plangate（2026-11-02） |
| **session 外的操作帳本**：長時間的變更交給 session 外的監督程序執行並記帳；session 斷掉、續接或換人時，先查證哪些步驟真的完成，擋住重複執行 | C2 | opencode-bgrun（07-29）、kacho-workspace 的 issue（10 月） |
| **秘密值換成代號**：依格式解析 Secret、terraform sensitive 輸出，把值換成代號；只在實際執行的程序裡換回真值，模型和紀錄都看不到 | C3 | claudepass（2026-09-09，「agent 只看到代號」） |

- 這 6 組的「新」都是**組合新**：查證 agent 的判斷是「6 月前沒有工具把這幾件事組在一起」，零件早就有（kubie 2020、destructive_command_guard 2026-01、6290 星）。這和原模型說的「現有解法＋在地差異」一致，但比「機制全新」弱。
- 7 月後做出來的工具都很小（0–8 星）。有人做、有人要，但還沒有人大量採用。
- 6 組全部是 infra 專屬，雖然資料偏一般開發。

## 結論

**決定 1（模型要不要繼續發展）**：在公開資料上，原模型和直接做找出的合格新解一樣多（[21](21-backtest.md) 也是一樣）。目前沒有證據顯示原模型的步驟有額外幫助。原模型唯一還沒公平測過的，是拿使用者自己的紀錄當在地資料。

**決定 3（要不要採用）**：最值得實地試用的是**每個 session 綁定目標與私有憑證環境**：
- 兩組獨立找到 3 次；
- 7 月後有好幾個人各自做出來或提出需求；
- 正對使用者「多 session、多叢集」的處境；
- workflow 分支的「session 綁定任務與目標」已經做了一半（guard 依任務宣告的目標把關），差的是把憑證環境也隔開。

下一步是照 [21](21-backtest.md) 檢討裡說的實地試用：每個 session 隨機決定開不開，量糾正次數、跨目標的錯誤與花的時間。
