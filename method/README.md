# 思考模型：用情境對比推導 agent 規則集

這份文件把你三篇筆記的方法（縮窄法 → 雙向問題空間探索 → 情境對比驅動的問題重構）用在一個具體的問題上：**替特定使用者、特定工作情境，找出最好的 CLAUDE.md／規則集**。

模型分兩部分：
- **推導**：決定要有哪些規則、每條放在哪一層。
- **實驗**：證明每條規則確實有用，沒用的就刪掉。

---

## 1. 形式化定義

| 符號 | 意義 |
|---|---|
| P₀ | 原始問題，整個過程中固定不變（防止問題漂移） |
| H = {h₁…hₙ} | 使用者提出的需求，**每一條都當成假設**，要附可測量的指標 |
| C | 使用者的情境（工作類型、工具、環境、限制） |
| T = {t₁…tₘ} | 從 C 抽樣出的任務集，每個任務 t 有可判定的成功條件 |
| S_e | 一般解：社群或官方已有的規則集與工具，作為基準 |
| D | 一般情境和 C 之間的差異 |
| L | S_e 在 C 裡的瓶頸（因為 D 而產生） |
| r = (內容, 層級, 成本) | 一條規則 |
| R | 規則集 |

**層級**（可靠度由高到低，成本也由高到低）

| 層級 | 載體 | 性質 | 成本 |
|---|---|---|---|
| L0 | hook、工具、權限設定 | 一定會發生，不靠模型自覺 | 寫程式、維護、可能誤擋 |
| L1 | AGENTS.md / CLAUDE.md（每次都載入） | 模型通常會遵守 | 佔上下文；規則越多，每條的遵守率越低 |
| L2 | 需要時才讀的文件、skill | 模型要判斷何時去讀 | 可能沒被讀到 |
| L3 | 狀態檔（任務紀錄、TRUTH.md） | 不是規則，是讓規則能運作的資料 | 要有人或 agent 持續更新 |

**目標函數**

```
U(R) = mean_{t∈T} s(t, R) − λ_tok·tokens(R) − λ_int·interventions(R)

R* = argmax_R U(R)    限制：lines(L1) ≤ B（預設 B = 80）
```
- s(t, R)：任務 t 在規則集 R 下的成功分數（0–1，多次執行取平均）
- interventions：使用者需要介入的次數（含不必要的確認）

**單條規則的貢獻**（往上剪枝用）

```
c_k = U(R) − U(R ∖ {k})            只在標了 k 的任務上計算
保留 k  ⇔  c_k ≥ ε  且  沒有任何任務因為 k 退步超過 δ
預設 ε = 0.10、δ = 0.15
```

## 2. 推導流程

```
 ① 固定 P₀，把需求改寫成假設
 ② 抽象化：找出一般問題 P_g 與一般解 S_e（基準）
 ③ 情境對比：一般情境 vs C，列出差異 D
 ④ 瓶頸 × 差異配對：S_e 在 C 的瓶頸 L；用 D 帶來的資源消除 L → 候選規則
 ⑤ 放置：每條規則放在能達到所需可靠度的最便宜層級
 ⑥ 往下特化（實驗）：只為「觀察到的失敗」新增規則
 ⑦ 往上剪枝（實驗）：消融每條規則，貢獻不足就刪；改寫得更一般，找出適用範圍 P*
 ⑧ 停止條件成立 → 輸出 (R*, P*)
```

### ① 需求即假設
每條需求寫成：「如果做了 X，任務集上的指標 M 會改善」。
- 測得出效果 → 保留，轉成規則或工具。
- 測不出效果，或使用者撤回 → 刪除，並記錄原因。

這一步對應筆記第三篇的核心：agent 把使用者一開始的問題描述當成假設，不當成事實。

### ② 抽象化
把 P₀ 抽象成一般問題，例如「讓多個 agent session 可靠地延續與協作」，再收集一般解 S_e：官方 best practice、社群範本、工具內建功能。抽象化**只用來取得基準**，不改變 P₀（筆記第三篇第 3 節的修正）。

### ③ 情境對比的維度
| 維度 | 問題 |
|---|---|
| 事實所在 | 「目前狀態」存在哪裡？repo？外部系統？ |
| 工作單位 | 一件工作的邊界是什麼？分支？事故？變更單？ |
| 完成證據 | 怎麼證明做完？測試？diff？觀察到的系統狀態？ |
| 共享狀態 | 多個 session 會在哪裡互相干擾？檔案？全域設定？遠端系統？ |
| 執行環境 | 用什麼介面？有哪些內建能力（session 管理、hooks）？ |
| 風險 | 錯誤可以回復嗎？影響範圍多大？ |
| 使用者偏好 | 什麼算「有效率」？哪些介入是可接受的？ |

### ④ 瓶頸 × 差異配對
對每個一般解的每個元件問兩個問題：
1. 在 C 裡，D 是否讓這個元件失效或變差？→ 得到瓶頸 L
2. D 是否帶來一般情境沒有的資源，能消除 L？→ **資源重新詮釋**（例如把桌面版內建的 session 管理當成 orchestrator）

產出候選規則 r = Adapt(S_e 的元件, L, D)。

### ⑤ 放置原則
| 這條規則如果沒被遵守… | 放哪裡 |
|---|---|
| 會造成不可逆的傷害 | **L0**（hook／權限），L1 再寫一次原因 |
| 每個任務都可能用到 | **L1**，一兩行 |
| 只在特定任務類型用到 | **L2**（文件或 skill），L1 留一行指向它 |
| 是資料而不是行為 | **L3**（狀態檔），L1 說明怎麼讀寫 |

### ⑥ 往下特化：失敗歸因
在任務集上跑目前的 R，每個失敗歸到一類，再決定補哪一層：

| 失敗類型 | 例子 | 補在 |
|---|---|---|
| 缺知識 | 不知道哪個 context 是 prod | L3（TRUTH.md）或 L1 |
| 缺流程 | 沒先看 log 就改設定 | L1 規則 |
| 缺保證 | 規則寫了但還是在 prod 直接 apply | L0 hook |
| 缺狀態 | 接續任務時不知道做到哪 | L3 任務紀錄 + L1 讀寫規則 |
| 環境限制 | 工具不支援某個動作 | 改流程或工具，不是寫規則 |

**只有觀察到的失敗才新增規則**，避免規則集膨脹。

### ⑦ 往上剪枝與一般化
- **剪枝**：對每條規則 k 跑 R ∖ {k}，用 c_k 決定去留。
- **一般化**：把保留下來的規則改寫得更一般（例如「kubectl 要帶 --context」→「所有會讀寫遠端狀態的指令都要明確指定目標」），只要分數不降就接受。
- **找 P***：在情境外的任務（例如資料庫、雲端帳號管理）上測試，規則仍有正貢獻的最大範圍就是 P*。

**第 1 輪學到的修正**（見 [round1.md](round1.md)）
- **基準飽和準則**：規則對應的行為，在無規則時已經 ≥ 0.85 → 刪除或縮短。規則重疊時，單條消融的 c_k 會趨近 0，不能單獨當作刪除依據。
- **群組消融**：互相支援的規則（例如文字規則 + 保證它的 hook）要整組拿掉再測，才看得出這組的貢獻；之後再用基準飽和與成本決定留哪一個。
- **可自行修正的錯誤不要打擾使用者**：L0 hook 分成「擋下並請 agent 修正」「要求使用者確認」「直接拒絕」三類。

**第 2 輪學到的修正**（見 [round2.md](round2.md)）
- **對手要夠強**：一定要有一組「懂這個領域的人直接寫的規則」。打贏通用範本不代表方法有用。
- **總分會掩蓋取捨**：分開報告「避免損害」「把事做完」「不必要的停頓」，並算出損益兩平的事故代價倍數。規則要多嚴，取決於危險任務的比例和事故代價，這兩個數字要從真實紀錄取得。
- **結果對、理由不對也要記下**：例如 d04 是靠「prod 一律確認」碰巧避開衝突，不是衝突檢查真的發現了衝突。換一個案例就會失效。
- **hook 這類程式要直接測，不要只靠推測**：評分者推測出 hook 會誤判，實際測試找到 7 個錯誤。能執行的部分先執行。
- **針對失敗修改後，要在新案例上驗證**：在同一批案例上驗證，會高估修改的效果。

**第 3 輪學到的修正**（見 [round3.md](round3.md)）
- **迭代才是有效的部分**：同一份失敗數據，方法修改和專家修改在新案例上都進步約 0.2；推導步驟本身沒有帶來優勢。
- **第 ⑥ 步要看絕對失敗**：不只修「規則造成的失敗」（相對於無規則變差），也要修「所有組都偏低」的行為。
- **寫成指令，不要寫成類別**：「Grep 整個 ops/、`who`、`ps`」比「看最近的登入與跡象」更容易被照做。
- **停下的門檻看三件事**：可回復性 × 環境 × 是否明確授權。只看一件，會在另外兩件上出錯。

### ⑧ 停止條件
- 往下：連續一輪迭代沒有新的失敗類型，或 L1 已達行數上限 B。
- 往上：所有規則的 c_k ≥ ε；再拿掉任何一條都會讓某個任務退步。

---

## 3. 防止問題漂移
- P₀ 和任務集 T 在一輪迭代中**凍結**，只能改 R。
- 任務集的修改另外記錄版本；換版後要重跑全部 arms，不能和舊版分數比較。
- 新規則必須連到某個失敗案例或假設；沒有來源的規則不收。

## 4. 評估要避免的兩個陷阱
- **循環評估**：規則和 grader 出自同一人時，grader 很容易只是在檢查「有沒有照規則做」。grader 要在寫規則之前，由使用者依真實任務定義（預先登記）。結果型 grader（問題有沒有解決）和流程型 grader（有沒有照流程）要分開報告。
- **評分者不獨立**：思想實驗的評分者如果是同一類模型，一致性高不代表準確。要用少量實際執行的結果校準，或混用不同的評分者。

## 5. 思想實驗模式（不實際執行模型）
`evals/thought/` 把同一套案例改成盲測思想實驗：
1. `make_packet.py` 產生兩份資料包，規則集匿名成 X1–X4、對應方式不同，規則編號統一成 §n。
2. 交給獨立評分者，每位負責 4 個案例；每組、每個 grader 都要給通過機率，以及拿掉哪條規則會讓它失敗。
3. `analyze.py` 解盲、合併、算一致性與反事實消融，並輸出和實際評估相同格式的比較報告。

適合在花錢跑實際評估之前，先篩掉明顯沒用的規則、找出措辭問題；它的結論仍需要實際執行來校準。

## 6. 已知限制
- 「最佳」只相對於 T。T 的抽樣品質決定結論的外部效度。
- 評估用的模擬環境（evals/）是單輪、無互動的，測不到人機來回的效率；這部分要靠實際使用的紀錄補充（evals/mine_sessions.py）。
- LLM 評分有變異：盡量用可程式判定的 grader，LLM grader 只用在短輸出。
- 思想實驗中的「獨立」只代表彼此看不到內容；案例作者、對手和評分者都是同一系列模型。
